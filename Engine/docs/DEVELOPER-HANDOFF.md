# Текущая структура и порядок работы проекта

Обновление 032: добавлен [каркас одного EngineRuntime.exe с game/editor DLL](RUNTIME-QUICKSTART.md), запускаемый из лаунчера. Его жизненный цикл работает на заглушках, старые примеры и реальный рендер пока используют Game. Вариант отдельного Editor.exe заменён режимом editor общего host.


Документ для передачи разработчикам. Состояние на 2026-10-04. Пути указаны относительно корня репозитория. Подробности размещения файлов — в [архитектуре папок](FOLDER-ARCHITECTURE.md), практические примеры расширения — в [руководстве по разработке](DEVELOPMENT.md).

## 1. Назначение и границы

Это учебный C++17 / Windows / Direct3D 11 движок. Приоритет — понятная структура и надёжное поведение. Долгосрочная цель — стратегии с большим количеством юнитов в духе Total War. Оптимизации добавляются по результатам измерений; полноценный ECS, универсальная система плагинов и многопоточность не являются предварительными условиями.

**Сейчас существуют два пути:** старые игры запускаются своими exe; новый Runtime Example запускается через один EngineRuntime.exe в режимах game/editor. Engine.lib — общая реализация, включаемая в host при сборке. В новом пути Engine инициализируется до загрузки Game.dll или Editor.dll. Лаунчер только выбирает проект/режим и запускает процесс.

Разработчику редактора следует начать с разделов 7–8 этого документа. Разделы 5–6 описывают старый Game как источник механизмов для переноса, а не основу нового Editor.

| Часть | Ответственность |
|---|---|
| Engine | Окно игры, D3D11, главный цикл, ввод, камера, рендер, общие компоненты и загрузчики |
| Конкретная игра | Сцена, игровые правила, собственные классы, настройки и ресурсы |
| Game/Launcher | Выбор приложения, проверка файлов и запуск отдельного процесса |
| Game/Common | Общая обвязка примеров: подготовка ресурсов, ошибки, smoke-режим |
| Agent | Инструкции помощнику, задачи, разборы и результаты проверок |

Engine не должен включать игровые исходники или выбирать конкретную игру по её имени.

## 3. Сборка и запуск

Нужны Visual Studio с C++ tools и Windows SDK 10. Скрипты выбирают установленный v145 или v143; проекты IDE по умолчанию указывают v145. Поддерживаемые конфигурации — x64 Debug и Release. Скрипты не устанавливают инструменты.

Для обычного запуска открыть папку Game и дважды щёлкнуть **Start.cmd**. Последовательность:

```text
Game/Start.cmd
  → Engine/BuildSupport/Start-Launcher.ps1
  → Engine/build.ps1
  → Engine/BuildSupport/Invoke-MSBuild.ps1
  → MSBuild проверяет и собирает Engine/Engine.sln
  → при успехе открывается Game/build/x64/Debug/EngineLauncher.exe
```

При ошибке сборки лаунчер автоматически не запускается, даже если старый exe существует. Обычная сборка включает Engine, тесты, лаунчер, EngineRuntime, Editor.dll, RuntimeExample/Game.dll, BasicExamples, Pong и SunGame. Каталог проектов содержит и Katamari, но по умолчанию она исключена из Build из-за зависимости Assimp.

Лаунчер вызывает Windows `CreateProcessW`. Для Runtime Example кнопки «Играть» и «Редактировать» передают одному EngineRuntime.exe тот же Project.json с разными --mode. Для старых записей запускается прежний exe, редактирование пока отключено. Процесс работает независимо от лаунчера. **Кнопки запуска в уже открытом лаунчере не вызывают сборку.** Подробные команды нового пути — в [инструкции Runtime](RUNTIME-QUICKSTART.md).

Прямой запуск также возможен:

```text
Game/build/x64/Debug/SunGame/SunGame.exe
Game/build/x64/Debug/BasicExamples/BasicExamples.exe
```

BasicExamples предлагает выбор «Квадраты» / «Куб». Отмена закрывает приложение. Для явного выбора доступны `--scene triangles` и `--scene cube`.

Команды из корня репозитория:

```powershell
./Engine/build.ps1
./Engine/build.ps1 -Configuration Release
./Engine/build.ps1 -Target Engine
./Engine/build.ps1 -Target SunGame
./Engine/tests/run.ps1 -NoBuild
./Game/tests/run-games.ps1
```

В IDE открыть Engine/Engine.sln. Если IDE сохранила прежний стартовый проект, выбрать EngineLauncher вручную. Перед запуском собрать решение: сборка лаунчера собирает новый Runtime и его модули, но не все старые игровые приложения.

Для Katamari после самостоятельной установки vcpkg задать VCPKG_ROOT и использовать Game/Start-With-Assimp.cmd либо `./Engine/build.ps1 -Target Katamari -EnableAssimp`. Manifest-интеграция может получать и собирать пакеты из Engine/vcpkg.json. Без зависимости выдаётся ошибка; заменяющей упрощённой сцены нет.

## 4. Когда пересобирается движок

Компиляция и запуск — разные этапы:

```text
Engine/*.cpp → объектные файлы → Engine.lib
Старые игровые *.cpp → объектные файлы + Engine.lib → игровой exe
EngineRuntime + Engine.lib → EngineRuntime.exe
Исходники нового игрового модуля → Game.dll
Исходники редактора → Editor.dll
```

При линковке нужный код Engine включается в exe. Engine.lib не загружается с диска во время исполнения. Новый host после готовности ядра отдельно загружает выбранную DLL; изменение кода модуля требует пересборки DLL и перезапуска процесса, но не перелинковки host при неизменном ABI. Поэтому две одновременно запущенные игры имеют независимые устройства, сцены и циклы.

Start.cmd каждый раз вызывает MSBuild, но MSBuild выполняет инкрементальную сборку. Вызов сборки не равен полной перекомпиляции.

| Изменение | Ожидаемая работа при сборке |
|---|---|
| Ничего не изменилось | Готовые результаты используются повторно |
| Один игровой cpp | Компиляция этого файла и перелинковка соответствующего exe |
| Один cpp движка | Компиляция файла, обновление Engine.lib, перелинковка собираемых зависимых приложений |
| Общий заголовок | Перекомпиляция использующих его единиц трансляции, затем линковка |
| Настройки компилятора или зависимости | Возможна более широкая пересборка |
| Файл Content | Копирование ресурса; C++ обычно не требуется компилировать |

Новые cpp включаются в `.vcxproj` как ClCompile. Заголовки обычно перечислены как ClInclude для IDE, а компилятор получает их через `#include`. ProjectReference связывает игру с проектом Engine; копировать cpp ядра в игровой проект не нужно.

Debug и Release имеют отдельные результаты. После изменения кода обычный порядок: закрыть игру → собрать → запустить снова. Уже запущенный процесс не получает новый код автоматически. Горячая замена DLL и перенос состояния не реализованы.

HLSL копируются при сборке, а необходимые варианты компилируются движком во время работы. Это отдельная компиляция шейдеров, не пересборка C++-библиотеки. Автоматическое обновление изменённого шейдера или текстуры в работающем приложении также не реализовано.

## 5. Последовательность старта старых игровых exe

Наиболее прямой пример — [Main.cpp SunGame](../../Game/SunGame/Source/Main.cpp):

```text
main()
  → разобрать аргументы
  → ExampleStartup::PrepareContent()
  → создать SunGameConfig
  → создать SunGame
  → Game::Initialize()
  → SunGame::BuildScene(content)
  → Game::StartGame()
  → после завершения уничтожить SunGame и ресурсы
```

**PrepareContent** определяет каталог exe, проверяет RequiredFiles.txt, устанавливает корень EngineContent и возвращает корень GameContent. До этого графическое устройство ещё не создано.

**Конструктор SunGame** сохраняет настройки. SunGame наследуется от движкового Game; создание C++-объекта само по себе не запускает цикл.

**Game::Initialize** выполняет общую инициализацию:

1. Создаёт Display и окно Windows.
2. Создаёт Player (в текущем коде это камера) и InputDevice.
3. Показывает окно.
4. Создаёт D3D11 device и swapchain — механизм вывода готового изображения.
5. Создаёт буферы изображения/глубины, базовые шейдеры, буферы данных, описание формата вершин и состояния рендера.
6. Отмечает успешную инициализацию и вызывает виртуальный AfterInitialize().

При ошибке Initialize освобождает подготовленные ресурсы и возвращает false. Игровая точка входа не должна продолжать запуск после отказа.

**BuildScene** принадлежит игре: создаёт конкретные объекты, свет, материалы, связи и настройки сцены. Регистрация компонента выполняется после создания устройства. RegisterComponent принимает владение только при RegisterResult::Ok; до этого за объект отвечает вызывающий код. Восстановленные лабораторные используют проверяющую обёртку ExampleStartup::Register.

SunGame вызывает BuildScene явно после Initialize. Если в будущем построение перенесут в AfterInitialize, прежний вызов нужно убрать, иначе сцена будет создана дважды.

**StartGame** проверяет успешную инициализацию и вызывает Run. Этот вызов блокирует текущий поток до окончания игры. Код после StartGame выполняется после остановки цикла, а не параллельно ему.

## 6. Один кадр и завершение старого Game

Реализация — [Game.cpp](../Source/MainGame/BaseGameClass/Game.cpp).

```text
Game::Run(), пока приложение работает:
  PumpMessages()             сообщения Windows и запрос завершения
  ApplyPendingResize()       отложенное изменение размеров
  вычисление deltaTime       реальное время между кадрами, с ограничением
  UpdateFrame(deltaTime)
  RenderFrame()
  EndFrame()                 вызывает Present()
  InputDevice::EndFrame()
  обновление статистики и заголовка окна
```

При свёрнутом окне цикл ждёт сообщения вместо обычного обновления и отрисовки.

Внутри UpdateFrame:

```text
Применить SimulationTimeScale и обновить TotalTime
  → ProcessHotkeys()
  → PreUpdate(deltaTime)
  → обновить камеру
  → TickComponents(deltaTime)
  → подготовить тени, свет и общие константы
  → Update() зарегистрированных компонентов
```

| Точка | Назначение |
|---|---|
| PreUpdate | Общая игровая логика перед камерой и компонентами |
| Tick компонента | Поведение отдельного объекта |
| Update компонента | Служебная подготовка преобразований и данных рендера |
| RenderFrame | Выбор Forward, Deferred или Custom и отрисовка |
| EndFrame / Present | Передача готового кадра на экран |

Зарегистрированные объекты обновляются движком; дополнительный ручной Tick может привести к двойному обновлению. Игры могут переопределять порядок: Pong обновляет ракетки/стены, затем обрабатывает мяч.

Исторический SimulationTimeScale равен 7.8. Для новой игры с обычными скоростями можно явно вызвать SetSimulationTimeScale(1.0f). Space в базовом TickComponents передаёт обычным компонентам нулевой deltaTime, но не останавливает PreUpdate и не отменяет сам вызов Tick. Это ещё не общая пауза всей симуляции. Создание/удаление объектов из обходящего их Tick требует отдельной безопасной очереди; задача 028-G.

WM_QUIT прекращает цикл. StartGame возвращает код результата. При уничтожении игрового объекта деструктор Game вызывает DestroyResources, освобождая принадлежащие ему объекты и ресурсы. Потеря графического устройства или ошибка Present также останавливает цикл с ошибкой.

## 7. Текущая основа нового Runtime

После задачи 032 уже существуют:

| Файл / проект | Что реально делает |
|---|---|
| `Engine/Runtime/Main.cpp` | Читает аргументы и Project.json, выбирает DLL режима, задаёт пути, вызывает BaseEngine::Run |
| `Engine/Source/Base/Base.cpp` | Инициализирует заглушки ядра, загружает DLL после EngineReady, владеет сессией и единственным циклом, освобождает всё в обратном порядке |
| `Engine/Source/Base/Config/BaseResources.cpp` | Реализует Initialize/DeInitialize заглушек ресурсов |
| `Engine/Include/Engine/Base/Config/BaseGameConfig.h` | Сохранённая конфигурация; графические поля ещё не используются каркасом |
| `Engine/Include/Engine/Runtime/ModuleApi.h` | ABI v1: create/start/update/overlay/stop/destroy, версия и тип модуля |
| `Editor/Source/Module.cpp` | Editor.dll: журнал открытия проекта, счётчик обновлений, overlay-заглушка |
| `Game/RuntimeExample/Source/Module.cpp` | Game.dll: тестовая игровая сессия |
| `Game/Launcher/Source/Main.cpp` | Два действия для Runtime Example; старые игры запускаются прежним способом |

У BaseEngine Initialize/StartUp/Play приватные. Модуль получает только журнал, запрос выхода и строки проекта через EngineModuleHost. **API доступа к сцене, графике и вводу ещё нет.** Наличие overlay-callback не означает наличие графического UI: сейчас он лишь пишет строку в журнал.

Старый Game всё ещё владеет настоящим окном, D3D11 и сценой старых игр. Их нужно перенести в общую основу Engine без копирования второго рендера и без вложенного Game::Run. BaseEngine, BaseResources и BaseGameConfig сохраняются; реализацию заглушек постепенно заменяем настоящими механизмами.

## 8. Внедрение редактора: согласованный контракт

Этот раздел — актуальное направление внедрения. Отдельный Editor.exe, наследование Editor от старого Game и статическая линковка конкретной игры в редактор не являются выбранным решением.

### Один exe, два режима

```text
Лаунчер → EngineRuntime.exe --project <Project.json> --mode game
             → EngineReady → Game.dll → игровая сессия

Лаунчер → EngineRuntime.exe --project <тот же Project.json> --mode editor
             → EngineReady → Editor.dll → открытие проекта
```

В каждом запуске один процесс Runtime и один владелец кадра. Лаунчер — отдельный процесс выбора/запуска. Engine.lib не является процессом. Editor.dll и при необходимости код игровых типов работают внутри host, общаются с Engine через ограниченный API; межпроцессная память для редактирования не нужна.

Editor.dll уже собирается из корневого каталога `Editor/` проектом `Editor/EditorModule.vcxproj`. Продолжать его, не создавать рядом вторую реализацию. Host определяет путь Editor.dll относительно своего exe; проект игры не подменяет редактор.

### Три независимых действия

| Действие | Нужна ли Game.dll | Запускается ли игровое поведение |
|---|---|---|
| Открыть описание проекта, контент и инструменты | Нет | Нет |
| Загрузить сцену из встроенных типов Engine | Нет | Нет |
| Создать/показать объекты пользовательских игровых типов | Нужен код этих типов; предусмотренное направление — Game.dll | Нет: только отдельное описание/регистрация типов и создание объектов в режиме редактирования |
| Начать игровую сессию | Да для проекта с игровым кодом | Да, после явного запуска игры |

**Открытие проекта не означает начало игры. Загрузка DLL тоже не должна запускать симуляцию.** Конструкторы, регистрация типов и DllMain не должны скрыто запускать игровой мир, таймеры или игровой цикл.

Сейчас режим editor вообще не загружает Game.dll. Это проверяется тестами, включая проект с отсутствующим игровым бинарником. Поле `module` пока обязательно в Project.json, но файл по этому пути редактору не требуется. Это ограничение текущей схемы данных, а не архитектурная зависимость редактора от наличия игровой DLL.

### Порядок открытия полноценного редактора

1. Host читает и проверяет описание выбранного проекта.
2. Engine самостоятельно создаёт окно, графику, ввод и базовые ресурсы. В текущем каркасе эти стадии ещё заглушки.
3. Только после готовности ядра host загружает Editor.dll, создаёт сессию и вызывает её Start.
4. Editor через расширенный редакторский API создаёт панели и открывает сведения о проекте/контенте.
5. По запросу открытия сцены Engine загружает её данные. Для встроенных типов игровой модуль не нужен.
6. Если сцене нужны игровые типы, host загружает соответствующий модуль и вызывает отдельный контракт регистрации типов, без старта игровой сессии.
7. Engine создаёт редактируемую сцену без игровых тиков. Камера редактора, интерфейс и отображение продолжают обновляться.
8. Изменение поля transform в инспекторе превращается в команду Engine; Engine применяет её безопасно и показывает результат.
9. Сохранение записывает данные сцены. Изменение позиции не переписывает C++-исходник игры и не сохраняет сырые указатели/виртуальные таблицы.
10. При закрытии удаляются callbacks, подписки и сцены, уничтожаются модульные объекты, затем выгружаются DLL и освобождается Engine.

Это будущие стадии полноценного редактора; текущий Start Editor.dll выводит только имя и путь проекта в журнал.

### Какие возможности добавить в Engine

Editor отвечает за панели, выделение, инспектор, команды пользователя и историю отмены. Engine владеет сценой, ресурсами, рендером и временем жизни объектов. Нужны небольшие интерфейсы:

- Получить список объектов и их проверяемые идентификаторы, прочитать/изменить свойства.
- Создать/удалить объект через очередь команд между обходами, без передачи изменяемого контейнера сцены наружу.
- Открыть/сохранить данные сцены, загрузить ресурс по идентификатору.
- Управлять камерой редактора и областью просмотра.
- Получить ввод с приоритетом UI: набор текста не должен двигать камеру или управлять игрой.
- Нарисовать UI в предусмотренной фазе после сцены и до единственного Present. Графический backend UI принадлежит Engine или внутреннему адаптеру; обычный редакторский API не выдаёт всё ядро или неограниченный D3D context.

Не возвращать доступ к обязательным стадиям через новый GetEngine/GetGame. Engine решает, когда применяются изменения и когда выполняется служебное обновление; Editor не заменяет основной рендер и не вызывает второй цикл.

Будущий кадр editor: события/захват ввода → Editor.Update → безопасное применение команд и служебное обновление сцены → рендер сцены → Editor.Overlay → Present. Игровые Tick/Update поведения без запущенной игровой сессии не выполняются. Служебная подготовка трансформаций и рендер продолжаются; редакторский update не равен игровому тику.

### Расширение игрового контракта

В ABI v1 есть только жизненный цикл одной активной сессии. Нет отдельной регистрации типов и одновременного владения Editor-сессией и модулем игровых типов. Эти возможности нужно добавить явно в host/ABI; они не появляются от второго LoadLibrary.

Предусмотреть отдельный контракт описания/регистрации игровых типов и отдельный старт игровой сессии. Не вызывать текущий Game.Start ради получения списка классов: он означает начало игры. Для типов нужны стабильные идентификаторы, фабрики и описание редактируемых свойств. Реестр экземпляров сцены и реестр типов — разные вещи.

При изменении структуры ABI поднять версию или ввести согласованное версионированное расширение, пересобрать модули и проверить отклонение несовместимых DLL. Сохранить C-границу без STL и исключений; владелец выделенной памяти обязан её освободить на своей стороне.

Перед выгрузкой Game.dll уничтожить все объекты её типов, убрать фабрики и callbacks из Engine/Editor. Editor не может хранить указатели на функции выгруженного модуля. Затем уничтожить оставшуюся сессию редактора/его ресурсы и выгрузить Editor.dll; ресурсы ядра освобождаются последними. Конкретный порядок очистки подписок следует задать до подключения игровых типов.

### Почему старые игры пока нельзя реально редактировать

Их сцены строятся кодом старого игрового exe. Наличие каталога игры или одного Project.json не превращает эту сцену в редактируемые данные.

Можно отдельно добавить описание старого проекта и разрешить открытие **оболочки редактора** без перевода игры на DLL. Это позволит работать с проектом/контентом, но не загрузит существующую сцену автоматически. Для отображения сцены нужны перенесённые механизмы Engine и поддерживаемый путь создания данных: сохранённая сцена либо отдельный построитель сцены без старта игрового поведения. Если используются игровые C++-типы, нужен их модульный контракт.

Кнопка «Редактировать» сейчас отключена для старых записей по правилу каталога лаунчера. Это временное ограничение реализации, не требование наличия DLL для любого редактирования. В дальнейшем доступность открытия редактора должна определяться поддерживаемым описанием проекта и установленным Editor, независимо от готовности игрового бинарника. Недоступную конкретную сцену/тип объяснять внутри редактора; неизвестные данные не удалять молча при сохранении.

Текущий Project.json допускает ровно name/module/content. Добавление пути стартовой сцены или возможностей проекта требует изменения схемы, парсера, deployment и тестов; произвольные новые поля сегодня отклоняются.

### Play из редактора

Первый вариант после появления реальных сцен: сохранить сцену или временную копию и запустить **тот же EngineRuntime.exe --mode game** отдельным процессом. Это не новый Game.exe. Открытый редактор продолжает работать в своём Runtime; тестовая игра получает другой процесс и собственную память, читает переданные файлы. Изменения во время игры не переносятся в редактируемую сцену автоматически.

Встроенный Play позже потребует отдельной копии мира, маршрутизации ввода, явных Start/Stop симуляции и уничтожения игровой копии после Stop. Он не нужен для первого редактора, как и hot reload. Сейчас ни один вариант Play из Editor.dll не реализован.

### Порядок внедрения и приёмка

1. Перенести минимальное окно/графику/сцену из старого Game в Engine, которым управляет BaseEngine; сохранить один цикл и одного владельца ресурсов.
2. Расширить API и заменить Editor.dll-заглушку одной панелью и областью просмотра со встроенным объектом. Игровая DLL для этого не требуется.
3. Добавить список объектов, выбор, изменение transform и захват ввода интерфейсом.
4. Добавить сохранение/загрузку сцены и поддерживаемое описание проекта; подключение старых проектов к оболочке можно делать независимо от миграции их игрового кода.
5. Добавить отдельно версионированный контракт игровых типов и перенести один нужный пример. Не запускать его игровую сессию при открытии редактора.
6. Добавить внешний Play через EngineRuntime; встроенный Play рассматривать отдельной задачей.

Критерии проверки:

- Оба действия лаунчера запускают один host с тем же проектом; EngineReady предшествует загрузке модулей.
- Editor открывает проект и сцену встроенных типов при отсутствующей Game.dll.
- Регистрация пользовательских типов не вызывает игровой Start и игровые тики; их объекты корректно видны и редактируются.
- Изменённый transform виден сразу и сохраняется после повторного открытия; неизвестный тип не приводит к потере исходных данных.
- Ввод в текстовом поле не двигает камеру; resize, сворачивание и закрытие работают, Present остаётся единственным.
- Отказ загрузки типа/сцены сообщает понятную причину; отказ старта и штатное закрытие не оставляют callbacks и живых объектов выгружаемой DLL.
- Внешний Play использует выбранную версию данных и не изменяет редактируемый мир самопроизвольно.

Сохранить существующие проверки `Engine/tests/run-runtime.ps1`; новые тесты должны отличать открытие проекта, регистрацию типов и начало игры. Результаты 032 подтверждают только каркас: графика и UI требуют новой автоматической и ручной приёмки.

## 9. Ресурсы и ограничения проверки

У старых игр рядом с exe находятся EngineContent, GameContent и RequiredFiles.txt. Для нового Runtime размещение и Project.json описаны в [инструкции](RUNTIME-QUICKSTART.md). Манифест проверяют и лаунчер, и прямая точка входа. ENGINE_CONTENT_ROOT / GAME_CONTENT_ROOT позволяют задать альтернативные корни. По умолчанию поиск не зависит от рабочей директории процесса.

Проверено после последнего переноса каталогов: Debug/Release собираются; EngineTests — 9/9 в каждой конфигурации; BasicExamples (обе сцены), Pong и SunGame проходят 30-кадровые запуски напрямую и через лаунчер, включая посторонний CWD и путь с пробелами. Game/Start.cmd открывает лаунчер. Эти проверки не подтверждают визуальную эквивалентность и правильность всех игровых правил.

Известные ограничения:

- Katamari требует отсутствующий в проверенном окружении vcpkg/Assimp. Её исходники прошли синтаксическую проверку, но полный запуск не проверен.
- cosy.jpg не предоставлена; сохраняется работа без соответствующих отражений.
- Материалы MTL Katamari требуют отдельного восстановления из исторических архивов и визуальной проверки.
- Копирование Content пока не удаляет устаревшие файлы в выходном каталоге.
- Горячая замена кода, перезагрузка ассетов и графический редактор не реализованы. Жизненный цикл BaseEngine и Editor.dll реализованы только в объёме заглушек 032.
