# Текущая структура и порядок работы проекта

Обновление 032: добавлен [каркас одного EngineRuntime.exe с game/editor DLL](RUNTIME-QUICKSTART.md), запускаемый из лаунчера. Его жизненный цикл работает на заглушках, старые примеры и реальный рендер пока используют Game. Вариант отдельного Editor.exe заменён режимом editor общего host.


Документ для передачи разработчикам. Состояние на 2026-10-04. Пути указаны относительно корня репозитория. Подробности размещения файлов — в [архитектуре папок](FOLDER-ARCHITECTURE.md), практические примеры расширения — в [руководстве по разработке](DEVELOPMENT.md).

## 1. Назначение и границы

Это учебный C++17 / Windows / Direct3D 11 движок. Приоритет — понятная структура и надёжное поведение. Долгосрочная цель — стратегии с большим количеством юнитов в духе Total War. Оптимизации добавляются по результатам измерений; полноценный ECS, универсальная система плагинов и многопоточность не являются предварительными условиями.

**Сейчас Engine — статическая библиотека, игры — отдельные исполняемые приложения, лаунчер — отдельная программа выбора и запуска.** Лаунчер не запускает общий экземпляр движка, к которому затем подключаются игры.

| Часть | Ответственность |
|---|---|
| Engine | Окно игры, D3D11, главный цикл, ввод, камера, рендер, общие компоненты и загрузчики |
| Конкретная игра | Сцена, игровые правила, собственные классы, настройки и ресурсы |
| Game/Launcher | Выбор приложения, проверка файлов и запуск отдельного процесса |
| Game/Common | Общая обвязка примеров: подготовка ресурсов, ошибки, smoke-режим |
| Agent | Инструкции помощнику, задачи, разборы и результаты проверок |

Engine не должен включать игровые исходники или выбирать конкретную игру по её имени.

## 3. Сборка и запуск

Нужны Visual Studio 2026 с C++ toolset v145 и Windows SDK 10. Поддерживаемые конфигурации — x64 Debug и Release. Скрипты не устанавливают инструменты.

Для обычного запуска открыть папку Game и дважды щёлкнуть **Start.cmd**. Последовательность:

```text
Game/Start.cmd
  → Engine/BuildSupport/Start-Launcher.ps1
  → Engine/build.ps1
  → Engine/BuildSupport/Invoke-MSBuild.ps1
  → MSBuild проверяет и собирает Engine/Engine.sln
  → при успехе открывается Game/build/x64/Debug/EngineLauncher.exe
```

При ошибке сборки лаунчер автоматически не запускается, даже если старый exe существует. Обычная сборка включает Engine, тесты, лаунчер, BasicExamples, Pong и SunGame. Каталог проектов содержит и Katamari, но по умолчанию она исключена из Build из-за зависимости Assimp.

После выбора игры лаунчер проверяет её exe и обязательные файлы, затем вызывает Windows `CreateProcessW`. Игра работает независимо; лаунчер можно закрыть. **Кнопка «Запустить» в уже открытом лаунчере не вызывает сборку.**

Прямой запуск также возможен:

```text
Game/build/x64/Debug/SunGame/SunGame.exe
Game/build/x64/Debug/BasicExamples/BasicExamples.exe
```

BasicExamples предлагает выбор «Квадраты» / «Куб». Отмена закрывает приложение. Для явного выбора доступны `--scene triangles` и `--scene cube`.

Команды из корня репозитория:

```powershell
./Engine/build.ps1
./Engine/build.ps1 -Configuration Release
./Engine/build.ps1 -Target Engine
./Engine/build.ps1 -Target SunGame
./Engine/tests/run.ps1 -NoBuild
./Game/tests/run-games.ps1
```

В IDE открыть Engine/Engine.sln. Если IDE сохранила прежний стартовый проект, выбрать EngineLauncher вручную. Перед запуском собрать решение: сборка одного лаунчера не собирает игровые приложения.

Для Katamari после самостоятельной установки vcpkg задать VCPKG_ROOT и использовать Game/Start-With-Assimp.cmd либо `./Engine/build.ps1 -Target Katamari -EnableAssimp`. Manifest-интеграция может получать и собирать пакеты из Engine/vcpkg.json. Без зависимости выдаётся ошибка; заменяющей упрощённой сцены нет.

## 4. Когда пересобирается движок

Компиляция и запуск — разные этапы:

```text
Engine/*.cpp → объектные файлы → Engine.lib
Игровые *.cpp → объектные файлы + Engine.lib → игровой exe
```

При линковке нужный код Engine включается в exe. Во время обычного запуска игра не загружает Engine.lib с диска. Поэтому две одновременно запущенные игры имеют независимые устройства, сцены и циклы.

Start.cmd каждый раз вызывает MSBuild, но MSBuild выполняет инкрементальную сборку. Вызов сборки не равен полной перекомпиляции.

| Изменение | Ожидаемая работа при сборке |
|---|---|
| Ничего не изменилось | Готовые результаты используются повторно |
| Один игровой cpp | Компиляция этого файла и перелинковка соответствующего exe |
| Один cpp движка | Компиляция файла, обновление Engine.lib, перелинковка собираемых зависимых приложений |
| Общий заголовок | Перекомпиляция использующих его единиц трансляции, затем линковка |
| Настройки компилятора или зависимости | Возможна более широкая пересборка |
| Файл Content | Копирование ресурса; C++ обычно не требуется компилировать |

Новые cpp включаются в `.vcxproj` как ClCompile. Заголовки обычно перечислены как ClInclude для IDE, а компилятор получает их через `#include`. ProjectReference связывает игру с проектом Engine; копировать cpp ядра в игровой проект не нужно.

Debug и Release имеют отдельные результаты. После изменения кода обычный порядок: закрыть игру → собрать → запустить снова. Уже запущенный процесс не получает новый код автоматически. Горячая замена DLL и перенос состояния не реализованы.

HLSL копируются при сборке, а необходимые варианты компилируются движком во время работы. Это отдельная компиляция шейдеров, не пересборка C++-библиотеки. Автоматическое обновление изменённого шейдера или текстуры в работающем приложении также не реализовано.

## 5. Последовательность старта игры

Наиболее прямой пример — [Main.cpp SunGame](../../Game/SunGame/Source/Main.cpp):

```text
main()
  → разобрать аргументы
  → ExampleStartup::PrepareContent()
  → создать SunGameConfig
  → создать SunGame
  → Game::Initialize()
  → SunGame::BuildScene(content)
  → Game::StartGame()
  → после завершения уничтожить SunGame и ресурсы
```

**PrepareContent** определяет каталог exe, проверяет RequiredFiles.txt, устанавливает корень EngineContent и возвращает корень GameContent. До этого графическое устройство ещё не создано.

**Конструктор SunGame** сохраняет настройки. SunGame наследуется от движкового Game; создание C++-объекта само по себе не запускает цикл.

**Game::Initialize** выполняет общую инициализацию:

1. Создаёт Display и окно Windows.
2. Создаёт Player (в текущем коде это камера) и InputDevice.
3. Показывает окно.
4. Создаёт D3D11 device и swapchain — механизм вывода готового изображения.
5. Создаёт буферы изображения/глубины, базовые шейдеры, буферы данных, описание формата вершин и состояния рендера.
6. Отмечает успешную инициализацию и вызывает виртуальный AfterInitialize().

При ошибке Initialize освобождает подготовленные ресурсы и возвращает false. Игровая точка входа не должна продолжать запуск после отказа.

**BuildScene** принадлежит игре: создаёт конкретные объекты, свет, материалы, связи и настройки сцены. Регистрация компонента выполняется после создания устройства. RegisterComponent принимает владение только при RegisterResult::Ok; до этого за объект отвечает вызывающий код. Восстановленные лабораторные используют проверяющую обёртку ExampleStartup::Register.

SunGame вызывает BuildScene явно после Initialize. Если в будущем построение перенесут в AfterInitialize, прежний вызов нужно убрать, иначе сцена будет создана дважды.

**StartGame** проверяет успешную инициализацию и вызывает Run. Этот вызов блокирует текущий поток до окончания игры. Код после StartGame выполняется после остановки цикла, а не параллельно ему.

## 6. Один кадр и завершение

Реализация — [Game.cpp](../Source/MainGame/BaseGameClass/Game.cpp).

```text
Game::Run(), пока приложение работает:
  PumpMessages()             сообщения Windows и запрос завершения
  ApplyPendingResize()       отложенное изменение размеров
  вычисление deltaTime       реальное время между кадрами, с ограничением
  UpdateFrame(deltaTime)
  RenderFrame()
  EndFrame()                 вызывает Present()
  InputDevice::EndFrame()
  обновление статистики и заголовка окна
```

При свёрнутом окне цикл ждёт сообщения вместо обычного обновления и отрисовки.

Внутри UpdateFrame:

```text
Применить SimulationTimeScale и обновить TotalTime
  → ProcessHotkeys()
  → PreUpdate(deltaTime)
  → обновить камеру
  → TickComponents(deltaTime)
  → подготовить тени, свет и общие константы
  → Update() зарегистрированных компонентов
```

| Точка | Назначение |
|---|---|
| PreUpdate | Общая игровая логика перед камерой и компонентами |
| Tick компонента | Поведение отдельного объекта |
| Update компонента | Служебная подготовка преобразований и данных рендера |
| RenderFrame | Выбор Forward, Deferred или Custom и отрисовка |
| EndFrame / Present | Передача готового кадра на экран |

Зарегистрированные объекты обновляются движком; дополнительный ручной Tick может привести к двойному обновлению. Игры могут переопределять порядок: Pong обновляет ракетки/стены, затем обрабатывает мяч.

Исторический SimulationTimeScale равен 7.8. Для новой игры с обычными скоростями можно явно вызвать SetSimulationTimeScale(1.0f). Space в базовом TickComponents передаёт обычным компонентам нулевой deltaTime, но не останавливает PreUpdate и не отменяет сам вызов Tick. Это ещё не общая пауза всей симуляции. Создание/удаление объектов из обходящего их Tick требует отдельной безопасной очереди; задача 028-G.

WM_QUIT прекращает цикл. StartGame возвращает код результата. При уничтожении игрового объекта деструктор Game вызывает DestroyResources, освобождая принадлежащие ему объекты и ресурсы. Потеря графического устройства или ошибка Present также останавливает цикл с ошибкой.

## 7. Статус BaseEngine, BaseResources и BaseGameConfig

Эти классы находятся в Engine/Include/Engine/Base и Engine/Source/Base, их cpp включены в сборку. Это сохранённая основа следующего рефакторинга, а не уже подключённый новый runtime.

- BaseEngine: методы Initialize, StartUp, Play, IsPlaying, Stop объявлены, но пока не реализованы.
- BaseResources: предоставляет пути общих шейдеров через EnginePaths; Initialize/DeInitialize пока не реализованы. Корень ресурсов нужно задавать до создания экземпляра, поскольку пути сохраняются в полях.
- BaseGameConfig: общая конфигурация сохранена; выбор номера лабораторной из неё исключён. SunGameConfig пока отдельный тип.

**Рабочий владелец окна, графики и цикла сейчас — Game.** Подключение BaseEngine и перенос обязанностей отслеживаются в 028-H. Нельзя считать перенос файлов в Engine завершённой интеграцией этих классов.

## 8. Куда подключать редактор

Этот раздел описывает предлагаемое развитие. **Редактора и указанных ниже новых точек расширения сейчас нет.**

В выбранной структуре отдельный проект редактора следует разместить в Engine/Editor:

```text
Engine/Editor/
  Source/
  Content/
  Editor.vcxproj → Editor.exe, использующий Engine.lib
```

Панели, инспектор, выбор объектов и история отмены принадлежат приложению редактора. Общие операции над объектами, устройством и рендером остаются в ядре. Библиотека Engine не должна зависеть от панелей редактора.

### Запуск процесса редактора

Открытие Editor.exe можно добавить отдельной кнопкой в Game/Launcher либо отдельным Engine/StartEditor.cmd. Сам лаунчер не превращается при этом в редактор или владельца игрового цикла.

### Инициализация интерфейса

Первое приложение редактора может наследоваться от текущего Game и использовать существующее окно и цикл:

```text
main редактора
  → подготовить пути
  → создать приложение редактора
  → Initialize(): окно и графическое устройство
  → инициализировать интерфейс редактора
  → создать/загрузить редактируемую сцену
  → StartGame(): войти в цикл
```

Существующая точка для инициализации интерфейса — AfterInitialize у производного приложения. Альтернатива — явный вызов сразу после успешного Initialize. Выбрать один способ, не вызывать инициализацию дважды.

Размещение `OpenEditor()` после `StartGame()` приведёт к открытию редактора только после завершения игры, поскольку StartGame блокирует поток.

### Работа в каждом кадре

Интерфейс нужно обновлять и рисовать каждый кадр. Планируемый порядок:

```text
Ввод → обновление редактора/сцены → RenderFrame()
     → рисование панелей редактора → EndFrame()/Present()
```

Минимальное расширение ядра — нейтральная виртуальная точка, например DrawOverlay, после RenderFrame и перед Present. Название приведено как предложение, готового метода нет. При интеграции нужно корректно выбрать render target и состояния графики для UI.

Также нужна обработка захвата ввода: текстовое поле или панель не должны одновременно управлять камерой/игрой. Время интерфейса и пауза симуляции должны быть определены отдельно.

### Небольшие этапы реализации

1. Editor.exe с одной сценой и одной панелью.
2. Список объектов, выбор и редактирование transform.
3. Сохранение/загрузка данных сцены и явные фабрики игровых типов.
4. Play, сначала запускающий игровой exe отдельным процессом.
5. При необходимости — встроенная симуляция со своим жизненным циклом; позже DLL hot reload.

Чтобы создавать специфические игровые классы внутри редактора, нужен их код: простой следующий вариант — игровая статическая библиотека с явными фабриками, подключённая к игре и редактору. Сейчас игровые проекты целиком собираются в exe, поэтому произвольные классы игры редактор автоматически получить не сможет.

При последующем переносе управления из Game в BaseEngine должен остаться один владелец окна, устройства и цикла. Второй цикл поверх Game::Run создавать не нужно.

## 9. Ресурсы и ограничения проверки

Рядом с каждым игровым exe находятся EngineContent, GameContent и RequiredFiles.txt. Манифест проверяют и лаунчер, и прямая точка входа. ENGINE_CONTENT_ROOT / GAME_CONTENT_ROOT позволяют задать альтернативные корни. По умолчанию поиск не зависит от рабочей директории процесса.

Проверено после последнего переноса каталогов: Debug/Release собираются; EngineTests — 9/9 в каждой конфигурации; BasicExamples (обе сцены), Pong и SunGame проходят 30-кадровые запуски напрямую и через лаунчер, включая посторонний CWD и путь с пробелами. Game/Start.cmd открывает лаунчер. Эти проверки не подтверждают визуальную эквивалентность и правильность всех игровых правил.

Известные ограничения:

- Katamari требует отсутствующий в проверенном окружении vcpkg/Assimp. Её исходники прошли синтаксическую проверку, но полный запуск не проверен.
- cosy.jpg не предоставлена; сохраняется работа без соответствующих отражений.
- Материалы MTL Katamari требуют отдельного восстановления из исторических архивов и визуальной проверки.
- Копирование Content пока не удаляет устаревшие файлы в выходном каталоге.
- Горячая замена кода, перезагрузка ассетов, редактор и новый жизненный цикл BaseEngine не реализованы.

Рабочие планы и результаты: [028 — дальнейшие улучшения](../../Agent/Tasks/028-separation-followups.md), [029 — игры и лаунчер](../../Agent/Tasks/029-games-and-launcher.md), [030 — структура каталогов](../../Agent/Tasks/030-repository-layout.md). Исторические команды в задачах могут содержать прежние пути; актуальные команды приведены в этом документе и архитектуре папок.
