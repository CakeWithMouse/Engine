# Отрисовка массовой техники: инстансинг и LOD

Документ описывает, как движок рисует тысячи одинаковых единиц техники и что должны передать дизайнеры, чтобы заменить временные процедурные модели на настоящие.

Сцена для проверки и измерений — `Game/Battle`: по умолчанию 30000 единиц техники четырёх типов и три типа построек на одном поле. Компонент — `InstancedMeshComponent` (`Engine/Include/Engine/Components/SpecificComponents/InstancedMeshComponent.h`), материал — `Engine/Content/Shaders/InstancedMesh.hlsl`.

## 1. Как это работает

Одна единица техники — не отдельный объект сцены. В реестре движка регистрируется **один** компонент на тип техники, а каждая машина — это запись в массиве экземпляров.

За кадр компонент один раз:

1. отсекает экземпляры по пирамиде видимости камеры (сфера радиусом модели);
2. выбирает уровень детализации по расстоянию до камеры;
3. раскладывает экземпляры по корзинам LOD и загружает по одному GPU-буферу на уровень;
4. рисует по одному `DrawIndexedInstanced` на уровень.

Тени используют отдельный набор экземпляров: он не отсекается камерой, иначе техника за краем экрана перестала бы отбрасывать тень. У теней свой запас по дистанции и смещение LOD, обычно на уровень грубее.

Число draw call зависит от числа уровней детализации, а не от числа машин. В сцене `Battle` это 3–4 вызова на цветной проход и столько же на каждый каскад теней, независимо от того, 500 машин на поле или 20000.

## 2. Что требуется от моделей

Пока техника строится процедурно в `Game/Battle/Source/UnitMesh.h`. Чтобы подключить настоящие модели, нужны:

| Требование | Значение |
|---|---|
| Формат | Любой, который читает Assimp; проверяем на OBJ и FBX |
| Уровни детализации | 2–4 меша на единицу: `<Name>_LOD0`, `<Name>_LOD1`, `<Name>_LOD2`. Необязательно: движок достроит недостающие из LOD0 сам, см. раздел 2а |
| Полигоны | Ориентир: LOD0 ≈ 2–5 тыс. треугольников, LOD1 ≈ 1/4 от LOD0, LOD2 — силуэт в пределах сотни |
| Опорная точка | В центре машины по горизонтали, на уровне земли по вертикали |
| Ориентация | Нос машины смотрит в +Z, верх — +Y, левая рука — +X |
| Масштаб | 1 единица = 1 метр, корпус среднего танка ≈ 6 м в длину |
| Нормали | Должны быть в файле либо генерируются импортёром |
| UV | Один набор; текстура одна на машину |
| Материалы | Один материал на единицу техники. Несколько материалов на LOD0 пока не поддерживаются: это отдельная задача |
| Цвет команды | Задаётся движком на экземпляр и умножается на текстуру; в текстуре цвет стороны не запекать |

Ограничения текущей версии, о которых стоит знать заранее:

- масштаб экземпляра равномерный (нормали преобразуются той же матрицей);
- поворот экземпляра — только вокруг вертикальной оси, наклона по рельефу пока нет;
- анимации (башня, гусеницы) нет, модель рисуется цельной;
- карт нормалей нет, освещение использует нормали геометрии.

## 3. Как подключить модель в коде

```cpp
auto units = std::make_unique<InstancedMeshComponent>();
units->SetLod(0, LoadLod("Vehicle_LOD0"));     // MeshLodData: вершины и индексы
units->SetLod(1, LoadLod("Vehicle_LOD1"));
units->SetLod(2, LoadLod("Vehicle_LOD2"));
units->SetLodDistances({80.0f, 250.0f});       // границы переключения, в метрах
units->SetDrawDistance(2500.0f);               // дальше техника не рисуется
units->SetShadowDistance(900.0f);              // дальше не отбрасывает тень
units->SetShadowLodBias(1);                    // в тенях на уровень грубее
units->SetTexture(texturePath);                // одна текстура на тип техники

MeshInstance instance;
instance.Position = {x, 0.0f, z};
instance.Yaw = yaw;                            // радианы
instance.Color = teamColor;
units->AddInstance(instance);

game.RegisterComponent("Units", units.release(), shader, shader);
```

`MeshLodData` — это массив вершин (позиция, нормаль, UV) и 32-битных индексов. Импортёр моделей уже умеет читать такие данные (`FBXComponent`), отдельная функция загрузки LOD в компонент появится вместе с первыми реальными ассетами.

Движение и повороты задаются через `SetInstancePosition` и `SetInstanceYaw`; компонент сам пересоберёт GPU-поток в следующем кадре.

## 2а. Если уровней нет: движок построит их сам

`SetAutoLod({0.12f, 0.025f})` достраивает недостающие уровни из LOD0 — по одной доле треугольников на уровень. Дизайнеру достаточно одной модели. Уровень, который он всё-таки прислал, не перезаписывается: прислал LOD1 — останется его LOD1.

Внутри — meshoptimizer (`Engine/ThirdParty/meshoptimizer`, подмножество файлов, MIT). Обёртка `SimplifyMesh` в `Engine/Source/Render/MeshSimplifier.cpp` делает три вещи, без которых результат непригоден:

- **Сварка вершин по позиции.** Симплификатор схлопывает только те вершины, которые уже общие. В модели с раздельными нормалями общих нет вообще — каждое ребро шов, и упрощать нечего.
- **Нормали строятся заново, по углу складки.** Сварка теряет авторские нормали. Новые считаются по граням и усредняются внутри кластера: грани, расходящиеся больше чем на 50°, остаются раздельными. Коробка сохраняет рёбра, скруглённая панель остаётся гладкой.
- **Сторона «наружу» берётся из исходных нормалей, а не из обхода вершин.** Движок рисует с выключенным отсечением граней, поэтому ничто и никогда не заставляло экспортёр (и процедурные модели сцены) обходить все грани одинаково. Посчитанная по обходу нормаль переворачивается, если расходится с теми, что были в модели. Без этого половина техники светится изнутри и выглядит чёрной.

Самый дальний уровень дополнительно умеет «небрежное» упрощение, которое игнорирует топологию и всегда доходит до цели. Само по себе оно съедает тонкие детали целиком — у САУ исчезал ствол, и радиус модели терялся на 21%. Поэтому оно запускается несколько раз, от агрессивного к осторожному, и берётся первый результат, который удерживает силуэт (`MaxSilhouetteDrift`, по умолчанию 8%).

Отчёт печатается на каждый уровень:

```
auto-lod Tank LOD1: 2160 -> 456 triangles (target 259, error 0.00054, silhouette drift 0%)
auto-lod Artillery LOD2: 2160 -> 30 triangles (target 54, error 0.075, silhouette drift 2.4%, sloppy)
```

Чего ждать от автоматики честно: на процедурных машинах сцены (5–7 отдельных коробок — худший случай для упрощения с сохранением топологии) LOD1 останавливается на 456 треугольниках вместо заказанных 259, и кадр выходит на 20% тяжелее, чем с уровнями, сделанными руками (8.28 мс против 6.82 при 20000 единиц). На цельной модели запас больше. Построение всех уровней для четырёх типов стоит 0.3 с при загрузке.

Ключ сцены: `--auto-lod`.

## 2б. Проверка модели при импорте

`SetAssetValidation(true, "Tank")` сверяет LOD0 с контрактом и пишет отчёт:

```
asset-check Tank: 2160 triangles, 1470 vertices, size 3.50 x 2.20 x 6.20 m, pivot y 0.00, uv yes, ok
```

Что проверяется и почему именно это:

| Проверка | Как проявляется, если не поймать |
|---|---|
| Масштаб: самая длинная сторона в пределах 1–25 м | модель в сантиметрах — машина размером с квартал |
| Опорная точка на земле (`min.y` ≈ 0) | техника висит в воздухе или тонет |
| Опорная точка по центру в плане | экземпляр вращается вокруг точки вне себя и «ездит» по кругу |
| Нос вдоль +Z | вся армия едет боком |
| Верх вдоль +Y | модель лежит на боку |
| Бюджет треугольников | незаметно до первой сцены на 30000 единиц |
| Нормали: есть и единичной длины | чёрная техника |
| Вырожденные треугольники | стоят вершин, не рисуют ничего, мешают построению LOD |
| UV: есть и не улетает за пределы разумного | текстура размазана или её нет |

Деление на **problem** и **warning** по смыслу: problem — модель так работать не будет, warning — движок стерпит, но дизайнер обычно имел в виду не это.

Ключ сцены: `--validate`.

## 3а. Спрайты вместо геометрии на дальних дистанциях

`SetImpostorEnabled(true)` добавляет за мешевыми уровнями сгенерированный спрайтовый. При загрузке движок рендерит модель в атлас (по умолчанию 16 ракурсов × 4 наклона, 128 px на ячейку) в два слоя: цвет с маской и объектную нормаль. Дальние единицы рисуются квадами, которые сами выбирают ячейку по углу обзора; нормали поворачиваются по экземпляру, поэтому спрайты освещаются тем же солнцем и тенями и работают в deferred. Дизайнер для этого ничего не делает: источник — его же LOD0.

Три вещи в этом месте сделаны специально, и все три — про то, чтобы на плотном поле не появлялись полосы и кольца. Любой порог, завязанный на расстояние до камеры, на ровной земле превращается в окружность вокруг камеры: сверху она видна как кольцо, с низкой камеры — как линия поперёк поля.

- **Мипы атласа.** Спрайт занимает несколько пикселей, а ячейка — 128. Без мипов он точечно выбирает текселы, и какие именно — зависит от расстояния. Атлас строится с цепочкой мипов до ячейки в 16 текселов (ниже силуэт расплылся бы в одно среднее). Ячейки выровнены по степени двойки, поэтому ни один тексел мипа не попадает сразу в две ячейки; граница ячейки при выборке дополнительно поджимается на полтексела того мипа, который используется. Цвет в мипах усредняется вместе с прозрачным фоном, поэтому шейдер делит его обратно на покрытие.
- **Смешение по наклону.** Ряд наклона не округляется, а берётся дробным: шейдер читает две соседних строки атласа и смешивает их. Жёсткое переключение строки давало ступеньку яркости на окружности постоянного угла обзора.
- **Покрытие через дизеринг.** Маска не сравнивается с фиксированным порогом: пиксель остаётся с вероятностью своего покрытия (упорядоченный шаблон). Фиксированный порог съедает силуэт тем сильнее, чем мельче спрайт, и строй начинал просвечивать полосами.

Переход между уровнями плавный: в полосе вокруг порога оба уровня рисуются и смешиваются дизерингом (`SetLodFadeFraction`, по умолчанию 6% от порога). Уровни делят один шаблон дизеринга, а не проверяют его каждый сам по себе: тот, что проявляется, забирает ровно те пиксели, которые отдаёт уходящий. Иначе в середине полосы половина пикселей отбрасывалась бы дважды и переход светился бы. Тени от спрайтов не берутся — в теневом проходе всегда используется меш.

## 3б. Тени массовой сцены

Тени — самая дорогая часть такой сцены, поэтому они разделены на две части.

- **Техника**: каскады. Каждый каскад получает свой набор экземпляров: внутрь попадает то, что лежит в сфере каскада или находится над ней на пути от света. Детализация падает с номером каскада (`LOD + SetShadowLodBias + индекс каскада`). `SetShadowCascadeLimit(N)` ограничивает технику ближними каскадами, `SetShadowDistance` — дистанцией.
- **Граница дистанции теней размывается.** Обрезать тени на одной дистанции нельзя: это окружность вокруг камеры, и на плотном поле она видна как кольцо резко посветлевшей земли (в измерениях — скачок 13/255 на границе). Поэтому на последних `SetShadowDistance(d, fade)` (по умолчанию 30% дистанции) отбрасывающие тень экземпляры прореживаются: кто именно ещё отбрасывает, решает стабильный хеш экземпляра. Тени редеют постепенно, а не кончаются по линии, и хеш стабильный — иначе они бы мерцали между кадрами.
- **Местность**: запекание. `Game::SetStaticShadowArea(центр, половина стороны)` задаёт область, компоненты помечаются `SetStaticShadowCaster(true)`. Их тень рисуется один раз в карту, привязанную к миру, и переиспользуется: движение камеры её не инвалидирует, перезапекание происходит при смене направления солнца или области. В каскадах такие объекты не рисуются.

Освещённость пикселя — минимум из каскадной и запечённой видимости.

## 3в. Несколько типов моделей

Один компонент — один тип модели. В сцене `Battle` это четыре типа техники (танк, БТР, грузовик, САУ) и три типа построек (дом, башня, стена); каждый тип получает свои LOD, свой атлас спрайтов и свои инстанс-потоки. Техника распределяется между типами, так что в каждом ряду строя стоят разные машины.

Число draw call растёт линейно по числу типов, но времени это почти не стоит (20000 единиц, камера 400 м):

| Типов техники | draw calls | Кадр, мс (лёгкая модель) | Кадр, мс (реалистичная) |
|---|---|---|---|
| 1 | 10 | 5.56 | 17.95 |
| 2 | 14 | 6.10 | 18.09 |
| 4 | 22 | 6.25 | 18.30 |

То есть разнообразие моделей почти бесплатно: четыре типа вместо одного стоят около 0.7 мс при лёгкой геометрии и 0.35 мс при тяжёлой. Ограничение наступает не по типам, а по суммарной геометрии и теням.

## 3г. Сцена по умолчанию

`Battle.exe` без аргументов строит поле 1392×1392 м: 30000 единиц техники четырёх типов двумя армиями, 300 построек трёх типов, стратегическая камера на высоте с наклоном 55°. Вся техника движется каждый кадр, поэтому инстанс-потоки пересобираются и загружаются заново.

Строй намеренно не идеальная решётка: соседние ряды смещены на полшага, каждая машина довёрнута на несколько градусов, шаг 8 м при длине машины 6 м. На точной решётке одинаковые машины под одинаковым углом сливаются в сплошные полосы с просветами между ними, и издалека поле выглядит полосатым — это видно одинаково и на мешах, и на спрайтах, то есть дело в расстановке, а не в рендере. Плотность задаётся `--spacing N`.

| Сборка | Кадр, мс | FPS | draw calls | Нарисовано экземпляров |
|---|---|---|---|---|
| Release | 6.62 | 151 | 18 | 38 тыс. (с учётом трёх каскадов теней) |
| Debug | 25.12 | 40 | 18 | 41 тыс. |

Дистанцию и наклон камеры можно менять ключами `--camera N` и `--pitch N`, плотность строя — `--spacing N` (по умолчанию 8 м).

Для сравнения скриншотов есть `--lock-camera`: камера перестаёт слушать мышь и клавиатуру, и два запуска одной и той же сцены дают один и тот же кадр. Без него сравнивать кадры бессмысленно — орбитальная камера довернётся от любого движения мыши.

Машина: Windows 10, сборка Release x64, VSync выключен, окно 1000×500, камера над полем, техника движется каждый кадр. Запуск: `Battle.exe --units N --frames 300`.

|---|---|---|---|---|---|
| 2000 | deferred | вкл | 5.51 | 181 | 27 |
| 2000 | deferred | выкл | 3.58 | 280 | 19 |
| 2000 | forward | вкл | 5.73 | 174 | 26 |
| 8000 | deferred | вкл | 6.70 | 149 | 26 |
| 8000 | deferred | выкл | 3.06 | 326 | 18 |
| 20000 | deferred | вкл | 7.17 | 139 | 19 |
| 20000 | deferred | выкл | 3.54 | 283 | 11 |
| 20000 | forward | вкл | 6.23 | 161 | 18 |

Выводы из таблицы:

- число машин почти не влияет на число draw call и слабо влияет на время кадра: с 2000 до 20000 кадр вырос с 5.5 до 7.2 мс. Draw call больше на малых числах, потому что вблизи работают сразу несколько уровней детализации, а издалека вся техника уходит в спрайты;
- основная цена — тени: три каскада рисуют технику в радиусе 900 м, это примерно 3.6 мс из 7.2 мс при 20000 машин;
- отсечение по экземплярам убирает из цветного прохода то, что вне экрана (при 20000 машин — около 7000 за кадр в этом ракурсе).

Влияние спрайтов и теней, 20000 единиц, камера 400 м, модель реалистичной плотности (`--detail 4`, LOD0 35 тыс. треугольников):

| Состояние | Кадр, мс | FPS |
|---|---|---|
| Исходно: один теневой набор на все каскады, без спрайтов | 42.04 | 24 |
| + спрайты на дальних дистанциях | 34.14 | 29 |
| + отсечение и LOD по каскадам теней | 17.81 | 56 |

Вклад запекания отдельно виден на тяжёлой местности (5000 техники): 3000 построек — 8.32 мс против 9.20 мс, 8000 построек — 9.86 мс против 11.82 мс.

Проверка переключения уровней: `Battle.exe --units 2000 --camera N --frames 120` ставит камеру на заданное расстояние от центра поля и выводит, сколько экземпляров попало в каждый уровень.

| Камера, м | LOD0 | LOD1 | LOD2 | Отсечено | Кадр, мс | draw calls |
|---|---|---|---|---|---|---|
| 50 | 144 | 462 | 0 | 1394 | 7.54 | 13 |

Вблизи работают все три уровня и больше экземпляров уходит за край экрана; издалека вся техника рисуется силуэтами одним вызовом. Границы переключения задаются `SetLodDistances`, в сцене это 80 и 250 м.

Следующие кандидаты на оптимизацию, в порядке ожидаемой пользы: отсечение экземпляров отдельно для каждого каскада теней, более грубый LOD в тенях, уменьшение дистанции теней, затем перенос отбора на GPU. Выбирать по повторным замерам этой же сцены.

## 5. Проверка

```powershell
./Engine/build.ps1 -Target Battle -Configuration Release
./Game/build/x64/Release/Battle/Battle.exe --units 20000 --frames 300
```

Ключи сцены: `--units N`, `--types N`, `--spacing N`, `--camera N`, `--frames N`, `--detail N`, `--scenery N`, `--sprite-px N`, `--pitch N`, `--sun N`, `--shadow-distance N`, `--auto-lod`, `--validate`, `--dump-shadows`, `--dump-impostors`, `--no-shadows`, `--no-baked-shadows`, `--no-impostors`, `--forward`, `--static`, `--lod-debug`, `--lock-camera`, `--smoke`.

Диагностика полос и колец: `--lock-camera` для повторяемого кадра, `--no-impostors` чтобы понять, в спрайтах дело или нет, `--shadow-distance N` чтобы проверить, не граница ли теней, `--dump-impostors` чтобы посмотреть сам запечённый атлас (все мипы обоих слоёв ложатся рядом с exe в BMP). Клавиша **F6** включает раскраску по уровням детализации: зелёный — LOD0, жёлтый — LOD1, оранжевый — LOD2, фиолетовый — спрайт. Это самый быстрый способ проверить, что переключение уровней происходит там, где задумано.
