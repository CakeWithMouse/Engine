# Как дальше разрабатывать движок и игру

Обновление 032: добавлен [каркас одного EngineRuntime.exe с game/editor DLL](RUNTIME-QUICKSTART.md), запускаемый из лаунчера. Его жизненный цикл работает на заглушках, старые примеры и реальный рендер пока используют Game. Вариант отдельного Editor.exe заменён режимом editor общего host.


Актуальные пути сборки, структура Game и лаунчер: [архитектура папок](FOLDER-ARCHITECTURE.md).

Руководство по рабочей структуре на 2026-10-04. Команды сборки и запуска находятся в [README](../README.md), описание существующей архитектуры — в [Описание проекта.md](Описание%20проекта.md). Ниже явно разделены действующий код и предлагаемые следующие шаги.

Главный принцип: **Engine предоставляет общие возможности; игра определяет, как ими пользоваться; редактор помогает создавать и менять игровые данные.** Для учебного проекта сначала делаем небольшой работающий сценарий, затем обобщаем действительно повторяющуюся часть.

## Карта ответственности

| Что добавляем | Где разрабатываем |
|---|---|
| Окно, D3D11, главный цикл, рендер, базовые преобразования объектов | `Engine/Source`, публичный API — `Engine/Include/Engine` |
| Общие шейдеры, стандартные ресурсы рендера | `Engine/Content` |
| Сцену, правила боя, юнитов, отряды, команды, условия победы | `Game/SunGame/Source` |
| Модели солдат, карты, текстуры, настройки конкретной игры | `Game/SunGame/Content` |
| Панели редактора, выделение в редакторе, инспектор, сохранение редактируемой сцены | `Editor/EditorModule.vcxproj` → `Editor.dll`; пока заглушка |
| Проверки общих механизмов Engine | `Engine/tests` |

Сейчас существуют Editor.dll-заглушка и EngineRuntime.exe с двумя режимами. BaseEngine/BaseResources имеют работающий жизненный цикл заглушек. Настоящее окно, графика и сцена старых примеров пока находятся в историческом классе Game. `Game/Archive/1_Lab` не используется для новых основных систем.

## 1. Где делать редактор

Актуальный подробный контракт для внедрения — [раздел 8 документа передачи разработчикам](DEVELOPER-HANDOFF.md#8-внедрение-редактора-согласованный-контракт). Следовать ему вместо прежнего варианта отдельного Editor.exe.

```text
Лаунчер → EngineRuntime.exe --project Project.json --mode editor
             → инициализация Engine → загрузка Editor.dll → открытие проекта
```

Продолжать существующий `Editor/EditorModule.vcxproj`. Панели, инспектор и команды пользователя принадлежат Editor; окно, сцена, ресурсы, основной цикл и рендер — Engine. Editor не наследуется от Game/BaseEngine. Сначала перенести нужные реальные механизмы в общий runtime; не запускать второй цикл старого Game из Editor.dll.

Открытие проекта не требует наличия Game.dll. Сцена встроенных типов также может редактироваться без неё. Для игровых типов host позже подключает Game.dll через отдельный контракт регистрации типов, без запуска игровой сессии. Сейчас editor вообще не загружает Game.dll, а ABI v1 ещё не содержит регистрации типов. При расширении ABI необходимы версия, управление временем жизни фабрик/объектов и новые проверки.

Минимальный графический редактор: область просмотра, список объектов и изменение transform через ограниченный API Engine. Текущий контекст содержит только журнал, запрос выхода и строки проекта: API сцены/ввода/UI нужно добавить. Существующий overlay-callback пока пишет сообщение; полноценную отрисовку интерфейса следует выполнять после сцены и до единственного Present. Захват ввода панелью должен блокировать соответствующее управление камерой.

Сохранённая сцена — данные, а не снимок C++-объектов с указателями. Начать со встроенных типов, затем отдельно подключать фабрики игровых типов. Служебное обновление и отображение сцены продолжаются при выключенной игровой симуляции.

Старым играм можно добавить открытие оболочки редактора через описание проекта ещё до перевода на DLL. Это не покажет их текущую сцену автоматически: она строится внутри старого exe. Для неё нужен отдельный путь загрузки/построения без старта игры. Отключённая сейчас кнопка у старых записей — временное правило лаунчера, а не обязательная зависимость редактора от игрового бинарника.

Первый Play из редактора — сохранение данных и запуск того же EngineRuntime.exe в режиме game отдельным процессом. Встроенный Play с копией мира и hot reload — последующие задачи, сейчас не реализованы.

## 2. Где делать инициализацию и базовые ресурсы

Следующие разделы описывают сохранённый старый API примеров и источники механизмов для переноса. Для нового host порядок задают Engine/Runtime/Main.cpp и BaseEngine::Run; модуль игры/редактора не запускает подсистемы сам.

У старой SunGame последовательность задана в `Game/SunGame/Source/Main.cpp`:

```text
Определить EngineContent и GameContent
→ создать SunGame с конфигурацией
→ Initialize(): окно и механизмы Engine
→ BuildScene(gameContent): содержимое конкретной игры
→ StartGame(): общий цикл
→ уничтожение объектов и ресурсов
```

`Game::Initialize()` реализован в `Engine/Source/MainGame/BaseGameClass/Game.cpp`. Здесь развиваем общую инициализацию: устройство, swapchain, буферы, состояния рендера, общие механизмы шейдеров и другие необходимые каждой игре возможности. В конце вызывается виртуальный `AfterInitialize()`. У SunGame построение сцены сейчас явно вызывается из `Main.cpp` после Initialize; не нужно дополнительно вызывать его из AfterInitialize, иначе сцена будет создана дважды.

В конструкторе игровой программы удобно сохранять настройки и создавать обычные CPU-данные. GPU-ресурсы и регистрация компонентов требуют готового устройства, поэтому выполняются после успешного Initialize. Неуспешную инициализацию нельзя продолжать вызовом StartGame.

Разделение на примере света:

- Engine умеет отрисовывать направленный свет и тени, создаёт нужные GPU-ресурсы.
- Игра задаёт направление солнца, цвет, интенсивность и желаемые параметры теней через API.
- Editor показывает поля для редактирования этих игровых значений.

Разделение файлов ресурсов:

| Ресурс | Исходный каталог | Рядом с собранным exe |
|---|---|---|
| Общие HLSL движка | `Engine/Content/Shaders` | `EngineContent/Shaders` |
| Модель солдата, карта, текстура игры | `Game/SunGame/Content` | `GameContent` |
| Будущие иконки и оформление редактора | `Editor/Content` | Предлагаемый `EditorContent` |

Стандартная белая текстура или материал ошибки, когда они понадобятся, относятся к Engine. Конкретная текстура земли на карте относится к игре. Загрузчик текстур может быть общим, но от этого все текстуры не становятся ресурсами движка.

`EnginePaths::SetContentRoot(...)` задаётся до инициализации; `EnginePaths::Shader(...)` формирует путь к шейдеру ядра. Игровые пути строим от переданного `gameContent`, например `gameContent / "Textures" / "ground.png"`. Не используем рабочую директорию процесса и не зашиваем `O:\Engine` в код.

Общего менеджера ресурсов с идентификаторами, подсчётом пользователей и горячим обновлением сейчас нет. Добавлять его стоит начиная с конкретной проблемы: например, одна текстура загружается повторно для сотни объектов. Владельца кэша и момент освобождения ресурсов определяем явно; не создаём большой глобальный `BaseResources`, содержащий и устройство, и сцены, и игровые модели.

Изменение файла текстуры не означает её автоматическую перезагрузку в GPU. Сегодня надёжный путь — обновить ресурсы сборкой и перезапустить приложение. Перезагрузка ресурса во время работы и перекомпиляция игрового C++ — разные будущие возможности.

## 3. Как делать свою игру

Пример ниже иллюстрирует старый путь через Game и не является предписанием создавать новые exe вместо модулей. Для нового модульного пути ориентир — RuntimeExample; реальные сцены в него ещё предстоит перенести.

В старом API для первого стратегического прототипа создаём отдельный проект `Game/BattleGame` по образцу BasicExamples. SunGame сохраняем как отдельный пример. Новую сцену описываем классом `BattleGame : public Game`, а её Main.cpp отвечает за запуск. Шаги подключения проекта и лаунчера описаны в FOLDER-ARCHITECTURE.md.

Практическая последовательность:

1. Создать `BattleGame.h/.cpp` и небольшой `BattleGameConfig`: размер поля, начальное число юнитов, скорость движения. Это игровые настройки.
2. После Initialize построить поле, камеру и небольшую группу видимых объектов. Не копировать из SunGame всю солнечную систему ради доступа к циклу.
3. Добавить выделение одного объекта, затем группы, затем одну команду перемещения.
4. Держать состояние боя и обработку команд в игровых классах. Например, `BattleState` содержит отряды, а `BattleGame` связывает их с вводом и отображением.
5. Добавлять модели и текстуры через GameContent. Для FBXComponent предварительно включить и проверить опциональную сборку Assimp, как описано в README.
6. Проверить запуск, ошибки отсутствующих ресурсов и завершение приложения. После этого увеличивать число объектов и измерять стоимость обновления и рендера.

Новый `.cpp` нужно добавить в проект своей игры (например, `BattleGame.vcxproj`) как `ClCompile`; одного появления файла на диске недостаточно. В Visual Studio это делает добавление существующего файла в проект. Заголовок обычно добавляют как `ClInclude` для отображения в IDE; компилятор получает его содержимое через `#include`.

Если нужен отдельный игровой продукт, позднее создаём соседний проект приложения со ссылкой ProjectReference на Engine, его публичными include-путями, общими настройками сборки и собственным копированием Content. Добавляем проект в решение; если хотим выбирать его через `build.ps1 -Target`, расширяем список целей скрипта. Исходники Engine в игровой проект повторно не включаем.

Сегодня игра статически линкуется с Engine.lib. Изменение игрового `.cpp` требует сборки соответствующего объекта и перелинковки exe; неизменившееся ядро пересобирать не требуется. Изменение публичного заголовка Engine может закономерно вызвать перекомпиляцию использующих его файлов. Запущенное приложение не получит новый код автоматически.

## 4. Где развивать основной тик и поведение

Есть два разных уровня работы:

| Уровень | Место | Примеры |
|---|---|---|
| Организация кадра | `Game` в Engine | Время, сообщения окна, resize, порядок обновления, проходы рендера, Present |
| Правила конкретной игры | Производный игровой класс и игровые системы | Команды отрядам, движение по приказу, бой, победа |
| Поведение отдельного объекта | Переопределение `GameComponent::Tick(float)` | Движение небольшого тестового объекта, его локальная логика |

Основные методы для чтения в `Engine/Source/MainGame/BaseGameClass/Game.cpp`: `Run`, `UpdateFrame`, `TickComponents`, `RenderFrame`, `EndFrame`. Текущий порядок упрощённо:

```text
Сообщения окна и resize
→ UpdateFrame
    → обработка горячих клавиш
    → игровой PreUpdate(deltaTime)
    → обновление камеры
    → Tick компонентов
    → подготовка света, теней и констант
    → Update компонентов (преобразования и данные рендера)
→ RenderFrame и Present
→ завершение кадра ввода
```

`PreUpdate` — существующая виртуальная точка для общего игрового обновления перед камерой и компонентами. В SunGame она сейчас обслуживает счётчик `--smoke`; при добавлении логики нужно сохранить этот режим проверки. `GameComponent::Update()` — служебная подготовка данных, не виртуальный игровой тик. Уже зарегистрированный компонент движок вызывает сам: дополнительно вызывать его Tick из игры не надо.

Для новой игры задайте осмысленный масштаб времени. Сейчас по историческим причинам `SimulationTimeScale` равен **7.8**; SunGame сохранена с прежними скоростями. В новом BattleGame можно вызвать `SetSimulationTimeScale(1.0f)`, чтобы скорость «5 единиц в секунду» соответствовала обычному реальному времени. Движение считается как `position += velocity * deltaTime`, а не фиксированное смещение на каждый кадр.

**Пауза пока имеет ограниченную семантику.** При удержании Space движок передаёт обычным компонентам нулевой deltaTime, но продолжает вызывать Tick. Skybox получает обычный deltaTime; PreUpdate, камера и накопление TotalTime также продолжаются. Поэтому игровая логика в PreUpdate не ставится этим на паузу, а логика в Tick, не учитывающая время, всё равно выполняется. Перед полноценной стратегической симуляцией следует отдельно определить общую паузу игры и время интерфейса. Нельзя считать нынешний Space готовой паузой всего игрового мира.

Регистрация и удаление компонентов меняют контейнер, который движок обходит. Не делайте их непосредственно из Tick/Render обходящегося объекта. Простой будущий механизм — очередь команд создания/удаления, применяемая в известной точке между обходами. До её появления создание сцены до StartGame остаётся понятным безопасным вариантом. Порядок обхода компонентов не используйте как порядок игровых правил: зависимые действия организуйте явно в игровой системе.

Для стратегии со временем может понадобиться фиксированный шаг симуляции: команды и движение обновляются с заданным шагом, а картинка рисуется с доступной частотой. Планирование таких шагов относится к Engine; правила шага — к игре. Сейчас отдельного фиксированного цикла нет. Сначала проверяем простой сценарий на разных FPS, затем добавляем его с ограничением числа догоняющих шагов, если это нужно задаче.

## 5. Как добавлять компоненты и другие игровые классы

Сначала решаем, кому принадлежит новая возможность. `SoldierComponent`, `Squad`, `BattleRules` относятся к игре. Общая геометрия, преобразования и механизмы рендера — к Engine. Само по себе наследование от GameComponent не делает класс движковым.

GameComponent сегодня совмещает несколько обязанностей объекта сцены. Готовой системы «Actor с произвольным набором независимых компонентов», как в UE, здесь нет. Обычный класс состояния отряда вполне может не наследоваться от GameComponent. Для небольшой сцены удобно связать такие данные с зарегистрированными визуальными объектами.

Пример небольшого игрового компонента — файл `Game/BattleGame/Source/Components/MovingCubeComponent.h` (пример для добавления, проект и файл пока не созданы):

```cpp
#pragma once
#include <Engine/Components/SpecificComponents/CubeComponent.h>

class MovingCubeComponent : public CubeComponent
{
public:
    float Speed = 2.0f;

    void Tick(float dt) override
    {
        CubeComponent::Tick(dt);
        SetPosition(GetLocalPosition() + glm::vec3(Speed * dt, 0.0f, 0.0f));
    }
};
```

Это движение вдоль локальной X; при наличии родителя направление в мире зависит от его преобразования. Пользуйтесь SetPosition/SetRotation/SetScale: они отмечают необходимость пересчитать преобразования.

Фрагмент построения сцены **после успешного Initialize**; требуются заголовок компонента, `<Engine/Resources/Paths.h>`, `<memory>` и `<stdexcept>`:

```cpp
auto unit = std::make_unique<MovingCubeComponent>();
unit->InitCube();
unit->SetPosition(glm::vec3(0.0f, 0.0f, 0.0f));

const auto shader = EnginePaths::Shader("BaseShader.hlsl").generic_u8string();
const auto result = RegisterComponent("Unit_01", unit.get(), shader, shader);
if (result != RegisterResult::Ok)
    throw std::runtime_error("Cannot register Unit_01");

unit.release(); // После Ok объектом владеет Game.
```

Это иллюстрация API, не добавленная и не отдельно собранная сцена. Для видимой картинки также нужны подходящие настройки камеры и рендера. У RegisterComponent порядок аргументов после объекта: **pixel shader, затем vertex shader**. У SetShaderNames порядок обратный — vertex, затем pixel; не смешивайте эти два вызова.

Имя зарегистрированного объекта должно быть уникальным. При отказе регистрации владение остаётся у вызывающего, поэтому unique_ptr освобождает объект. После успешной передачи нельзя удалять объект самостоятельно. `FindComponent` возвращает невладеющий указатель, который станет недействительным после `UnregisterComponent` или уничтожения игры. Для долговременных игровых ссылок позднее стоит ввести проверяемые идентификаторы; сейчас нужно явно следить за временем жизни.

Движку не требуется знать имя C++-класса MovingCubeComponent: виртуальный Tick вызывает игровую реализацию через базовый указатель. Но для появления типа в меню редактора или загрузки по имени из файла потребуется отдельная явная регистрация фабрики типа. **Регистрация экземпляра в текущей сцене и регистрация типа для будущего редактора — разные операции.**

Для тысяч солдат не обязательно сразу делать тысячи сложных наследников с собственными ресурсами. Начните с небольшого количества, затем измерьте. При необходимости отряд хранит массив простых состояний и обновляет их вместе, а отображение использует общую геометрию и инстансинг. Существующий инстансинг не следует считать готовой системой игровых юнитов: отдельно проверяем, как обновляются состояния экземпляров. Решение об ECS принимаем по выявленным ограничениям.

## Порядок следующих небольших работ

1. Разобрать ошибки регистрации и неактивные настройки SunGame — 028-B.
2. Сделать BattleGame с небольшой группой, выделением и одной командой — 028-D.
3. Уточнить паузу, порядок симуляции и безопасное создание/удаление — 028-G.
4. Добавить первый Editor со списком объектов и изменением transform — 028-F.
5. Измерить CPU/GPU на растущем количестве юнитов и выбрать одну подтверждённую оптимизацию.
