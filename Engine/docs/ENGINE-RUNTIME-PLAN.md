## 1. Как всё устроено сейчас

### Коротко

По папкам и сборке движок уже отделён от игр. По управлению приложением разделение ещё не закончено: класс `Game`, находящийся внутри Engine, фактически и является движком. Конкретная игра наследуется от него и получает доступ к его внутренностям.

```text
EngineLauncher.exe
  └─ запускает выбранный игровой exe отдельным процессом
       └─ main конкретной игры
            ├─ готовит пути ресурсов
            ├─ создаёт SunGame / PongGame / другую игру
            ├─ вызывает Game::Initialize()
            ├─ строит игровую сцену
            └─ вызывает Game::StartGame()
                 └─ Game::Run(): общий цикл обновления и рендера
```

`Engine.lib` — статическая библиотека. Она не запускается сама: её код включается в игровой exe при линковке. `EngineLauncher.exe` — список приложений и вызов `CreateProcessW`, а не работающий внутри него движок.

### Что сделали последние изменения

- Общий код, шейдеры, зависимости и сборка вынесены в `Engine`.
- Игры находятся в `Game/BasicExamples`, `Game/Pong`, `Game/SunGame`, `Game/Katamari`; старые лабораторные сохранены в архиве.
- Публичные заголовки выделены в `Engine/Include/Engine`, реализации — в `Engine/Source`.
- Разделены `EngineContent` и `GameContent`; общий запуск примеров готовит пути до построения сцены.
- Добавлены `BaseEngine`, `BaseResources`, `BaseGameConfig`, но новый жизненный цикл ещё не подключён.
- В задаче [031](../../Agent/Tasks/031-engine-runtime.md) уже зафиксировано направление переноса runtime. План ниже уточняет его границы и последовательность.

### Кто чем владеет

| Часть | Текущее место и ответственность |
| --- | --- |
| Запуск приложения | `Game/<Name>/Source/Main.cpp`: порядок подготовки, инициализации, построения сцены и старта |
| Окно, ввод, камера | Поля `Game`: `DisplayPtr`, `InputDevicePtr`, `FirstPlayer` |
| Direct3D | Тот же `Game`: device, context, swap chain, буферы, состояния и кэши |
| Сцена | `Game::Components` хранит `unique_ptr<GameComponent>`; отдельный список наблюдает за источниками света |
| Основной цикл | `Game::Run`, `UpdateFrame`, `RenderFrame`, `EndFrame` |
| Правила игры | Наследники `Game` и игровые компоненты |
| Освобождение ядра | `Game::DestroyResources`, вызываемый в том числе деструктором |

Это уже единая реализация ядра: каждый игровой проект не содержит свою копию Direct3D-цикла. Проблема в том, что ядро одновременно служит базовым классом игры с очень широким доступом.

### Как проходит инициализация

На примере `SunGame/Source/Main.cpp`:

1. `ExampleStartup::PrepareContent()` проверяет размещение ресурсов и задаёт `EnginePaths::SetContentRoot`.
2. Создаётся `SunGame` с игровой конфигурацией.
3. `Game::Initialize()` создаёт окно, Player, ввод, device/swap chain, back/depth buffers, базовые шейдеры, layouts и render states.
4. После установки `bInitialized` вызывается виртуальный `AfterInitialize()`.
5. Внешний `main` отдельно вызывает `BuildScene(content)`.
6. Затем вызывается `StartGame()`.

Встроенные проверки ошибок и очистка при отказах уже есть. Однако обязанность соблюсти весь сценарий лежит на коде запуска игры. Единого обязательного вызова загрузки игровой сцены внутри runtime нет.

`BaseEngine` пока не участвует в этом сценарии: его `Initialize`, `StartUp`, `Play`, `IsPlaying`, `Stop` объявлены, но не реализованы; `Base.cpp` содержит только include. У `BaseResources` не реализованы `Initialize` и `DeInitialize`; сейчас это в основном набор имён/путей шейдеров, цветов и вспомогательных функций. Пути в его полях вычисляются при конструировании объекта.

`BaseGameConfig` содержит параметры рендера, солнца и теней, но не управляет стартом. `SunGameConfig` существует отдельно с похожими полями. Наличие этих классов в библиотеке ещё не создаёт новый порядок запуска.

### Что происходит каждый кадр

Текущий `Game::Run()` выполняет:

```text
Сообщения Windows → отложенный resize → проверка свёрнутого окна
  → расчёт времени кадра
  → UpdateFrame
      → обработка общих горячих клавиш
      → PreUpdate(dt) игры
      → обновление камеры
      → TickComponents(dt)
      → подготовка теней и общих данных кадра
      → Update() каждого зарегистрированного компонента
  → RenderFrame
      → Forward / Deferred / Custom
  → Present
  → завершение кадра ввода и статистика
```

Здесь важно различать два метода компонентов:

- `Tick(float)` — виртуальное поведение объекта, например движение мяча.
- `Update()` — невиртуальная подготовка transform/констант объекта и данных его экземпляров для рендера.

То есть обязательный обход `Update()` уже находится в ядре. Но `TickComponents()` виртуален, а `Draw()`, `DrawForward()`, `DrawDeffered()` тоже доступны для переопределения. Поэтому игра способна заменить существенные части кадра. Инстансы дополнительно обслуживаются своими владельцами; при переносе нельзя начать обновлять их второй раз как обычные объекты.

### Где именно нарушена желаемая граница

1. **Наследование от всего runtime.** `SunGame : Game`, `OrderedSceneGame : Game` и другие наследники получают `protected`-доступ к устройству, контексту, реестру компонентов и служебным методам, включая очистку.
2. **Замена обхода объектов.** `PongGame::TickComponents()` самостоятельно тикает стены/ракетки, затем проверяет столкновения мяча и тикает его. Игра определяет и правила, и сам обход.
3. **Замена рендера.** `OrderedSceneGame::Draw()` и `PongGame::Draw()` вызывают `BeginMainPass(false)` и сами отправляют компоненты на рисование через `Context`. Для них важны порядок и отключённый depth test — это поведение потребуется сохранить.
4. **Публичный доступ к графике.** `GetDevice()`, `GetContext()`, шейдеры и изменяемая статистика доступны наружу. Закрыть только поля недостаточно.
5. **Обход через компоненты.** `GameComponent::GetGame()/SetGame()` и `GamePtr` связывают компонент со всем runtime. Публичный интерфейс компонента содержит `CreateBuffers`, `Render`, `RenderShadow`, `DispatchCompute` с Direct3D-типами.
6. **Связь со своей игрой через ядро.** В Pong `Wall.cpp` приводит `GamePtr` к `PongGame*`, чтобы начислить очки. После разделения это должен быть отдельный игровой callback/сервис счёта, а не приведение runtime к игре.
7. **Глобальная настройка ресурсов.** `EnginePaths::SetContentRoot()` доступен игре и меняет общее состояние; `BaseResources` сохраняет вычисленные пути. Нужен один владелец настройки путей и определённый момент её фиксации.

## 2. Какая архитектура соответствует цели

Предлагаю композицию: **Engine содержит игровую сессию и вызывает игру через небольшой интерфейс**. Игра больше не наследуется от владельца окна и Direct3D.

```text
EngineHost — общая точка входа
  └─ BaseEngine / EngineRuntime — владелец жизненного цикла
       ├─ окно и ввод
       ├─ ресурсы и Renderer
       ├─ Scene: владение объектами и их обновление
       └─ игровая сессия: IGame
            └─ GameContext: только разрешённые операции
```

Имена предложенные, а не существующие классы. Можно сохранить имя `BaseEngine`, но он не должен становиться новой базой для наследования игр. Для закрытого владельца подходит `final` с приватной реализацией; внутренние заголовки следует убрать из публичного SDK.

### Что получает разработчик игры

| Разрешённый механизм | Что остаётся внутри Engine |
| --- | --- |
| Создать/удалить объект, поменять transform, запросить объекты сцены | Хранение объектов, момент применения изменений, обход и служебное обновление |
| Написать поведение компонента | Когда и сколько раз runtime вызовет его callback |
| Настроить камеру, свет, материал, render layer | Проходы рендера, ресурсы GPU, clear, resize, Present |
| Читать состояние ввода, назначить действия | Сбор событий платформы, сброс состояния, маршрутизация ввода |
| Запросить материал/текстуру по идентификатору | Загрузка, кэширование, базовые ресурсы, освобождение |
| Запросить паузу, выход, смену сцены | Переход состояния и безопасный момент выполнения |

`GameContext` не должен выдавать `EngineRuntime*`, изменяемый реестр, `ID3D11DeviceContext*` или сервис с методом `Shutdown()`. Иначе старый доступ сохранится через другую дверь.

Игра реализует небольшой контракт, например `OnStart(GameContext&)`, `OnUpdate(GameContext&, dt)` и `OnStop(GameContext&)`. Для объектов — отдельные callbacks поведения. Эти методы не заменяют обязательные стадии кадра, а вызываются внутри них.

### Обязательный порядок запуска

```text
Прочитать и проверить настройки запуска
→ определить EngineContent и GameContent
→ создать обязательные подсистемы и базовые ресурсы Engine
→ создать игровую сессию через фабрику
→ вызвать OnStart: загрузка контента и создание сцены
→ начать единственный цикл Engine
→ остановить callbacks игры
→ OnStop и освобождение сессии/сцены
→ освободить ресурсы, графику, ввод и окно
```

Фабрика позволяет даже конструировать игровой объект после готовности ядра. До этого host может читать декларативное описание проекта; исполнять игровую инициализацию для чтения настроек не требуется.

Обязательные ресурсы готовы до `OnStart`. Необязательные ресурсы можно создавать лениво: существующие G-buffer и тени не обязательно загружать для любой игры заранее. Порядком инициализации и обработкой ошибки всё равно управляет Engine.

### Что означает «отдельно запускается Engine»

Здесь два уровня, и полезно реализовать их по очереди.

**Уровень 1 — Engine всегда управляет запуском.** Общий host собирается с выбранной игрой в один exe. Игровой проект предоставляет фабрику/описание; точка входа, инициализация и цикл принадлежат Engine. `Engine.lib` остаётся статической. Правки игры требуют перелинковки exe, но не компиляции неизменённых исходников движка. Имя exe не определяет архитектуру.

**Уровень 2 — один самостоятельный `EngineRuntime.exe` для разных игр.** Host читает описание проекта и загружает игровой модуль, например `SunGame.dll`. Это реализует буквальный запуск одного движка поверх разных игр без перелинковки host при изменении игрового модуля. Потребуются версия интерфейса модуля, фабрика и функция уничтожения, согласованные настройки компилятора/CRT, обработка несовместимости и правила времени жизни callbacks. Объекты, подписки и функции из DLL должны исчезнуть до её выгрузки.

Для второго уровня DLL работает в том же процессе. Отдельный процесс Game с межпроцессным обменом для этой задачи излишен. Hot reload также отдельная задача: для первого варианта DLL достаточно перезапуска приложения.

## 3. План переделки

### Шаг 1. Зафиксировать контракт и ответственность

Детализировать задачу 031: Engine владеет кадром, сцена — объектами, игра — правилами и своими данными. Определить состояния `Starting → Ready → Playing → Stopping → Stopped`, выход при ошибке и поведение повторных вызовов.

Для первой версии достаточно одной игровой сессии на экземпляр runtime. Повторный запуск можно поддержать созданием нового runtime после полного уничтожения предыдущего. Повторный `Run` на том же объекте должен явно отклоняться, пока восстановление состояния не реализовано.

**Готово:** записано, кто вызывает каждый этап и что происходит при ошибке ядра, ошибке `OnStart`, запросе выхода и штатном завершении. `OnStop` вызывается только для успешно запущенной сессии; частично созданная сцена и объект игры освобождаются и при провале `OnStart`.

### Шаг 2. Создать одного настоящего владельца runtime

Перенести ответственность существующего `Game` в `BaseEngine`/`EngineRuntime`. Публичной точкой для host сделать один `Run(LaunchOptions, GameFactory)`. Инициализация, главный цикл и очистка — приватные невиртуальные операции. `GameContext` не предоставляет `Run`.

Не реализовывать параллельно весь набор `Initialize/StartUp/Play/Stop` только потому, что объявления уже существуют: сначала определить необходимость и различие каждого метода. Особенно не создавать второй цикл внутри нового `BaseEngine` поверх старого цикла `Game`.

На переходный период старые приложения могут оставаться на прежнем API, но новый путь должен использовать ту же реализацию ядра через внутренний адаптер. Два самостоятельных владельца device/сцены и две расходящиеся копии рендера недопустимы.

**Готово:** пустая игровая сессия автоматически запускается после ядра, показывает пустую сцену и корректно завершается. Отказ ядра не вызывает фабрику и `OnStart` игры.

### Шаг 3. Ввести IGame и ограниченный GameContext

Разделить `Engine/Include/Engine` на действительно публичные контракты и внутреннюю реализацию в `Engine/Source` либо отдельном непубличном каталоге. Убрать из игрового API window procedure, управление device, буферами, проходами и освобождением ресурсов. При необходимости спрятать реализацию за `Impl`.

Разделить настройки: `LaunchOptions` — окно/режим рендера/разрешённые параметры запуска; параметры света и сцены — через API сцены; количество планет, скорости, очки — в конфигурациях игр. `SunDistanceMult` и подобные настройки конкретного примера не должны определять ядро.

`BaseResources` превратить во внутреннего владельца действительно общих ресурсов либо разделить на внутренний менеджер и публичные идентификаторы встроенных материалов. Игра не передаёт движку готовый `BaseResources` и не вызывает его Initialize/DeInitialize.

**Готово:** минимальная игра собирается только с SDK и разрешёнными зависимостями; через доступные ей объекты нельзя получить graphics context или вызвать очистку ядра.

### Шаг 4. Закрыть обход через GameComponent

Разделить игровое поведение и внутреннюю графическую реализацию компонента. На первом этапе достаточно небольшого интерфейса поведения и готовых компонентов сцены; полный ECS не нужен.

Игре доступны transform, свойства материала и callback поведения. Создание GPU-буферов, подготовка render data, `RenderShadow`, `DispatchCompute` и владение графическими объектами находятся во внутренних компонентах/Renderer. Простая замена `GamePtr` на `EngineRuntime*` не решает задачу.

`SetGame` и назначение владельца должны стать внутренними. Вместо `GetGame()` поведение получает ограниченный контекст. В Pong начисление очков из `Wall.cpp` перевести на игровой callback или ссылку на сервис счёта с ясным временем жизни. Katamari и Rocket используют интерфейсы ввода/камеры.

**Готово:** игровой компонент может двигать объект и реагировать на ввод, но не может через базовый компонент получить D3D11 или подменить владельца регистрации.

### Шаг 5. Зафиксировать обновление сцены и безопасные изменения

Engine всегда вызывает игровые callbacks, затем нужные стадии обновления сцены и подготовку данных рендера в определённом порядке. Внешнего переопределения `TickComponents()` больше нет. Служебный нынешний `Update()` остаётся внутренним, а игровое поведение можно пока оставить с именем `Tick`.

Для Pong сохранить последовательность «стены/ракетки → столкновения мяча → движение мяча» через небольшие группы обновления и игровой callback в нужной фазе. Engine обходит зарегистрированные поведения; игра задаёт участие в разрешённой группе. Не вводить автоматический Tick мяча одновременно с его ручным вызовом из игровой логики.

Создание/удаление из callbacks ставить в очередь и применять между обходами. Зафиксировать правило: добавленные во время обновления объекты начинают тикать со следующего кадра; удаляемые помечаются сразу и пропускают последующие callbacks, освобождаются в безопасной точке. Вместо долгоживущих сырых указателей для поиска использовать проверяемые handles.

Пауза должна быть настройкой симуляции, а назначение Space — политикой примера/привязкой ввода. Сейчас PreUpdate и камера продолжают работу при паузе базовых компонентов; изменение этого поведения следует проверять отдельно. Исторический масштаб времени 7.8 сохранить при миграции примеров, нормализацию скоростей вынести в отдельную правку.

**Готово:** для каждого активного поведения ровно один вызов на положенную фазу/шаг, служебное обновление не зависит от добросовестности игры; создание и удаление из callback не нарушают обход.

### Шаг 6. Оставить рендер сцены у Engine

Перенести проходы в закрытый Renderer и убрать возможность переопределить основной `Draw*`. Для BasicExamples и Pong предоставить режим рисования по слоям/порядку с отключённым depth test и настройку цвета очистки. Для SunGame сохранить Forward/Deferred и материалы как поддерживаемые настройки.

Если позже понадобится пользовательский проход, вводить отдельный ограниченный интерфейс расширения с определённым местом в кадре. Доступ к raw D3D-контексту означает более доверенный уровень плагинов и не должен быть частью обычного игрового SDK.

**Готово:** очистку, тени, основную сцену и Present вызывает только Engine; обе простые сцены и Pong сохраняют порядок изображения без собственных `Draw()`.

### Шаг 7. Перевести игры и запуск

Сначала перенести BasicExamples, как намечено в 031: обе сцены проверят замену Custom-рисования. Затем Pong проверит порядок симуляции и игровые связи; SunGame — ресурсы, материалы, свет, частицы и инстансы. Katamari переносить с учётом её зависимости от Assimp и проверять на доступной конфигурации.

Общую подготовку ресурсов из `Game/Common/ExampleStartup.h` перенести в host/runtime. Проверку игровых файлов оставить по декларации конкретного проекта. Установку EngineContent выполнять один раз до создания ресурсов; разработчик задаёт разрешённые пути через launch options, а не меняет глобальный корень в процессе игры.

Ограничение `--smoke` перенести в host как лимит кадров: игра не должна наследоваться от `SmokeGame` или вызывать Win32 `PostQuitMessage` ради тестового запуска.

После переноса убрать старое публичное наследование и старые пути инициализации. Обновить `.vcxproj`, deployment, тестовые скрипты, launcher и документацию. Если нужен именно один неизменяемый exe, следующим отдельным шагом добавить загрузку Game DLL и перевести каталог launcher на описания проектов/модулей.

**Готово:** добавление игры требует только игрового модуля/фабрики, данных и настроек проекта; исходники ядра и его порядок запуска не меняются.

### Шаг 8. Проверить архитектурные гарантии

Нужны проверки поведения, а не только успешная сборка:

- До готовности обязательных подсистем нет вызовов игры; при отказе старта освобождаются уже созданные ресурсы.
- Трасса одного кадра подтверждает порядок callbacks, отсутствие повторного Tick и единственный Present.
- Создание/удаление объекта из callback безопасно; после остановки callbacks и подписки не продолжают работу.
- Тестовая игра, собранная только против SDK, не может получить device/context, вызвать внутреннее обновление или подменить основной рендер. Недопустимые обращения должны не компилироваться.
- Последовательное создание, запуск и уничтожение runtime не оставляет ресурсы предыдущего запуска.
- Существующие EngineTests и smoke-прогоны проходят в Debug/Release; визуально сохраняются обе сцены BasicExamples, Pong и SunGame, отдельно проверяется Katamari с Assimp.
- Resize, сворачивание, потеря фокуса, закрытие окна и ошибки обязательных ресурсов остаются рабочими. Smoke на 30 кадров не заменяет эти проверки.

Эти проверки предстоит добавить/адаптировать во время реализации. Результаты из старых документов не подтверждают новый runtime.

## 4. Правильно ли само желание

**Да. Для этого проекта разумно, чтобы Engine определял жизненный цикл, а Game подключал правила через предоставленные механизмы.** Так новая игра не обязана помнить, когда создавать буферы, обновлять трансформации и вызывать Present. И будущий редактор сможет пользоваться тем же runtime.

Уточнить стоит слово «неизменяемый». Хорошая цель: **разработка игры не требует правок ядра и не позволяет подменять его обязательные стадии через обычный API**. Сам движок всё равно будет развиваться: новые механизмы, исправления и версии SDK неизбежны. Для игровой команды можно поставлять собранную библиотеку/host, публичные заголовки и ресурсы без исходников внутренних подсистем.

`private`, `final` и закрытые заголовки обеспечивают архитектурную границу, но не изоляцию произвольного нативного C++-кода в одном процессе. Это не мешает выбранной цели, если речь об обычной разработке игр. Для исполнения недоверенного кода понадобилась бы другая модель, например sandbox скриптов.

Не стоит одновременно переписывать рендер, вводить ECS, редактор, hot reload и универсальную систему модулей. Сначала один владелец жизненного цикла, небольшой игровой интерфейс, закрытый доступ к компонентам и доказанная миграция примеров. Самостоятельный host с DLL строится на этой границе, а не заменяет её.

Самый полезный первый результат: **пустая игра и обе сцены BasicExamples запускаются через обязательный Engine runtime, не наследуются от него и не имеют доступа к Direct3D; при этом весь старый рендер используется из одной реализации.**
