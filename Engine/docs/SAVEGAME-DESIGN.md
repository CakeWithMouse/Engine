## Задача и границы

Игрок сохраняет партию, закрывает игру, затем продолжает с теми же деньгами, домами и таймерами. Сохранение не должно изменять исходную сцену редактора. Повреждённый файл, несовместимая версия или ошибка подготовки нового мира не должны разрушать текущую игру.

Первая версия: локальные именованные слоты, один активный игровой мир, явный набор игровых данных, версия формата и игровая миграция, безопасная запись, загрузка в новый экземпляр сессии. Без облака, сетевого состояния, автоматической сериализации всей памяти, физики, UI-подписок и GPU-ресурсов. Это сохранение прогресса, не снимок процесса Windows.

## Сущности и владение

1. **SaveGame** — чистый контейнер данных: engine envelope и версионированный игровой payload. Не GameComponent и не новая сцена. Нет указателей на Game, Scene, DLL или GPU.
2. **GameSaveCodec** — реализация в проектной DLL. Знает, какие игровые данные сохранить, как проверить/мигрировать payload и как подготовить восстановленный мир. Для MVP один codec на игру; обязательные/опциональные секции задаёт игра. Экономику движок не знает.
3. **SaveGame facade** — удобный C++ API, доступный игре через Game/контекст сессии. Передаёт запрос координатору; нажатие кнопки не выполняет запись посреди обхода компонентов. Разработчик получает ticket/result, а не ложный успех при постановке запроса.
4. **SaveGameCoordinator** — Engine/runtime, вне заменяемой игровой сессии. Ставит запросы в очередь, выбирает безопасную границу кадра, управляет захватом и подготовкой кандидата, доставляет результат. На одну сессию одновременно одна операция Save/Load; повторный запрос получает Busy, а не неявно теряется.
5. **SaveGameStore** — Engine/host: List/Read/Write/Delete слотов, ограничения размера, путь, атомарная замена. Получает только принадлежащие host байты и метаданные. Не хранит callbacks/объекты из выгруженной DLL.

Путь: `%LOCALAPPDATA%/PainEngine/Saves/<gameId>/<profileId>/<slotId>.save.json`. Для тестов — отдельный явно заданный корень. Профиль MVP один: `default`; игровые проекты и export сохраняют один стабильный `gameId` из manifest. Это новое поле нужно добавить с миграцией: один раз выдать UUID старому проекту, сохранить при export/upgrade, новый ID выдавать при создании самостоятельной игры. Не генерировать новый ID на каждом запуске.

Slot ID — ограниченный идентификатор, не произвольный путь. Отображаемое русское название хранится внутри метаданных. Все разрешённые пути остаются внутри game/profile root, включая проверки reparse points. Запись в исходный Content и произвольные пути запрещены контрактом API.

## Файл первой версии

```json
{
  "format": 1,
  "gameId": "5b8dd2b0-96c1-4ea8-b3a1-47c17d787253",
  "gameSchema": 1,
  "engineVersion": "2026.11.04.1",
  "slotId": "manual-1",
  "label": "Город перед расширением",
  "savedAtUtc": "2026-11-04T19:00:00Z",
  "scene": "/Game/Scenes/Main.scene.json",
  "payload": {
    "economy": {"balance": 140, "incomeRemainder": 0.25, "incomePaused": false},
    "houses": [{"id": "house-a", "definition": "house-small", "position": [2, 0, 4]}]
  }
}
```

Пример иллюстрирует форму файла, а не полную игровую сцену. `format` — формат контейнера Engine, `gameSchema` — схема игры; версия Engine диагностическая и не требует точного равенства. Совместимость решают capabilities/кодеки и миграции, а не совпадение номера сборки. Неизвестный будущий format/schema возвращает UnsupportedVersion без записи в слот. Порог размера MVP выбрать явно, например 16 MiB, и тестировать отказ; большие миры/бинарный формат — последующая измеренная задача.

Каждая сущность принадлежит одному источнику восстановления: либо базовой сцене, либо игровому snapshot. Дом нельзя одновременно сохранить как объект сцены и ещё раз создать из houses. Для MVP взять базовую сцену с землёй/камерой/светом, а динамические дома — из DTO игры. Scene ComponentId не использовать как постоянный ID. Игра назначает устойчивые SaveId, после создания строит таблицу SaveId → новый ComponentId и отдельным проходом восстанавливает ссылки. Неизвестные обязательные ссылки отклоняют кандидата.

## Сохранение

1. UI/клавиша вызывает RequestSave(slot). Результат на этом этапе — Accepted(ticket), не Saved.
2. Координатор обрабатывает запрос после завершения тика и отложенных изменений Scene, до следующего тика. В renderer захват не переносится. Во время capture игровое состояние не меняется.
3. Module-local codec собирает DTO: деньги, дома, остаток таймера, нужное состояние подсистем. Он не сохраняет указатели, Input connections, HUD, GPU, текущие frame IDs и кэши.
4. Engine валидирует envelope/лимиты и получает собственную копию сериализованных байтов. Захват синхронный в потоке Engine; MVP может синхронно писать небольшой файл на этой же границе. Фоновая запись добавляется после измерения задержки, без доступа worker к игровым объектам.
5. Store пишет уникальный temp рядом со слотом, завершает/сбрасывает запись, затем заменяет файл через проверенный Windows atomic replace path. При ошибке старый слот остаётся, temp очищается. Проверить disk-full/access-denied и сбой перед заменой. Backup не считать необходимым условием MVP.
6. HUD получает Completed(Saved) либо Failed(code, message). Остановка игры/выгрузка DLL отменяет ещё не захваченные запросы; после копирования байтов host завершает запись без вызова уничтоженного игрового callback.

## Загрузка и жизненный цикл

1. RequestLoad(slot) проверяет возможность загрузки и читает файл, не меняя текущий мир. Проверяются gameId, schema/format, обязательные секции, конечные числа/диапазоны, ссылки на ассеты и типы. Игровые миграции работают над копией; исходный слот автоматически не переписывается.
2. Codec подготавливает данные, а module adapter создаёт отдельный кандидат GameSession + Game. Старый мир приостановлен, но жив. Загружается базовая сцена; формируются подсистемы и объекты кандидата, затем remap ссылок. Это новый путь в Engine, текущий Start не обеспечивает его автоматически.
3. Добавить контекст старта `NewGame` / `LoadGame`. При LoadGame состояние подсистем применяется **до OnSceneReady/BeginPlay**. Обычная начальная покупка/спавн трёх домов выполняется только при NewGame. HUD и input subscriptions создаются заново по данным, не восстанавливаются из указателей.
4. До commit выполнить все отклоняемые проверки/подготовку. Подготовительные callbacks не имеют внешних побочных эффектов. При ошибке уничтожить только кандидата и возобновить прежнюю сессию.
5. На границе кадра заменить активный экземпляр и переключить ввод/камеру, затем уничтожить старый. Commit — короткий, заранее подготовленный шаг без пользовательского кода, который может отклонить загрузку. После commit отправить событие Loaded для UI.

**Важное ограничение гарантии:** нельзя обещать откат произвольных файловых/сетевых действий игры или исключений из уже активированных callbacks. Контракт prepare должен быть без побочных эффектов; такие действия выполняются после commit и имеют собственную обработку ошибок. Не объявлять live load готовым, пока Runtime и embedded Play не умеют переключать кандидата безопасно. На первом этапе разрешить загрузку из главного меню в новую сессию; live load открыть только после соответствующих тестов.

## Граница DLL и совместимость

Не дописывать поля в существующие frozen Module API структуры и не передавать STL/JSON/unique_ptr между DLL и host. Предложение: необязательный экспорт `EngineGetSaveGameApi(version, size, out)` и host service `SaveGameStorage v1`, получаемый через существующий getService. Конкретную таблицу функций зафиксировать на этапе проектирования ABI: opaque session/candidate handles, UTF-8 байты с размером, явный owner/освобождение, числовые статусы. Старые DLL продолжают запускаться; отсутствие extension означает SaveGameUnsupported, не аварийный вызов нового virtual метода.

Высокоуровневые типы и game codec остаются внутри нового игрового модуля, собранного с соответствующим SDK. Все opaque handles освобождаются до unload DLL. Host не вызывает callbacks старой generation после hot reload. Hot reload во время активной операции отклоняется Busy либо сначала явно отменяет подготовку; silent unload недопустим.

## Пример взаимодействия разработчика

Следующий код — **проектный эскиз, не компилируемый пример текущего API**. Точные сигнатуры определятся после проверки lifecycle и ABI.

```cpp
struct CitySaveData {
    int balance;
    double incomeRemainder;
    bool incomePaused;
    std::vector<HouseSaveData> houses; // SaveId, definition, position
};

// Один раз при создании игровой сессии, до её запуска:
saveGames.RegisterCodec("city", 1, std::make_unique<CitySaveCodec>());
// Codec реализует Capture / DecodeAndValidate / Migrate / PrepareRestore.

// Кнопка и клавиша вызывают одну игровую функцию:
auto ticket = saveGames.RequestSave("manual-1");
// Accepted -> "Сохраняется…"; Completed(ticket) -> "Сохранено".
// Failed(ticket, error) -> понятное сообщение, игра продолжает работать.

// В меню загрузки:
auto slots = saveGames.ListSlots();
auto load = saveGames.RequestLoad(slots.front().id);

// В логике старта (новый контекст):
if (start.reason == StartReason::NewGame) CreateInitialCity();
// LoadGame уже получил восстановленное состояние; повторно денег не списывать.
```

Для самой первой реализации допустим сериализатор JSON в коде игры. Inspector properties не равны автоматическому включению в SaveGame: designer-настройка цены и runtime-баланс имеют разные контракты. Автогенерацию Save-полей через новые аннотации рассматривать после рабочего ручного codec; не включать все свойства без решения разработчика.

Позиция игрока/камеры, инвентарь, изменённые параметры объектов и состояние игрового RNG добавляются в DTO явно, если игра требует их восстановления. Для параметров, заданных definition-ассетом, игра решает, фиксировать ли значение в сохранении или использовать текущую версию definition; изменения этого правила сопровождаются gameSchema/migration.

## Этапы реализации и критерии

| Этап | Изменения | Проверяемый результат |
|---|---|---|
| 1. Контракты и хранилище | SaveGame envelope/result, stable gameId, List/Read/Write/Delete, UTF-8 JSON, temp/replace, лимиты | Сохранение переживает перезапуск процесса; отказ записи не меняет прежний слот; пути/размеры ограничены |
| 2. Захват игры | Codec registration, queue/ticket, boundary после Scene updates, экономика/дома/таймер Curious City | Получаем согласованный snapshot, деньги/дома не расходятся при Deferred; HUD отличает Accepted и Saved |
| 3. Загрузка из меню | Новая сессия, StartReason, decode/migrate/validate, SaveId remap | 4 дома/140 денег/0.25 таймера восстановлены, нет повторной покупки и двойных подписок |
| 4. Безопасная смена живой сессии | Candidate preparation + commit, rollback до commit, focus/camera, embedded Play | Неуспешная подготовка оставляет старую игру; успешная Load переключает ввод один раз |
| 5. SDK и совместимость | Optional C ABI extension/service, старые DLL, examples/API Reference | Старый модуль запускается с Unsupported; новый работает и в editor Play, и в экспортированной игре |
| 6. Последующие удобства | Autosave policy, thumbnails, большие/асинхронные saves, оптимизация по измерениям | Только после MVP и измерения времени/объёма; не условие первой версии |

Этапы 1–3 — первый полезный релиз; этап 4 нужен до обещания «загрузить прямо из игры с сохранением старой сессии при отказе». ABI-эскиз требуется до этапа 2, полная совместимость проверяется на этапе 5; это не разрешение временно ломать frozen API.

Минимальный набор тестов: запись/перезапуск/чтение; перезапись и сбой до replace; повреждённый/truncated JSON; неизвестные format/gameSchema; другая gameId; отсутствующий обязательный asset/type; миграция старого payload без изменения исходника; циклические/неразрешённые ссылки; повторный запрос Busy; Save во время Deferred mutation; Load не удваивает стартовый спавн; доход после resume учитывает остаток таймера; Pause; Stop/Reload при запросе; кириллица; writable user folder у экспортированной игры; два gameId не видят чужие слоты; фото/кадр до и после восстановления сцены.

Тестовые команды `savegame.list/save/load/validate` — план будущего расширения EngineCommandlets, не существующие команды. Они должны обращаться к Store и настоящему игровому codec, а не реализовывать копию экономики внутри тестовой утилиты.
