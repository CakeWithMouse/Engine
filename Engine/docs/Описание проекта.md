# Архитектура Engine, игр и лаунчера

Добавлен отдельный [каркас EngineRuntime](RUNTIME-QUICKSTART.md): один exe, game/editor DLL и заглушки. Описание ниже относится к сохранённому старому runtime класса Game. BaseEngine/BaseResources теперь имеют реализацию заглушек; старый Game ещё не перенесён.

Актуальные пути сборки, структура Game и лаунчер: [архитектура папок](FOLDER-ARCHITECTURE.md).

Актуальная рабочая структура с 2026-10-04. Историческое описание до переноса сохранено в `Game/Archive/1_Lab/ARCHITECTURE.before-split.md`.

Практические примеры и границы будущего редактора описаны в [руководстве по разработке](DEVELOPMENT.md).

## Границы и сборка

`Engine/Engine.vcxproj` собирает статическую библиотеку. Четыре проекта в Game (BasicExamples, Pong, SunGame, Katamari) собирают самостоятельные приложения и ссылаются на Engine через ProjectReference. `Engine/tests/EngineTests.vcxproj` использует ту же библиотеку. Отдельный EngineLauncher запускает выбранный exe и не линкуется с Engine. Все проекты объединены в `Engine/Engine.sln`; Katamari требует Assimp и исключена из сборки по умолчанию. Каталоги результатов игр изолированы: `Game/build/x64/<Configuration>/<Name>`.

MSBuild оставлен потому, что исходный проект уже использовал Visual Studio и MSVC. Не понадобились новый генератор проектов или runtime plugin API. Эта итерация даёт раздельную компиляцию: при изменении SunGame ядро не перекомпилируется, затем приложение перелинковывается. Горячей замены кода пока нет.

Публичный SDK — `Engine/Include/Engine`; include-пути задаёт `Engine/Engine.props`. Game/SunGame не включает приватные исходники движка. GLM является зависимостью публичных типов, его include-путь экспортируется вместе с SDK. stb применяется внутри реализации. Assimp — опциональная сборочная зависимость существующего импортёра, отключённая для процедурной SunGame по умолчанию.

Общие параметры C++17, Unicode, runtime, Debug/Release и каталоги результатов заданы в `Engine/BuildSupport/Cpp.props`. Индивидуальные Debug-переопределения из старого vcxproj не переносились. Новое решение поддерживает x64; Win32 оставлен в исторических файлах, не обещается для новой сборки.

## Выполнение

`Game/SunGame/Source/Main.cpp` определяет корни ресурсов, создаёт SunGame, вызывает Initialize, BuildScene, затем StartGame. Базовый класс `Game` реализован в Engine: он владеет Win32-окном, D3D11 device/context/swapchain, реестром компонентов, кадром и освобождением ресурсов. SunGame задаёт цвет очистки и содержимое сцены.

Имя `Game` осталось историческим: это базовое приложение движка, а не ссылка на конкретную игру. Неиспользуемый enum GameType и SetGameType с названиями лабораторных удалены из API ядра. Engine не выбирает SunGame и не знает о Game/SunGame.

Цикл: сообщения окна → отложенный resize → UpdateFrame → PreUpdate → камера → компоненты → свет/тени и константы → рендер → Present → завершение кадра ввода. Масштаб времени и все скорости солнечной системы сохранены. При --smoke SunGame отправляет WM_QUIT после 30 обновлений; штатный цикл движка обрабатывает сообщение.

BaseEngine, BaseResources и BaseGameConfig перенесены как основа дальнейшей разработки в `Engine/Include/Engine/Base` и `Engine/Source/Base`; все три cpp включены в Engine.vcxproj. Методы жизненного цикла BaseEngine и Initialize/DeInitialize у BaseResources пока только объявлены, их вызов потребует реализации. Текущий запуск остаётся в Game; StartMain в Game/Archive/1_Lab — исторический прототип. Следующий этап подключения основы отслеживается в 028-H.

BaseResources получает пути общих шейдеров через EnginePaths. Корень нужно задать до создания BaseResources; пути сохраняются в его полях при создании. Исторический FindProjectDirectory теперь возвращает корень контента Engine, как и ResolveContentRoot, а не каталог старой лабораторной. Выбор конкретной игры исключён из BaseGameConfig; остальные настройки сохранены. SunGameConfig пока остаётся отдельной конфигурацией примера.

## Ресурсы

EnginePaths определяет корень EngineContent относительно exe; SetContentRoot позволяет явно переопределить его до инициализации Game. Шейдеры движка и пути, передаваемые компонентам SunGame, получаются через EnginePaths::Shader. Загрузка HLSL не зависит от рабочей директории.

Каждая игра отдельно получает свой GameContent. В SunGame может лежать cosy.jpg; остальные объекты создаются процедурно. Непредоставленная текстура даёт прежнее поведение без cubemap. Katamari использует собственную копию моделей/текстур в Game/Katamari/Content; оригиналы и архивы сохранены в Game/Archive/1_Lab. RequiredFiles.txt проверяется лаунчером и прямой точкой входа игры до инициализации окна.

При сборке Content.targets копирует Engine/Content в EngineContent рядом с каждым игровым exe; каждый проект копирует свой Content в GameContent. Файлы, удалённые из исходного Content, пока автоматически не удаляются из выходного каталога: это записано в 028-C.

В текущем учебном варианте корень ресурсов Engine общий для процесса; менять его во время игры или из разных потоков не предусмотрено. Resource manager, reload, handles и миграция состояния — отдельные будущие задачи.

## Сохранённые контракты

- RegisterComponent принимает владение только при RegisterResult::Ok; при отказе объект остаётся у вызывающего.
- Удаление компонента очищает связи иерархии и реестр света; Game уничтожает принадлежащие ему объекты до освобождения устройства.
- Базовые Forward/Deferred проходы, кэш вариантов шейдеров, инстансинг, тени и GPU-частицы перенесены с прежней реализацией.
- Импортёр FBXComponent сохранён; заголовки Assimp перенесены из публичного заголовка в его cpp.
- Статические библиотека и приложение собираются совместимым toolset и CRT. Стабильный DLL ABI этой итерацией не вводится.

## Направление разработки

Учебный движок должен быть понятным и надёжным. Игры в духе Total War — ориентир для последующих сцен и измерений, а не основание сейчас строить большой ECS. Следующие кандидаты: выделение и команды группам, простая навигация, измерения большого числа объектов, затем конкретная оптимизация видимости/отрисовки или симуляции. См. трекеры 027 и 028.
