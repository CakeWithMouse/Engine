# Scene: API ядра и контракт подключения редактора

Для нового подключения viewport/Play использовать [Edit session API](EDIT-SESSION-API.md).
Это отдельная edit-safe сессия, которая отображает ту же Scene, что редактирует.

Следующий этап: [автообнаружение классов, каталог и фабрики](COMPONENT-GENERATION.md).
Каталог реализован отдельно. Этап 039 добавил ключ типа в снимок и
[команды через игровой DLL](SCENE-MODULE-API.md); JSON ещё впереди.

Статус: C++ API реализован на этапе 037. В самой Scene нет SceneObject, JSON, реестра типов,
новых панелей. Отдельный DLL-контракт добавлен этапом 039. Заголовок —
[`Scene.h`](../Include/Engine/Scene/Scene.h), реализация —
[`Scene.cpp`](../Source/Scene/Scene.cpp).

## Модель и владение

```text
Game / ViewportSession (движок, один поток)
  Game редактирования → Scene → unique_ptr<GameComponent>
  Game для Play       → Scene → другие unique_ptr<GameComponent>
```

Scene владеет компонентами и их именами/ID. GameComponent сохраняет transform,
связь с родителем и игровое поведение. Отдельного объекта-контейнера нет.
Сцена не создаёт окно, устройство, swap chain, графические буферы или свой цикл.
Её можно создавать, наполнять, изменять и проверять без окна/GPU.
Существующие GameComponent всё ещё содержат графические поля и могут зависеть
от Game в своей логике; создание Scene не делает такую логику независимой от Game.

`Game::GetScene()` возвращает принадлежащую Game сцену. Поле `Components` в Game
теперь лишь read-only ссылка на её контейнер для совместимости старых обходов.
Удалять компоненты через raw pointer запрещено: использовать RemoveComponent.
Scene не копируется и не перемещается. Срок жизни UpdateScope должен быть короче Scene.

Сцена хранится только в памяти. Построители BuildScene/AfterInitialize продолжают
наполнять её через совместимый Game::RegisterComponent. Закрытие её уничтожает;
сохранения на диск в этом этапе нет.

## Идентификаторы

- `SceneId` и `ComponentId` — uint64_t; 0 означает отсутствие.
- SceneId различает сцены, созданные ядром host в текущем процессе.
- ComponentId уникален только внутри Scene и не переиспользуется после удаления.
- Полная внешняя ссылка: `(SceneId, ComponentId)`. Нельзя использовать один ID
  компонента для маршрутизации между сценами: локальные номера могут совпадать.
- Переименование не меняет ID. Новая игровая сцена получает другой SceneId.
- Это runtime-ID, не GUID ресурсов и не обещание стабильности между запусками.
- Для сцен в разных DLL дополнительно нужно поколение сессии: статическая Engine.lib
  не даёт общего счётчика между модулями. См. Scene module API.
- Внутренние инстансы `GameComponent::CreateInstance` пока не отдельные элементы
  Scene: у них нет Scene-ID компонента и строк в Hierarchy/snapshot.

## Публичные операции

Все вызовы ниже выполняются на потоке движка. Внутренних mutex нет.

| Метод | Результат и правила |
|---|---|
| `Scene(name)` | Создаёт пустую сцену; пустое имя вызывает invalid_argument |
| `GetId/GetName/GetRevision` | Идентификатор, имя, счётчик изменений API |
| `SetName(name)` | Ok или EmptyName; одинаковое имя не меняет revision |
| `AddComponent(name, unique_ptr<GameComponent>&, typeName={})` | Возвращает `{result, id}`; Ok/Deferred передают владение сцене и обнуляют аргумент; копирует ключ типа, пустой для прежних вызовов |
| `RemoveComponent(id)` | Ok, Deferred или NotFound; удаляет также компонент, ожидающий добавления |
| `FindComponent(id)` | Указатель на существующий компонент или nullptr; const-перегрузка read-only |
| `FindComponentByName(name)` | Совместимость с нынешними играми; поиск регистрозависимый |
| `RenameComponent(id, name)` | ID сохраняется; NotFound, EmptyName, DuplicateName, Busy или Ok |
| `SetTransform(id, transform)` | Меняет локальные position/rotation/scale; Ok, NotFound или InvalidTransform |
| `SetParent(child, parent, inheritScale=true)` | Только существующие компоненты этой сцены; Ok, NotFound, InvalidParent или ParentCycle |
| `ClearParent(child)` | Ok или NotFound; локальный transform остаётся прежним |
| `GetSnapshot()` | Независимая копия метаданных; изменение копии не меняет Scene |
| `BeginUpdate()` | RAII-граница отложенных изменений для нестандартного игрового обновления |
| `Tick(dt, pauseNonSkybox=false)` | Вызывает Tick компонентов; сам по себе не проверяет режим редактора |

AddComponent проверяет null, пустое/занятое имя, принадлежность другой сцене и родителя.
Ошибки: NullComponent, EmptyName, DuplicateName, AlreadyOwned, InvalidParent.
При отказе unique_ptr остаётся у вызывающего. При исключении выделения памяти
AddComponent также не забирает компонент. Резервирование ID может оставлять пропуски.
Нельзя создавать второй unique_ptr для уже принадлежащего сцене указателя.
Аргумент имеет тип `unique_ptr<GameComponent>`, не ссылку на `unique_ptr<Derived>`.

Имена пока уникальны в сцене, включая ожидающие добавления. Это нужно старым играм.
Указатели, ссылки на контейнеры и итераторы предназначены для ядра, не UI.
Указатель становится недействительным после фактического удаления или закрытия Scene.

## Transform и иерархия

`SceneTransform` содержит `glm::vec3 position`, `glm::quat rotation`, `glm::vec3 scale`.
Все значения локальные. Quaternion нормализуется; конструктор GLM принимает `(w,x,y,z)`.
Inspector может показывать углы в градусах, преобразуя их перед вызовом API.
Отрицательный scale разрешён; по каждой оси требуется `abs(scale) >= 1e-6`.
NaN/Infinity и quaternion с квадратом длины меньше 1e-12 отклоняются целиком:
не меняется ни transform, ни revision. Quaternion по умолчанию единичный.

SetParent не пересчитывает локальный transform, поэтому мировое положение может
измениться. `inheritScale=false` использует существующий SetParentWithoutScale.
Цикл, включая самого себя, запрещён. Зарегистрированный GameComponent также
отклоняет прямой SetParent на компонент чужой сцены.

Для добавления уже связанного компонента его родитель должен быть зарегистрирован
в той же сцене и уже виден в FindComponent. Другой вариант: сначала добавить объекты,
затем установить связи. Удаление родителя отсоединяет его непосредственных детей
и очищает ссылки внутренних инстансов; дети не удаляются, локальные transforms сохраняются.

## Снимки и revision

```text
SceneSnapshot: id, name, revision, components[]
  SceneComponentSnapshot:
    id, name, parentId (0 = нет), inheritParentScale, transform
```

Список упорядочен по ID, то есть порядку добавления. Snapshot не содержит raw pointer,
GPU-объектов, типов для универсального Inspector и произвольных игровых свойств.
Снимок можно передать в UI копированием после получения на потоке движка.
Сам GetSnapshot одновременно с игровым обновлением из другого потока вызывать нельзя.

Revision монотонно растёт при применении изменений через Scene. Ошибки его не меняют;
одна отложенная пачка добавлений может увеличить его один раз. Это маркер изменения,
а не число команд, не Undo-индекс и не версия сохранённого файла.
Прямые SetPosition/игровые Tick могут менять компонент без revision: в Play нельзя
полагаться только на этот счётчик, если UI требуется живое состояние компонентов.

## Обновление и отложенные операции

```text
Game.UpdateFrame
  → подготовить новые компоненты к работе с Game/GPU
  → только при включённой симуляции:
       BeginUpdate → PreUpdate → камера → TickComponents → конец scope
  → подготовить добавленные во время Tick компоненты и данные изображения
  → render / present
```

Обычный TickComponents делегирует Scene::Tick; тот обходит имена в прежнем порядке.
Специальный порядок Pong сохранён; внешний scope охватывает и его обход.
Scene::Tick можно использовать без Game, если конкретным компонентам не нужны его
сервисы. Повторный рекурсивный Scene::Tick запрещён и вызывает logic_error.
Второй аргумент Tick сохранён для старой standalone-паузы Space; редактор при Pause
вообще не вызывает игровой Tick, даже с нулевым dt.

Внутри UpdateScope:
- Add резервирует ID/имя и получает владение, возвращая Deferred. Find/Snapshot
  пока его не показывают; первый Tick нового компонента — в следующем обновлении.
- Remove возвращает Deferred. Компонент остаётся живым до конца внешнего scope
  и может ещё получить Tick в этом проходе. Повторное удаление объединяется.
- Можно отменить ожидающее добавление вызовом Remove по зарезервированному ID.
- Переименование, меняющее порядок обхода, возвращает Busy; его надо повторить
  между обновлениями. Transform/parent можно менять сразу.
- На выходе из внешнего scope сначала присоединяются новые компоненты, потом
  применяются удаления и очищаются родительские ссылки.

Scope применяет принятые операции и при исключении из Tick. Это безопасность
жизни объектов, а не транзакционный rollback. Нельзя уничтожать Scene из её Tick.

## Графическая интеграция

Game::RegisterComponent остаётся совместимой обёрткой: проверяет device, создаёт
ресурсы и передаёт владение Scene. Ok также означает принятое отложенное добавление
во время Tick; компонент не становится доступен через Find до конца обновления.
UnregisterComponent возвращает true для принятого отложенного удаления.

При прямом Scene::AddComponent GPU-ресурсы не создаются. Принадлежащий Game компонент
получает GamePtr и CreateBuffers на следующем активном кадре, до игрового Tick/рендера.
Материалы/геометрию нужно настроить до добавления. Обновление transform через Scene
отображается в Edit без Tick и инвалидирует запечённую тень на следующем кадре.
Список света читается из Scene по ID; отдельного кэша с висячими указателями нет.

## Подключение редактора: реализовано и запланировано

**Реализовано:** Scene.h и C++ операции выше. В Editor.dll по-прежнему ABI v4:
viewport, камера и Play/Pause. Callback-команд редактирования Scene в ABI пока нет.
Редактор не должен включать Scene.h для передачи Scene*/STL через DLL.

Реализованный адаптер игрового модуля теперь описан в [Scene module API](SCENE-MODULE-API.md).
Он отклоняет команды во время BeginUpdate с Busy, не выдаёт Deferred наружу.
Описанная ниже очередь UI/host всё ещё относится к следующему этапу редактора.

Для следующего этапа подключения Hierarchy/Inspector требуется такой адаптер:

```text
Qt UI → запрос(requestId, SceneId, ComponentId, операция, значения)
      → очередь → поток host → проверка SceneId и режима
      → вызов C++ Scene API между обновлениями
      → ответ(requestId, результат, revision) + snapshot → Qt UI
```

Обязательства будущего адаптера:
1. Проверять SceneId до ComponentId, чтобы запоздавшая команда после Stop/закрытия
   не попала в другую сцену с тем же локальным ID.
2. Правки документа разрешать только в Edit. В Play/Pause показывать игровую сцену
   для просмотра; Scene сама не знает режим редактора и не обеспечивает эту политику.
3. Выполнять команды до BeginUpdate. При Deferred ответ о применении/новый snapshot
   выдавать после границы, не выдавая принятие в очередь за завершённую операцию.
4. Qt хранит значения и ID, не GameComponent*. Ошибки показываются пользователю.
5. Для C ABI определить POD, UTF-8, размеры/время жизни буферов и повысить версию;
   этот документ не объявляет ещё не реализованные callbacks доступными.

## Пример использования на потоке host

```cpp
Scene& scene = game.GetScene();
std::unique_ptr<GameComponent> candidate = std::make_unique<GameComponent>();
const auto added = scene.AddComponent("Marker", candidate);
if (added.result == SceneResult::Ok) {
    SceneTransform transform;
    transform.position = {1.0f, 2.0f, 3.0f};
    const auto result = scene.SetTransform(added.id, transform);
    const SceneSnapshot snapshot = scene.GetSnapshot();
    // Скопировать snapshot в UI через будущий адаптер; candidate уже пуст.
}
```

Marker здесь базовый компонент без геометрии. Для видимого объекта сначала
создать и настроить подходящий CubeComponent/другой существующий тип.

## Дальнейшее расширение

- JSON и реестр типов/свойств: сериализуемые начальные данные и миграции версий.
- Undo/Redo: редакторские команды с предыдущими значениями, поверх Scene API.
- Play из снимка данных: замена нынешней фабрики. Сейчас Play заново строит начальную
  сцену; произвольные правки Edit в игровую сцену ещё не копируются, но Stop их сохраняет.
- Несколько документов: независимые Scene и идентификаторы, затем менеджер загрузки.
- Игровая камера и окружение как данные Scene — отдельный перенос, не часть этой работы.
- Контейнер с несколькими компонентами — только при конкретной необходимости;
  SceneObject и ECS этим контрактом не вводятся.
