Статус на 2026-11-08: план согласован; этапы 1 и 2 выполнены, этапы 3–5 не начаты.

## Границы задачи

Делаем самый простой работающий визуальный скриптинг: граф событий и действий у объекта сцены, интерпретатор в движке, окно редактора на общем ядре графа. Пользователь может работать в проекте без C++.

Графовый редактор ИИ (behavior tree, state machine) сейчас не делаем. Ядро закладывается так, чтобы он лёг поверх без переписывания (см. последний раздел).

Что изучено:
- `MaterialGraphWidget`: ветка `origin/MaterialEditor`, коммит `926cd34`, уже в `main`;
- `MaterialGraphModel`, `HlslGraphCompiler`, `MaterialEditorWindow`, `EditorQtHost`;
- `EditExtensions.h`: базовые таблицы заморожены `static_assert`;
- `SceneModule.inl`, `GameComponents.h`;
- документы COMPONENT-GENERATION, PROPERTY-MACROS, CODE-PROJECTS, MATERIALS, SCENE-JSON.

- дублирование;

- ошибки на нодах (красная рамка и подсказка) и `FocusNode`;
- контекстные меню.

`MaterialGraphModel`:
- ноды (`id`, `type`, `title`, `pos`, `properties`) и связи по именам пинов;
- JSON без версии и без схемы.

Вывод: вынести в общее ядро, а не писать заново. Примерно 60–70% кода виджета общие.

Привязано к материалам:
- каталог и группы нод;
- типы пинов `float1..4`;
- правило «связь допустима всегда»;
- значения по умолчанию в `AddNode`;
- диалоги `EditNode`;
- текстуры и миниатюры;
- синхронизация параметров с материалом;
- готовые графы и AI-промпт;
- особый случай `MaterialOutput`;
- эвристика «массив из 4 чисел → `QColor`» в модели.

Правила связей сейчас жёсткие и не подходят для кода:
- у входа одна связь, выход расходится на много входов;
- циклы запрещены.

Для exec-пинов кода нужно наоборот: у exec-выхода одна связь, у exec-входа много. Поэтому правила переходят в схему.

## Архитектура

```text
Editor/Core/Graph/        (Qt Core, без виджетов, тестируется в CoreTests)
  GraphDocument           ноды, связи, переменные, свойства связей, неизвестные поля; JSON с заголовком
  GraphSchema             интерфейс: типы нод, пины (в т.ч. по свойствам ноды), CanConnect, Validate,
                          значения по умолчанию, цвета, что нельзя удалить или скопировать
  GraphHistory            снимки и склейка (перенос из виджета)
  GraphClipboard          JSON с меткой и id схемы; вставка в чужую схему отклоняется
Editor/Source/Graph/
  GraphEditorWidget       холст, ноды, связи, выделение, поиск, ошибки, горячие клавиши;
                          параметризован GraphSchema и необязательным декоратором ноды
                          (миниатюра, значение в ноде)
Схемы:
  MaterialSchema          + декоратор текстур; MaterialGraphWidget становится тонкой обёрткой
  CodeSchema              exec и data пины, типы, каталог нод из игрового модуля
  (позже) AiBtSchema / AiFsmSchema
Engine/Script/            каталог нод, ScriptProgram, интерпретатор, ScriptInstance
```

Решения:
- **Пины от ноды, а не только от типа:** `PinsFor(node)`. Это нужно для `Sequence` с N выходами и для будущих BT/FSM.
- **Связи хранят `properties`.** В коде они пустые; переходы state machine позже понесут в них условия.
- **Типы и цвета пинов задаёт схема.** Ядро не знает `float3` и `exec`.
- **Ошибки двух уровней.** Ошибки валидации в редакторе и ошибки выполнения в Play показываются одним API `SetNodeProblems`.

## Формат файла графа

Скрипт — ассет `Content/Scripts/Имя.vscript` (JSON, UTF-8):

```json
{
  "format": "ITMOEngine.Graph", "version": 1,
  "schema": "code", "schemaVersion": 1,
  "variables": [{"name": "Speed", "type": "float", "value": 90}],
  "nodes": [{"id": 1, "type": "Event.Tick", "title": "", "x": 0, "y": 0, "properties": {}}],
  "connections": [{"fromNode": 1, "fromPin": "then", "toNode": 2, "toPin": "exec", "properties": {}}],
  "editor": {"view": {"x": 0, "y": 0, "zoom": 1}}
}
```

Правила чтения:
- Ключи нод и связей те же, что у `.mat.graph.json`. Файл материала без заголовка читается как `schema: material` версии 0, его формат не меняется.
- **Неизвестный тип ноды** сохраняется при записи как есть и показывается ошибкой. **Неизвестные поля** тоже сохраняются.
- `version` или `schemaVersion` новее известных — файл открывается только для чтения с сообщением.
- Типы значений: `bool`, `float`, `vec3`, `string`, `object` (ComponentId; в файле только `null` или «сам объект»).

## Исполнение в игре: интерпретатор (рекомендация)

**Интерпретатор в `Engine` (static lib)**:
- работает в проекте без C++: шаблон `Game.dll` уже содержит движок;
- работает в C++-проектах после пересборки с новым SDK;
- правка графа видна в следующем Play без компилятора и Hot Reload;
- ошибка выполнения естественно указывает на id ноды.

**Генерация C++** требует MSVC и SDK, то есть только C++-проектов, плюс сборку и Hot Reload на каждую правку. Ошибки тогда пришлось бы сопоставлять с нодами отдельно. Откладываем; формат файла её не исключает.

Устройство:
- `ScriptCatalog`: таблица нод в C++. Для каждой ноды — тип, группа, подписи ru/en, пины, типы и реализация. Одна таблица служит и интерпретатору, и редактору (JSON через расширение, см. ABI).
- `ScriptProgram`: JSON собирается один раз на ассет. Получаются плотный массив нод, разрешённые индексы пинов, константы и точки входа событий. При ошибке сборки получаем список «нода → текст».
- Выполнение:
  - **exec-цепочка** проходится по шагам;
  - **data-пины** вычисляются лениво, с кэшем на одно выполнение события;
  - значения хранятся в маленьком variant;
  - лимит шагов на событие (10 000): «вероятно бесконечный цикл».
- **Ошибка** пишется в лог с путём и id ноды. Экземпляр скрипта выключается до следующего Play, игра не падает.
- `ScriptInstance` хранит переменные экземпляра и выполняется только в Play и в игре, не в Edit и Pause. События: `BeginPlay` — один раз, `Tick` — после `Tick` компонента.
- Кэш программ ключуется путём и временем записи. Начало Play перечитывает изменённые файлы, F6 не нужен.

## Привязка к объекту

**Рекомендация: один скрипт на объект, как материал.**
- Поле `ScriptAssetPath` и `std::unique_ptr<ScriptInstance>` в `GameComponent`. Это меняет layout только внутри static lib.
- В сцене необязательное `assets.script` рядом с `assets.material`.
- Дублирование, копия для Play и сохранение проходят через JSON сцены. Undo/Redo делаем по образцу материала (проверить на этапе 3, как `EditorHistory` хранит материал).

Альтернатива — отдельный объект `ScriptComponent` со строковым свойством. ABI она не трогает, но не умеет ссылаться на объект, которым управляет. Отклонена.

Переменные графа берут значения по умолчанию. Переопределение на объекте отложено.

## Минимальный набор нод (MVP)

**События:**
- Начало игры;
- Каждый кадр (`dt`);
- Действие ввода нажато / отпущено (имя действия из `Input::System`).

**Поток:**
- Ветвление (if);
- Последовательность (N выходов).

**Действия:**
- Вывести в консоль;
- Задать позицию / поворот / масштаб;
- Сдвинуть;
- Повернуть;
- Задать переменную.

**Данные:**
- Сам объект; Найти объект по имени;
- Получить позицию / поворот / масштаб;
- Получить переменную;
- Константы: число, логическое, вектор, строка;
- Собрать / разобрать vec3;
- Арифметика: `+ − × ÷` для числа и vec3, ×число для vec3;
- Сравнения, И / ИЛИ / НЕ;
- `sin`, `lerp`, `clamp`, случайное в диапазоне;
- Время с начала игры.

Ноды с объектом принимают `object`. Пустой вход означает «сам объект».

## Интеграция в редактор

**Files:**
- «Создать → Скрипт» в `Content/Scripts`;
- двойной щелчок открывает `ScriptEditorWindow` (немодальное окно, как окно материала);
- фильтр `*.vscript`.

**Окно скрипта:**
- холст на общем ядре;
- панель переменных: имя, тип, значение;
- список ошибок: щелчок фокусирует ноду;
- Ctrl+Z/Y/C/V/D, Tab — поиск нод, F — показать всё.
- Валидация на каждую правку: обязательные входы, типы, неизвестные ноды, граф без события.
- **Запись на каждую правку**, как у материалов: нет «грязного» состояния и вопросов при закрытии и Hot Reload.

**Свойства объекта:** поле «Скрипт» с выбором файла, «Открыть» и «Создать», как поле «Материал». Скрыто, если игровой модуль не поддерживает скрипты.

**Play:**
- скрипты читаются с диска при старте;
- правки во время Play действуют со следующего Play;
- ошибки выполнения идут в Console со ссылкой «скрипт: нода» и красной рамкой в открытом окне.

**Hot Reload DLL:** окно перечитывает каталог нод и заново проверяет граф.

## ABI и совместимость

- **Замороженные таблицы не меняются:** `EngineSceneApi` (72), `EngineEditSessionApi` (320). Edit API остаётся v6, Scene API — v4, `ENGINE_MODULE_VERSION` — 5.
- **Новое именованное расширение `Engine.Scene.Script` v1** через `EngineGetEditExtension`:
  - `describeNodes`: JSON каталога;
  - `getScript` / `setScript(id, path)`;
  - `takeErrors`: ошибки выполнения с путём и id ноды.

  Проверяются version и size; после Hot Reload расширение запрашивается заново.
- **Старый `Game.dll` без расширения:**
  - поле «Скрипт» скрыто;
  - `.vscript` открывается только для чтения с сообщением «обновите Game.dll проекта».

  Это известное ручное обновление DLL после смены версии.
- **`assets.script` в JSON сцены.** Проверить, что старый runtime игнорирует неизвестный ключ в `assets`. Если нет — поднять версию документа через `EngineDocumentCapabilities` и писать ключ только при назначенном скрипте.
- **Новый выпуск:**
  - пересобрать шаблон `SceneProject/Game.dll`;
  - обновить SDK, `TemplateCompatibility.json` и ENGINE-VERSIONS.
- SaveGame не сохраняет состояние скриптов (записать в «Границы» документа).

## Как поверх ляжет редактор ИИ

Новые схемы на том же ядре и формате (`schema: ai.bt` или `ai.fsm`) и отдельное окно.

**Переиспользуются:** холст, поиск, история, буфер обмена, ошибки, файл, панель переменных (blackboard).

**Behavior tree:**
- `CanConnect` разрешает одного родителя;
- порядок детей задаётся по X;
- нужна автораскладка дерева.

**State machine:**
- состояния — ноды с динамическими пинами (`PinsFor`);
- переходы — связи с `properties`: условие, приоритет.

**Условия и задачи** ссылаются на `.vscript` или берут чистые ноды из `ScriptCatalog`; значения те же, что у интерпретатора.

**Исполнитель** — отдельный в `Engine` (тик дерева или автомата), поверх будущей системы ИИ: навигация, восприятие.

**Отладка ИИ** требует живого статуса на нодах. Общий хук ядра (значок или подсветка ноды) пригодится и для отладчика кода.

**Что закладываем уже сейчас:**
- `PinsFor(node)`;
- свойства связей;
- id схемы в файле и буфере;
- реестр схем;
- хук статуса ноды в `GraphEditorWidget`.
