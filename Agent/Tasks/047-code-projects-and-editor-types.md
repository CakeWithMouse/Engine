# 047 Проекты с C++ и пользовательские типы в редакторе

Статус: реализовано, результаты проверок приведены ниже. Дата: 2026-10-25. Исходное состояние: commit `24bb6419`.

## Результат реализации

- Создание без кода / с C++, переход к C++ с сохранением сцены и предыдущей DLL, мастер Component / Game / Object.
- SDK выпуска 2026.10.25.0: публичные заголовки, готовые библиотеки, генератор и MSBuild props/targets. Проект не требует checkout Engine. IDE и Build.ps1 разрешают SDK по lock; конфигурации не смешиваются.
- Game и компонент генерируются с известными hooks и вызовом непосредственного родителя. Namespace можно задать вручную в C++; мастер создаёт класс в глобальном namespace.
- Три явных семейства регистрации вместо универсальной системы плагинов. ENGINE_OBJECT владеет независимым T через сценовую оболочку; собственного наследования от Engine у T не требуется. Сервисы с временем жизни всего проекта не добавлены.
- Каталог последней успешной сборки доступен в редакторе; Component/Object добавляются из палитры, Game выбирается отдельно. Непомеченные и служебные классы скрыты. Полный перечень: [PROJECT-CAPABILITIES.md](../../Engine/docs/PROJECT-CAPABILITIES.md).
- Пользовательские Game hooks выполняются в общем шаге симуляции встроенного Play и отдельной игры. Edit и Pause не тикают игровую логику.
- Явные JSON-кодеки, формат сцены 3, отдельное расширение Engine.Project.Data, сохранение / копия Play / Duplicate / Undo и remap ID. Инспектор редактирует JSON кодека; автоматической рефлексии C++ полей нет.
- Сборка кандидата, проверка сцен и фабрики, три кадра отдельного запуска, атомарное переключение Project.json. Старые бинарники сохраняются. Операции кода одного проекта защищены файловой блокировкой. Применение — повторное открытие, без переноса живой памяти.
- Схема действий пользователя, запуска, lock и build ID: [CODE-PROJECTS.md](../../Engine/docs/CODE-PROJECTS.md).

Ниже сохранён исходный план и расширенная матрица тестов. Это перечень проектных намерений; фактически выполненные проверки фиксируются в конце документа. Полный семантический анализ произвольных C++ методов и чистая машина без установленных tools не заявляются.

Цель: создавать проекты без кода и с C++, добавлять код в существующий проект без потери данных и показывать в редакторе пользовательские классы, доступные для создания. По уточнению пользователя поддержка должна охватывать иерархии вне GameComponent и Game.

Предлагается сохранить единый формат проекта и два способа предоставления игрового модуля: готовый модуль для проекта без кода и собираемая из исходников DLL для проекта с кодом. Начальные C++ файлы служат редактируемым каркасом; пользователь может добавлять свои классы, наследование и поведение.

## Предлагаемые архитектурные решения

### Единый проект и переход к C++

Сохранить Project.json и Engine.lock.json как описание запуска и привязку выпуска. Метаданные разработки вынести в отдельный версионированный файл, например Project.code.json: текущий строгий парсер Project.json отклоняет неизвестные поля. Точные имена новых полей фиксируются в этапе 0.

Пример структуры проекта с кодом:

```text
MyProject/
  Project.json
  Engine.lock.json
  Project.code.json
  Content/
  Source/
    MyProjectGame.h
    MyProjectGame.cpp
    MyComponent.h
    MyComponent.cpp
    Module.cpp
  MyProject.sln
  MyProject.vcxproj
  Build.ps1
  Binaries/<platform>/<configuration>/<build-id>/
  Intermediate/
```

Отображаемое имя проекта может быть кириллическим; C++ идентификатор, namespace и имя каталога генератора проверяются отдельно. Не вставлять отображаемое имя без экранирования в C++, XML и командную строку.

Переход к коду должен быть транзакцией: подготовить исходники и настройки, собрать кандидат, проверить экспорт API и каталог, проверить загрузку существующих сцен и только затем переключить активный модуль. Ошибка оставляет прежний проект запускаемым. Источники и лог неудачной сборки можно сохранить как подготовленные материалы, не отмечая переход завершённым. Повторный запуск мастера не перезаписывает правки пользователя.

В новый модуль включается библиотека штатных типов с прежними ключами Primitive.*, Light.* и ключами импортируемых моделей. Простое подключение только пользовательского GeneratedComponents лишит старую сцену её фабрик. Совпадение ключей должно быть ошибкой, а не переопределением встроенного типа.

Для проекта с неизвестной пользовательской DLL без исходников нельзя обещать восстановление кода: потребуется подключить имеющиеся исходники/описание сборки. Конвертация из штатного проекта проверяет его происхождение и совместимость; старому выпуску без SDK сначала нужен явный переход в копию на поддерживаемый выпуск.

### SDK для независимой сборки

Упаковывать вместе с выпуском либо отдельным связанным пакетом: публичные заголовки, Engine.lib и библиотеки поддержки модуля, необходимые заголовки сторонних библиотек, ComponentGenerator.exe, props/targets, исходные каркасы и манифест SDK. Ассеты, Qt и DLL-зависимости runtime остаются частью согласованного выпуска; SDK перечисляет необходимые варианты библиотек и зависимости.

В манифесте: идентификатор выпуска/SDK, архитектура, конфигурация, поддержанный toolset, CRT и варианты сборки, влияющие на ABI. Не обещать бинарную совместимость произвольных C++ сборок. Начальная поддержка — согласованные x64 Debug/Release и явно проверенные toolset.

Пользовательская сборка линкуется с готовыми библиотеками SDK, не требует исходников Engine и не пересобирает EngineRuntime/Editor. Выделить из SceneProject переиспользуемые штатные типы. SceneModule.inl сейчас включает приватный VfsRead.h через путь исходников; заменить такую зависимость публичной поддержкой модуля до упаковки SDK.

Runtime-выпуск не изменяется после установки. Build ID пользовательской DLL меняется при сборке независимо от номера движка. Проект хранит сведения о последней успешной сборке и её SDK; несовместимость диагностируется до загрузки.

### Общий каталог типов и правила создания

Расширить существующий генератор, сохранив ENGINE_COMPONENT. Для Game и других семейств ввести явно описанные метаданные типов. Рабочие названия новых аннотаций и API не считаются утверждённым контрактом до этапа 0.

Метаданные: устойчивый type ID, отображаемое имя, родитель/семейство, возможность создания, допустимые контексты, источник объявления, версия сохраняемых данных. Старые ключи компонентов сохраняются. Для новых типов отделить постоянный ID от имени C++ класса; переименование требует явного алиаса/миграции, чтобы не ломать сцены.

Распознавание строится на явном маркере и сгенерированном C++, без ручного списка каждого класса в движке. Мастер добавляет маркер сам. Для написанного вручную класса автор ставит его в заголовке. Наследование само по себе не является автоматической регистрацией: C++17 не предоставляет подходящего runtime-перечисления классов, а текущий сканер не является полным C++ парсером.

Один список типов не означает одну фабрику с небезопасным приведением указателей. Внутри DLL семейство предоставляет типизированный адаптер создания, уничтожения, владения и сохранения. Для наследников поддержанного семейства адаптер переиспользуется. Для новой независимой иерархии один раз определяется её адаптер; Engine и Editor не получают имён конкретных игровых классов.

| Семейство | Владелец и действие в редакторе |
|---|---|
| GameComponent и его косвенные наследники | Scene; действие «Добавить в сцену», пространственные инструменты |
| Game и его наследники | Сессия игры; действие «Выбрать класс игры», один активный экземпляр на сессию |
| Другая иерархия | Владелец и контекст из адаптера, например объект данных проекта или сервис игровой сессии |
| Абстрактный/не создаваемый зарегистрированный тип | Показать как базу с причиной недоступности создания |

Не вводить требование наследовать все типы от нового общего UObject. Независимый класс может быть виден и доступен к созданию через свой адаптер. Возможность default construction недостаточна: нужны доступное уничтожение, определённый владелец и допустимый контекст. Класс с параметрами конструктора допустим при явной фабрике, обеспечивающей эти параметры. Отсутствие такой фабрики исключает действие создания.

За границей DLL передавать копируемые описания и непрозрачные handles через версионированное C-расширение. Фабрики, C++ объекты, STL и уничтожение остаются внутри владельца DLL. Типы перечисляются без вызовов пользовательских конструкторов; редактор не хранит указатели каталога после завершения сессии.

Условия наследования/доступности проверяет C++ компилятор. Ограничения генератора для условных объявлений, шаблонов, вложенных и анонимных классов явно документировать; сложные конкретные специализации можно подключать через поддержанную явную регистрацию, без обещания полного разбора C++.

### Базовые классы и вызовы родителя

Создавать MyProjectGame и один простой MyComponent. Module.cpp подключает каталог штатных и пользовательских типов и фабрику выбранного класса игры. Файлы пользователя генерируются один раз; Generated/ пересоздаётся отдельно.

Мастер создаёт override только реальных доступных виртуальных методов выбранной базы. Вызов идёт к непосредственному родителю, а не всегда к GameComponent. Для текущих баз ориентиры: Game::AfterInitialize, Game::PreUpdate, Game::TickComponents и GameComponent::Tick. Не генерировать override для невиртуального GameComponent::Update или Game::Initialize. final-методы и final-классы исключаются.

Пример требуемого результата для текущего API:

```cpp
void MyProjectGame::AfterInitialize()
{
    Game::AfterInitialize();
    // Пользовательская инициализация после подготовки базовых ресурсов.
}

void MyProjectGame::TickComponents(float deltaTime)
{
    Game::TickComponents(deltaTime);
    // Пользовательская логика после обновления компонентов.
}

void MyComponent::Tick(float deltaTime)
{
    GameComponent::Tick(deltaTime);
    // Пользовательская логика компонента.
}
```

Для произвольной пользовательской базы информация о доступных hooks поступает из описания семейства/декларации методов; нельзя угадывать сигнатуры сканером. Неизвестные hooks не генерируются. Для pure virtual без реализации нельзя вставлять вызов базы: нужны реализация пользователя или явно поддержанный каркас с диагностикой. Автоматически гарантировать вызов родителя после ручного редактирования C++ невозможно; гарантии касаются генерируемых файлов и поведения тестового каркаса.

### Пользовательский Game и жизненный цикл

Выбранный класс Game должен реально создаваться и во встроенном Play, и при External/запуске из лаунчера. Добавить модульную фабрику игры и передачу контекста проекта; нынешней create(engineContent) у edit API недостаточно для всех проектных настроек. Использовать отдельное согласуемое расширение с fallback для старых модулей, не менять существующие C API таблицы молча.

Редакторский просмотр по умолчанию остаётся без запуска игровой логики. Предлагаемый первый вариант: нейтральный Game владеет редактируемой сценой, выбранный пользовательский Game создаётся для Play и отдельного запуска. UI показывает выбранный класс игры; Game не добавляется как компонент. Если понадобится пользовательское поведение именно в edit preview, оно должно иметь отдельный явный hook/контекст.

Определить порядок: создание → назначение контекста/владельца → загрузка данных сцены → подготовка ресурсов → начало игры → кадры → завершение → уничтожение. Разделить ресурсный AfterInitialize и начало gameplay. У новых hooks начала/окончания, если они вводятся, зафиксировать парность и поведение при частичной инициализации. Конструкторы должны быть пригодны для загрузки документов и не начинать симуляцию.

Исправить встроенный Play: сейчас он напрямую вызывает Scene::Tick и не выполняет Game::PreUpdate/TickComponents. Сделать единую точку симуляции, пригодную для встроенного viewport и отдельного окна, включая headless-тесты. Рендер не должен дополнительно тикать сцену. Edit/Pause не вызывают gameplay; Stop уничтожает игровую копию и возвращает исходную редакторскую сцену.

### Пользовательские данные

Текущий JSON v2 содержит versioned properties, но фактически принимает только Engine.PointLight. Произвольные поля C++ не сохраняются, а Play создаёт копию через SceneSnapshot. Без расширения данных пользовательский класс может появиться в каталоге, но его настройки потеряются после дублирования, Play или открытия.

Предусмотреть модульные сериализаторы данных типа: устойчивый ID, версия схемы, значения, валидация и явные миграции. Один путь используется при сохранении/загрузке, копировании для Play, Undo/Redo и дублировании. Ссылки на другие объекты remap-ятся при копировании; сырые указатели и адреса DLL не сохраняются. Объекты других иерархий сохраняются в документе своего владельца, а не принудительно как пространственные компоненты.

Минимальная цель — сохраняемые данные, объявленные автором типа, и базовый инспектор поддержанных полей. Не обещать автоматическое отображение всех приватных членов C++. Transient-состояние явно исключается. Неизвестный type ID или версия данных не должны молча удаляться/заменяться: отказ с сохранением исходного документа и возможностью открыть его прежней сборкой.

Расширение формата выпускается явно. Старые v1/v2 документы продолжают читаться; запись новых пользовательских блоков требует согласованного формата и поддержки DLL. Нельзя выдавать новый payload за формат, который старый reader гарантированно понимает.

### Сборка и применение изменений

Первая реализация — Build и управляемое повторное открытие сессии, без переноса произвольной живой C++ памяти. Перед закрытием обработать unsaved changes: сохранить / отменить. При остановке Play предупредить о сбросе игрового состояния в рамках действия применения сборки.

Компилятор пишет в отдельный каталог кандидата. Проверка экспортов, версии SDK, type ID и десериализации документов выполняется отдельным проверочным процессом. Неудача не меняет последнюю успешную DLL и активный module path. После проверки закрыть потребителей DLL, завершить процесс/сессию, атомарно переключить описание запуска и открыть проект; при ошибке запуска вернуть предыдущую сборку и сохранённый документ.

Не загружать проверяемый модуль в живой Editor до успешного результата. Изоляция проверочного процесса уменьшает последствия падения кода, но не является sandbox для недоверенного C++.

Источник истины для сборки — выбранный проект и его lock/SDK, не поиск EngineRuntime Debug в дереве движка. Изменение только игрового .cpp не должно перекомпилировать ядро. Повторная сборка без изменений не должна переписывать generated-файлы и менять build ID опубликованного модуля без причины.

## Последовательность реализации

| Этап | Работа | Критерий завершения |
|---|---|---|
| 0 | Зафиксировать контракты проекта, семейств, контекстов, Game lifecycle и данных; добавить образцы | Согласованные схемы и тестовые классы для всех трёх категорий, включая независимую иерархию |
| 1 | Выделить SDK, штатный каталог и поддержку модуля из привязок к репозиторию | Проект в отдельной папке собирается только установленным SDK; исходники движка недоступны |
| 2 | Расширить генератор, каталог и версионированные C-расширения | Компоненты, Game и независимая иерархия обнаруживаются и создаются в правильном контексте |
| 3 | Подключить Game-фабрику и единый lifecycle | Встроенный Play и отдельная игра вызывают пользовательский Game и компоненты в одинаковом порядке |
| 4 | Расширить сохранение и копирование пользовательских данных | Данные всех поддержанных семейств переживают save/load, Play, Undo/Redo и duplicate |
| 5 | Сделать создание проектов, переход к коду и мастер классов | Все пользовательские сценарии создания работают без ручного редактирования движка |
| 6 | Общий список классов и подходящие действия редактора | Видимость, причины запрета создания, выбор Game, размещение компонентов и создание других объектов |
| 7 | Сборка выбранного проекта, проверка кандидата, повторное открытие и откат | Ошибка компиляции/инициализации не разрушает рабочую сборку и документ |
| 8 | Совместимость, упаковка SDK/runtime, документация и полный прогон | Проверенный дистрибутив работает на машине без checkout; готовые игры — без компилятора |

Этапы 1–4 образуют основание до пользовательских мастеров. На этапе 2 адаптер независимой иерархии является обязательным доказательством, а не обещанием будущей универсальности. Этапы удобно поставлять отдельными проверяемыми изменениями; текущую задачу нельзя считать завершённой после одной кнопки «C++».

## План тестирования

Каждая проверка должна использовать отдельный временный проект/engine store. Реестр пользователя и его проекты не изменять. Поведенческие тесты выполняются на собранных DLL, а не только на сравнении текста generated C++.

| ID | Проверка | Наблюдаемый результат |
|---|---|---|
| T01 | Создание без кода без установленного компилятора | Создание, editor, Play и отдельный запуск работают |
| T02 | Создание C++ проекта из SDK, Debug и Release | Генерация, compile/link, загрузка DLL и выполнение родительских/дочерних методов |
| T03 | Нет C++ tools, нужного SDK или правильного CRT/toolset | Точная диагностика; нет переключения на неполную сборку |
| T04 | Добавить код в наполненный проект | Сохраняются сцены, иерархии, примитивы, свет, модели, текстуры и startupScene; контент сравнивается по хешам |
| T05 | Ошибка первой сборки, повторное добавление кода, сбой записи | Прежний проект работает; исходники пользователя не перезаписаны; операция восстанавливается |
| T06 | Путь с пробелами/кириллицей, перенос на другой диск, запуск из другого CWD | Сборка и запуск без абсолютных привязок к машине разработчика |
| T07 | Прямой и косвенный наследник GameComponent, в том числе от собственного родителя | Тип виден; spawn вызывает нужную фабрику; виртуальный Tick выполняется |
| T08 | Абстрактный тип, private/неоднозначное наследование, final-база, недоступный destructor | Создание недоступно либо сборка даёт точную диагностику; нет небезопасного cast |
| T09 | Параметризованный constructor с фабрикой и без неё; throwing/null factory | Создание разрешено только при контракте; ошибка не меняет сцену/владельца |
| T10 | Два Game-наследника; выбор одного и перезапуск | Выбранный Game используется в Play/External/лаунчере; нет двух Game в одной игровой сессии |
| T11 | Независимая иерархия, не наследующая Game/GameComponent | Тип виден и создаётся через адаптер; правильный владелец; уничтожение ровно один раз |
| T12 | Перечисление каталога и открытие списка классов | Счётчики конструкторов равны нулю; одинаковые подписи различаются по ID/namespace |
| T13 | Повторные ID, конфликт со штатным типом, удаление и переименование класса | Сборка/валидация отказывает или применяется явный alias; существующий документ не теряется |
| T14 | Мастер классов: Game, компонент, пользовательская база, другая иерархия | Реальные файлы компилируются; родитель вызывается один раз; невиртуальные/final методы не переопределены |
| T15 | Счётчики lifecycle в edit, Play, Pause, Stop, повторном Play и отдельном runtime | Родитель/потомок в заданном порядке; один Tick за шаг; игровая логика не работает в edit/pause |
| T16 | Исключение в init/start/tick; ошибка viewport; закрытие во время Play | Корректное завершение и очистка; редакторский документ восстановим |
| T17 | Пользовательские значения и ссылки: save/load, duplicate, Play, Undo/Redo | Равенство сохраняемых значений; корректный remap ссылок; игровые изменения не переносятся обратно |
| T18 | Неизвестный тип/версия данных, отсутствующий кодек, неудачная миграция | Нет тихой потери полей; исходные файлы неизменны |
| T19 | Изменить только игровой .cpp и выполнить Build | Меняется поведение DLL; журнал MSBuild подтверждает отсутствие сборки Engine/Editor/Runtime |
| T20 | No-op build, добавление/удаление заголовка, .cpp без ручной правки vcxproj | Каталог актуален; лишняя перекомпиляция отсутствует; новые исходники включены предсказуемо |
| T21 | Ошибка compile/link, несовместимый API, crash/hang проверочного процесса | Последняя успешная DLL и module path сохранены; timeout и диагностика |
| T22 | Применение сборки при unsaved scene, Play, отмене и DLL-lock | Действие отменяемо; нет выгрузки используемого кода; повторное открытие/откат работает |
| T23 | Старые опубликованные DLL и сцены; старый проект без lock | Существующие адаптеры работают; старые фиксированные таблицы C API не изменены |
| T24 | Сборка проекта против другого SDK или конфигурации; обновление копии | Явная проверка совместимости; пользовательская DLL/Source не заменяются шаблоном |
| T25 | Дистрибутив и SDK на чистой машине/в изоляции checkout | C++ проект собирается с tools; готовый проект запускается без tools и без исходников Engine |
| T26 | Qt workflow и D3D viewport | Через реальные кнопки создать класс/объект, сохранить и Play; подтвердить изменение кадра от пользовательского компонента |

Контрольные классы: счётчик вызовов родителя/потомка, компонент с косвенным наследованием, два Game с различимым поведением, независимый RulesObject с собственной базой и адаптером, тип с пользовательскими данными/ссылкой, абстрактная база, тип с throwing constructor и несовместимый модуль. Для данных проверять конкретные значения до/после каждого перехода, для lifetime — счётчики и отсутствие обращений после unload.

Использовать существующие наборы Engine/tests/component-generation, scene-module, edit-session, project-workflow, compatibility и Editor/tests; дополнить новым набором code-projects для внешней сборки и конвертации. Сначала прогонять связанные с этапом проверки; итоговый релизный прогон включает Debug/Release, опубликованные старые DLL, Qt и отдельную проверку пакета. Поддержку v143 и v145 заявлять только после прогона соответствующей матрицы с подходящими SDK-библиотеками.

## Критерии готовности всей задачи

1. Автор создаёт проект без кода, строит сцену, добавляет C++ и продолжает работу с той же сценой.
2. Автор создаёт проект с кодом, изменяет Game и компонент; базовое поведение сохранено, пользовательское выполняется в Play и отдельной игре.
3. Написанные вручную и созданные мастером типы проходят один путь регистрации; редактор не требует изменений для каждого нового класса.
4. Тип из независимой иерархии действительно создаётся и сохраняется через свой адаптер, а не просто отображается названием.
5. Код проекта собирается вне репозитория движка; установленный выпуск и чужие проекты не изменяются.
6. Ошибки сборки, загрузки и миграции не уничтожают исходники, сцены и последнюю рабочую сборку.
7. Старые проекты открываются по прежним контрактам; новый функционал имеет явные версии и проверки.

Автоматический перенос живой C++ памяти при hot reload, полный разбор произвольного C++, визуальное программирование и автоматическая сериализация всех полей не являются требованиями первой реализации. Общий каталог и адаптер независимой иерархии, сохранение объявленных пользовательских данных и управляемая пересборка входят в обязательный объём.

- Edit session: 609 проверок существующих контрактов.
- Code projects: x64 Debug и Release / v145; 25 проверок core после последнего расширения набора. Проверены custom Game, единственный вызов родителя/тика, независимая иерархия, время жизни, данные, формат 3, ошибка схемы и remap ссылки на себя.
- Workflow: Debug — 18 проверок, Release — 17 (до добавления проверки конкурентной операции); создание, конвертация, пути с пробелами/кириллицей, no-op, три семейства, косвенная база, Game selection, ошибки compile/factory/startup и сохранение рабочего пути DLL.
- Frozen compatibility Release: 72 проверки с исходными опубликованными DLL, без пересборки эталонов.

Логи находятся в Engine/build/code-*.log. Проверка на физически чистом компьютере, v143 и создание нового RAR-дистрибутива в этот прогон не входили.
