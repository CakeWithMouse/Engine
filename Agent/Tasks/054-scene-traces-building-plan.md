# 054 — Трассировки сцены и размещение зданий

Статус: план, реализация не начата. Первый потребитель — игра строительства: выбрать участок курсором, показать призрак дома, подтвердить размещение кликом.

## Что есть сейчас

- SceneEditSession::GetSceneApi выполняет unproject курсора из NDC через inverse(view * projection), перебирает объекты и возвращает только ComponentId. Это API редактора, а не удобный игровой запрос.
- GameComponent::RaycastPrimitive пересекает треугольники points/indices и возвращает расстояние через параметр. Для объектов без геометрии используется сфера выделения; её нельзя считать физической поверхностью земли. Визуальный proxy делегирует пересечение модели.
- Input::System передаёт кнопки и относительное движение мыши; для прицеливания нужен согласованный абсолютный курсор внутри игрового viewport.
- Scene уже владеет объектами, ComponentId и отложенным добавлением во время Tick. Отдельная физическая система для первого результата не нужна.

## Этап 1 — луч из курсора и пересечение плоскости

Добавить публичные структуры Ray (origin, нормализованный direction, maxDistance) и TraceHit (ComponentId, worldPosition, worldNormal, distance; при наличии triangleIndex). Для отсутствия попадания возвращать bool/optional, не фиктивный объект с ID 0.

Добавить Game::ScreenPointToRay(viewportPixel) с координатами относительно клиентской области viewport, явной обработкой DPI, выхода курсора за пределы, свёрнутого/нулевого viewport и вырожденной матрицы. Перспектива и ортография используют общий unproject near/far: у ортографии начала лучей разные, направления параллельны. Расстояния — в мировых единицах; origin на near plane документируется.

Ввести получение абсолютной позиции указателя и её валидности через игровой input. Для embedded viewport добавить необязательное версионированное расширение; старые таблицы DLL API не менять. Standalone и editor Play должны выдавать одинаковые координаты. Проверить, что HUD/редактор поглощает клик раньше игрового действия.

Чистая функция IntersectPlane(ray, point, normal) позволяет поставить первый дом на плоскую строительную карту без ожидания полной геометрической системы. Явно обработать параллельность, попадание позади начала и превышение дальности.

Готово, когда один пример строительства показывает точку под курсором в перспективе и ортографии, в editor Play и standalone; resize/DPI/выход курсора не создают ложных попаданий.

## Этап 2 — Scene::LineTraceClosest

Предлагаемый контракт (имена уточнить при реализации):

```cpp
Ray ray;
TraceHit hit;
if (game.ScreenPointToRay(input.GetPointerPosition(), ray) &&
    scene.LineTraceClosest(ray, TraceQuery{TraceLayer::BuildSurface}, hit)) {
    preview.SetPosition(hit.worldPosition);
}
```

TraceQuery содержит маску каналов, игнорируемые ComponentId, максимальную дистанцию, режим простой/точной геометрии и политику обратных граней. Начальные каналы: BuildSurface, PlacementBlocker, Selectable. Запросы не меняют сцену. Игнорируются сам игрок, призрак здания, skybox и служебные объекты. Отрисовка и участие в запросах независимы; служебная сфера picking не должна становиться землёй.

Выделить чистые пересечения ray/plane, ray/AABB, ray/triangle. Начать с линейного перебора по bounds, затем точных треугольников mesh. Корректно учитывать иерархию, неравномерный и отрицательный scale, нормаль через inverse transpose, singular transform, модельный proxy. Не нормализовать преобразованный локальный луч без восстановления мирового расстояния. На равной дистанции использовать стабильное правило по ComponentId.

Для terrain, инстансов и skinned mesh явно определить поддержку: сначала статический terrain/mesh и примитивы; skinned mesh — документированная простая collision-форма, не обещание точного попадания по текущей GPU-позе. Проверить фактические CPU-данные каждого типа mesh, не переносить предположение points/indices на все классы.

Обновить editor picking поверх общего запроса, сохранив отдельный режим выбора камер/света по служебным объёмам. TraceHit не содержит долгоживущих сырых указателей; объект разрешается по ID на момент использования.

Готово, когда луч по двум перекрывающимся поверхностям возвращает ближайшую, фильтры исключают призрак/игрока, нормаль и расстояние корректны при transform и попадание не зависит от порядка обхода контейнера.

## Этап 3 — возможность поставить дом

Одного луча недостаточно: точка на земле ещё не означает, что дом помещается. Для сеточной игры первым решением будет таблица занятости клеток в коде игры. Для свободного размещения добавить Scene::OverlapBox с ориентированным объёмом и PlacementBlocker. Проверять весь footprint, а не только центр; допустимый уклон — по нормалям опорных точек, перепад высоты — по нескольким лучам.

Игровой PlacementController владеет выбранным типом дома, footprint, размером сетки, поворотом, стоимостью и правилами участка. Движок предоставляет запросы, input и spawn; экономика и правила строительства остаются в проекте игры.

Цикл: курсор → луч → поверхность → snap → поворот и опорные точки → проверка занятости/уклона → зелёный или красный призрак → повторная проверка на Pressed → создание через существующее добавление в Scene. Не спавнить по Held и не подтверждать клик поверх UI. Призрак не участвует в trace/overlap, не сохраняется в сцену. При добавлении внутри Tick учесть SceneResult::Deferred; клетку резервировать до следующего подтверждения, а при ошибке откатывать резерв. Отмена по Escape/ПКМ не оставляет объект или занятость.

Готово, когда дом нельзя поставить на дом, вне участка или на недопустимый склон; один клик создаёт один объект; ресурсы списываются только после успешного размещения. Правила сохранения построек проверяются в игровом проекте отдельно от редакторского Undo.

## Этап 4 — отладка и производительность

Добавить DebugDraw луча, точки, нормали и placement-box с временем жизни. Счётчики: запросы/кадр, проверенные bounds/треугольники, длительность. Сначала измерить на целевой строительной карте; только затем добавлять spatial grid/BVH с обновлением при spawn/remove/transform и переимпорте. Не строить полноценный physics solver ради запросов.

LineTraceAll, Sphere/CapsuleSweep и каналы для боя — следующие отдельные задачи при появлении потребителя. Они не блокируют игру строительства.

## Проверки и порядок передачи разработчику

1. Unit: miss/hit, параллельность, старт внутри bounds, границы дальности, нулевой/NaN луч, normal, scale/parent, равные дистанции, masks/ignore, удалённый ID.
2. Camera/input: центр и углы viewport, перспектива/ортография, XY/XZ/YZ, DPI/resize, UI capture, отсутствие игрока, одинаковый результат editor Play/standalone.
3. Integration: ближайший участок, призрак игнорируется, snap/rotate, занятые клетки/overlap, slopes, повторные клики до deferred spawn, отмена, сохранение/загрузка построек.
4. Compatibility: новый SDK и необязательное input-расширение; старый DLL без расширения загружается, неподдерживаемый cursor-query возвращает явный статус. Существующие API не расширяются изменением размера старых таблиц.

Первый полезный результат для разработчика — этап 1 плюс игровой пример сеточного размещения на плоскости. Затем заменить плоскость на LineTraceClosest из этапа 2; правила строительства и UI при этом не переписываются. Этап 3 закрывает корректность свободного размещения, этап 4 — наблюдаемость и масштабирование.
