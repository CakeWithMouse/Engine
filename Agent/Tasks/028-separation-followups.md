## 028-B. Ошибки построения сцены и настройки SunGame

Обработать результат каждого RegisterComponent, сохранять владение через unique_ptr до успешной передачи движку. Вынести массовые константы сцены в SunGameConfig по необходимости. Удалить исторические неиспользуемые настройки после решения. Готово: искусственный отказ регистрации не даёт утечек; параметры соответствуют поведению.

## 028-C. Ресурсы и импорт

Проверить сборку опционального Assimp на машине с vcpkg. Проверить текстуры/модели на путях с кириллицей (HLSL уже использует wide paths, stb/Assimp получают narrow paths). Продумать единый идентификатор ресурса и обновление файла; не вводить полноценный asset pipeline до конкретного сценария. Очистку удалённых файлов из deployed Content при повторной сборке реализовать адресно: сейчас Copy добавляет/обновляет, но не удаляет устаревшие файлы. Готово: воспроизводимые сценарии импорта, Unicode и отсутствующих файлов, определённая политика кэша.

## 028-D. Первая стратегическая сцена и измерения

После отдельного запроса создать простой пример массовых юнитов: камера сверху, выделение группы, команда перемещения. Зафиксировать CPU/GPU время и число draw calls на нескольких размерах сцены и указанной машине. Затем выбирать конкретную оптимизацию: пространственный поиск, пакетное обновление, инстансинг, culling/LOD. Полный ECS, многопоточность, сложная навигация и анимация толп не являются предварительным условием. Готово: воспроизводимый сценарий и таблица измерений до/после одной оптимизации.

## 028-E. Игровая DLL

Текущая граница — статическая Engine.lib и приложение GameExample.exe; изменение игры требует перелинковки exe, но не пересборки неизменённого ядра. Отдельно спроектировать хост и DLL, безопасную остановку вызовов и удаление подписок. Первый результат — перезапуск сцены после пересборки DLL; перенос состояния и произвольных живых C++-объектов — последующие задачи. Это не обещание совместимости текущего C++ API между разными компиляторами.

## 028-F. Минимальный редактор

После 032 продолжать существующий `Editor/EditorModule.vcxproj` → Editor.dll, загружаемый одним EngineRuntime.exe в режиме editor после готовности Engine. Отдельный Editor.exe и наследование от старого Game не использовать. Подробный контракт и этапы — [раздел 8 передачи разработчикам](../../Engine/docs/DEVELOPER-HANDOFF.md#8-внедрение-редактора-согласованный-контракт).

Первый объём: перенос минимальной реальной сцены/графики в управляемый BaseEngine runtime, область просмотра, список объектов и изменение transform. Панели принадлежат Editor; цикл, рендер, владение сценой и безопасное применение команд — Engine. UI рисуется до единственного Present, ввод полей не двигает камеру.

Открытие проекта и редактирование встроенных типов не требуют Game.dll. Игровые типы подключаются отдельным будущим контрактом регистрации, без игрового Start и симуляции. Открытие оболочки для старого проекта не требует предварительно переводить его exe на DLL, но и не загружает автоматически сцену, построенную внутри exe. Текущий ABI содержит только callbacks одной сессии и должен быть явно расширен для модулей типов.

Готово: сцена видна, transform редактируется и сохраняется/загружается, захват ввода, resize и завершение работают; проект со встроенными типами открывается без игровой DLL. Затем отдельно — пользовательские игровые типы и внешний Play через тот же EngineRuntime.exe --mode game. Встроенный Play и hot reload не являются условием первого редактора. Реализация 032 подтверждает только каркас, этот пункт остаётся запланированным.

## 028-G. Время симуляции и изменения сцены

Определить единую паузу игровой симуляции: сейчас Space обнуляет deltaTime обычных компонентов, но PreUpdate и камера продолжают обновляться. Для новой стратегии явно выбрать масштаб времени (историческое значение Engine — 7.8). Добавить очередь создания/удаления объектов с применением между обходами; определить порядок общих игровых систем. Готово: пауза останавливает игровые правила, интерфейс остаётся отзывчивым, создание/удаление по запросу из Tick не нарушает обход и владение. Фиксированный шаг добавлять отдельной проверяемой правкой при необходимости; сравнить движение на разных FPS и ограничить догоняющие шаги.
