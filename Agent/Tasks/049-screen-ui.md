# 037. Экранный интерфейс и HUD в сцене техники

## Зачем

Интерфейса, который рисует движок, в проекте не было вообще — ни в одной ветке. Строка «Deferred | FPS…», которую видно на скриншотах, это заголовок окна, его рисует Windows. Всё, что называлось «классами UI», относится к редактору на Qt (`Editor/MainWindow`, `FileBrowser`, `ViewportWidget`) и внутри игры не работает.

## Что сделано

### Слой UI в движке

- `UIElement` и три наследника: `UIPanel` (заливка с рамкой), `UILabel` (строка), `UIBar` (значение 0..1).
- `UIComponent` — компонент сцены, владеет элементами, собирает вершины и рисует.
- `FontAtlas` — шрифт, растеризованный один раз в текстуру.
- `Engine/Content/Shaders/UI.hlsl`.

Разбор решений — в [UI.md](../../Engine/docs/UI.md). Коротко три, которые стоило обосновать:

**Один draw call.** В углу атласа лежит сплошной белый квадрат; панели и полосы берут его текселем, буквы — свои ячейки. Один материал, один буфер, один вызов на компонент независимо от числа элементов.

**Свой input layout не понадобился.** Пиксельная координата кладётся в `POSITION.xy`, координата атласа в `POSITION.zw`, цвет в `COLOR` — это ровно существующий `VertexFormat::Primitive`.

**Шрифт через GDI.** `CreateFontW` + `TextOutW` в DIB, результат загружается текстурой. Даёт хинтинг, сглаживание и кириллицу без шрифтового файла в репозитории и без библиотеки раскладки: 161 глиф при 18 px умещается в атлас 512×128.

### Проход в кадре

`Game::RenderUI()` добавлен последним в обоих путях — forward и deferred. Компонент помечает себя `IsScreenSpaceUI()`, остальные проходы его пропускают: интерфейс не отбрасывает тень, не отсекается пирамидой видимости, не попадает в G-буфер. Состояния (альфа-смешение, выключенная глубина) компонент ставит сам и после прохода движок их возвращает.

### HUD в Battle

Две панели: слева время кадра, FPS, число вызовов отрисовки, отсечённые экземпляры и полоса загрузки кадра относительно бюджета 60 FPS; справа распределение техники по уровням детализации теми же цветами, что у раскраски F6. Время кадра сглажено скользящим средним, иначе цифру невозможно прочитать.

**F7** убирает панели, `--no-hud` не создаёт их. Цена: один draw call, 19 → 20 в сцене по умолчанию.

## Чёрный кадр: два дефекта в этом же слое

Первая рабочая версия давала полностью чёрный кадр в deferred (в forward — нет). Разбор делался не по скриншотам, а новым `Game::DumpFrame`: кадр читается из back buffer и пишется в BMP перед `Present`, ключ сцены `--dump-frame <файл>`. Без него этот дефект пришлось бы ловить глазами.

Матрица замеров яркости дампа показала виновника сразу:

| Запуск | Яркость кадра |
|---|---|
| обычный | **0** |
| `--no-hud` | 53 714 |
| `--no-shadows` | **0** |
| `--no-hud --no-shadows` | 58 216 |
| `--forward` | 53 612 |

Дальше бисекция: без самого вызова `Draw` кадр нормальный — значит дело не в утечке состояний, а в отрисовке. Тест «вернуть из пиксельного шейдера красный» не дал красного, хотя развёрнутая копия шейдера содержала правку. Отсюда вывод: рисовалось **не моим шейдером**.

**Дефект 1: компонент не ставил свои шейдеры в контекст.** `Game::BindComponentShaders` только записывает пару шейдеров в компонент; загрузка их в контекст — дело самого компонента (`VSSetShader`/`PSSetShader`), как это делает `InstancedMeshComponent`. UI этого не делал и рисовался материалом, оставшимся от предыдущего прохода: вершины в пиксельных координатах уезжали через 3D-преобразование и закрывали кадр.

**Дефект 2: регистрация затирала имена шейдеров.** `RegisterComponent` безусловно вызывал `SetShaderNames(VShaderName, PShaderName)`, поэтому регистрация с пустыми именами стирала путь, выставленный конструктором компонента, и `UI.hlsl` не компилировался вовсе. Теперь пустые имена означают «оставить то, что компонент выбрал сам»: подменять материал молча нельзя, а для экранного компонента дефолтный 3D-материал — не материал.

Попутно `GetDrawnInstancesForLod` научился отвечать за спрайтовый уровень: `SelectLod` его возвращает, а счётчик по номеру уровня для него молча отдавал ноль.

## Попутно: VFS не работал на кириллическом пути

После слияния ни игры, ни тесты не стартовали: движок не находил собственные шейдеры.

```
[VfsRead] Failed to read bytes for path 'C:/Учёба/.../EngineContent/Shaders/RotatedFigure.hlsl'
   (virtual: '/C:/Учёба/...'): Virtual file not found (unmounted root)
```

`Engine/Source/Resources/VfsRead.cpp` строил `std::filesystem::path` из UTF-8 строки узким конструктором, который читает её в системной кодовой странице. На пути `C:\Учёба\…` имя ломается, `exists()` возвращает false, и путь уходит в последнюю ветку «считать виртуальным» — к несуществующему корню. На ASCII-пути это незаметно.

Исправлено на `std::filesystem::u8path`, как уже сделано в `VirtualFileSystem.cpp`, `Base.cpp` и `FBXComponent.cpp`.

Результат: тесты 12/20 → 16/20, игры запускаются.

## Попутно: не работал запуск

`Game/Start.cmd` ничего не запускал. Цепочка: `Start.cmd` → `Start-Launcher.ps1` → `build.ps1` с целью **All** → сборка падает на Qt-редакторе → лаунчер не стартует никогда. Тем же обрывом не собирался `EngineRuntime.exe`, из-за чего четыре теста движка и весь набор `run-runtime.ps1` падали.

Qt — необязательная зависимость, ровно как Assimp, и её отсутствие не должно останавливать сборку всего остального. `build.ps1` теперь проверяет `QTDIR` и `Editor/ThirdParty/Qt6.7/bin/moc.exe`; если Qt нет, печатает об этом и собирает проекты по одному в порядке зависимостей. Редактор достижим по ссылкам из `EngineRuntime`, а лаунчер — из runtime, поэтому эти два собираются с `BuildProjectReferences=false`, после того как всё нужное уже готово (`-SkipProjectReferences` в `Invoke-MSBuild.ps1`).

В `run-runtime.ps1` проверки редактора помечаются пропущенными, когда `Editor.dll` не собран — так же, как `run-games.ps1` сообщает про Katamari без Assimp.

| EngineTests | 12/20 | **20/20** |
| `run-runtime.ps1` | падал на сборке | **15 проверок**, проверки редактора пропущены |

Редактор по-прежнему требует Qt 6 — это его зависимость, а не дефект.

## Ограничения

- Слой только выводит: ввода, наведения и фокуса нет.
- Одна строка на `UILabel`, без переноса и выравнивания по центру.
- Один шрифт на компонент.
- Нет обрезки по родителю: вылезший за панель элемент рисуется поверх.
- Атлас строится на первом кадре; смена размера шрифта перестраивает его целиком.
