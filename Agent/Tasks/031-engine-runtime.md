**Цель:** сделать `BaseEngine` реальным владельцем старта, главного цикла и остановки приложений. Игры и будущий редактор должны задавать свою сцену и поведение через публичный API Engine. Это следующий этап после текущего устройства, где эти обязанности пока находятся в `Game`.

## Сейчас

- `Engine.lib` содержит класс `Game`, который создаёт окно/D3D11 и владеет `Run`, обновлением кадров, рендером, `Present` и освобождением ресурсов.
- `Game/<Name>/<Name>.exe` создаёт производный `Game`, вызывает `Initialize()`, строит сцену, затем блокирующий `StartGame()`.
- `BaseEngine` находится в Engine и включён в сборку, но его `Initialize`, `StartUp`, `Play`, `IsPlaying` и `Stop` не реализованы.
- `BaseResources::Initialize`/`DeInitialize` также не реализованы; шейдерные пути вычисляются при создании полей, поэтому корень EngineContent нужно задать раньше.
- `BaseGameConfig` хранит параметры рендера и света, но игры не обязаны использовать эту конфигурацию.

## План

- [ ] Описать один runtime и его владение: кто создаёт/уничтожает окно, графическое устройство, ресурсы и игровую сессию. Не запускать два вложенных цикла.
- [ ] Реализовать контракты и состояния `BaseResources` и `BaseEngine`: повторный/ошибочный запуск, штатная остановка, код завершения, очистка после частичной инициализации.
- [ ] Установить public API runtime-сессии: Engine владеет кадром, игра предоставляет создание сцены и игровые точки расширения через стабильные C++-объекты той же сборки.
- [ ] Перенести сначала одну игру (BasicExamples) с `Game::Initialize/StartGame` на новый API, не меняя её две сцены и поведение.
- [ ] После проверки перенести Pong и SunGame. Отдельно согласовать общие настройки `BaseGameConfig` с игровыми настройками SunGame и Pong.
- [ ] Удалить старые пути запуска/дублирующиеся реализации только после эквивалентной проверки всех доступных игр. Сохранить `GameComponent`, рендер и игровые классы в подходящих публичных/внутренних каталогах Engine.
- [ ] Подключить будущий Editor как ещё одного клиента runtime. Инициализировать UI после создания graphics device; обновлять его внутри единственного цикла, рисовать overlay до Present; разделить ввод UI и камеры.

## Критерии готовности

- Engine один раз и предсказуемо создаёт runtime и один главный цикл; отказ на каждом этапе сообщает ошибку и освобождает уже созданные ресурсы.
- Игра определяет сцену, а не вызывает сама набор низкоуровневых стадий запуска ядра.
- Несколько последовательных запусков/остановок в рамках определённого контракта не оставляют окно, устройства или объекты сцены.
- BasicExamples (обе сцены), Pong и SunGame сохраняют прежнее поведение; EngineTests остаются зелёными в Debug и Release.
- Игра и Editor зависят от публичного API Engine. Engine не ссылается на код или названия конкретных приложений.
- `Start.cmd`, EngineLauncher и прямой запуск игр продолжают работать; в коде нет второго вложенного цикла и DLL hot reload не является условием этой задачи.
- Документация обновлена после переноса; каждая часть чеклиста отмечается выполненной только после проверки.

**Риск:** текущий `Game` одновременно является приложением и местом размещения крупного runtime-кода. Не делать большой механический перенос до фиксации контрактов и успешной проверки одного приложения.
