# 032. Один EngineRuntime.exe: игра и режим редактирования

**Статус:** каркас реализован; автоматические проверки Debug/Release пройдены. Визуальная приёмка кнопок остаётся ручной (native UI недоступен в сессии).
**Дата:** 2026-10-04.
**Объём:** работающий каркас запуска с настоящими DLL и заглушками подсистем.

## Результат для пользователя

Пользователь открывает существующий EngineLauncher, выбирает тестовый игровой проект и нажимает одну из двух кнопок:

- **Играть** — запускается EngineRuntime.exe, сначала инициализируется Engine, затем запускается игровая сессия из Game.dll.
- **Редактировать** — запускается тот же EngineRuntime.exe, сначала инициализируется тот же Engine, затем открывается тот же проект через Editor.dll. Игровая симуляция автоматически не стартует.

На этом этапе «открывается» означает видимый консольный журнал и работающий цикл заглушек. Графической сцены, панелей и настоящего редактирования пока нет. Реальными должны быть сборка, запуск из лаунчера, чтение проекта, загрузка DLL, вызовы жизненного цикла и очистка.

## Принятое архитектурное решение

```text
EngineLauncher.exe — выбор проекта и режима
  └─ EngineRuntime.exe --project <path> --mode game|editor
       ├─ BaseEngine + BaseResources: обязательная инициализация
       └─ после готовности Engine:
            ├─ game   → Game.dll → игровая сессия
            └─ editor → Editor.dll → сессия редактирования проекта
```

Лаунчер и Runtime — разные процессы. Внутри каждого запуска Runtime один экземпляр Engine, один основной цикл и загруженный модуль выбранного режима в том же процессе. Editor.exe и Game.exe для нового пути не создаются. Одновременный запуск обоих режимов означает два независимых процесса Runtime; общая память между ними не требуется.

Общая реализация движка остаётся библиотекой Engine.lib, код которой использует EngineRuntime.exe. Это не отдельный процесс. Game.dll и Editor.dll не линкуются с реализацией Engine ради доступа к runtime; используют небольшой общий контракт и разрешённые callbacks host.

Эта задача уточняет первый этап [031](031-engine-runtime.md). Полный перенос старого Game, рендера и примеров из 031 остаётся последующей работой. Варианты отдельного Editor.exe из прежней документации не являются выбранной целью. Общая история разделения сохраняется в [027](027-engine-game-separation-roadmap.md).

## Ограничения

- Сохранить BaseEngine, BaseResources, BaseGameConfig. Наполнить их минимальной реализацией для нового сценария; не создавать дублирующий набор владельцев с той же ролью.
- Текущий API этих классов — заготовка. Допустимы минимальные изменения сигнатур, нужные для владения и состояний; записать причину. Не реализовывать неоднозначные методы вслепую.
- Engine инициализируется независимо от игровой сессии. Editor работает без запущенной игры.
- Игра и редактор не наследуются от BaseEngine, не получают доступ к его внутренней инициализации, очистке и главному циклу.
- Не подключать старый Game с Direct3D, сценой и рендером в новый каркас. Его существующий путь запуска сохраняется.
- Не переносить сейчас SunGame, Pong, BasicExamples и Katamari на DLL. Создать отдельный минимальный тестовый игровой проект.
- Не делать UI редактора, сериализацию настоящей сцены, ECS, hot reload, встроенный Play или универсальную систему плагинов.
- Сохранить C++17, Windows и действующий способ сборки. Не устанавливать зависимости для заглушек без необходимости.
- Не добавлять задержки ради имитации работы. Ограниченный прогон завершается по числу шагов, обычный запуск имеет понятный способ выхода без бесконтрольного busy loop.

## Порядок запуска и остановки

1. Host разбирает аргументы, читает описание проекта, проверяет выбранный режим и пути.
2. BaseEngine начинает инициализацию.
3. BaseResources и обязательные службы имитируют подготовку и переходят в состояние готовности.
4. Engine фиксирует готовность; до этого модули игры/редактора не загружаются и их callbacks не вызываются.
5. Host загружает DLL выбранного режима, проверяет экспортируемые функции, версию и тип модуля.
6. Через функцию DLL создаётся сессия.
7. Сессия получает ограниченный контекст и описание выбранного проекта.
8. Вызывается старт сессии. В game это начало тестовой игры; в editor это открытие проекта редактором.
9. Engine выполняет единственный цикл: callback выбранного режима → внутреннее обновление-заглушка → рендер-заглушка. Для editor предусмотреть обозначенную фазу интерфейса перед условным завершением кадра, без реализации графики.
10. По лимиту кадров или запросу выхода прекращаются обновления.
11. У успешно стартовавшей сессии вызывается Stop; затем сессия уничтожается функцией своей DLL.
12. Удаляются все сохранённые ссылки на функции/данные модуля и выгружается DLL.
13. Освобождаются ресурсы Engine и завершается процесс.

При ошибке выполняется очистка только успешно созданных частей в обратном порядке. Неуспешно стартовавшая, но созданная сессия уничтожается без обычного Stop; её Destroy должен освобождать и частично подготовленное состояние. После ошибки нет обновлений. У каждого этапа понятное сообщение; ошибки возвращают ненулевой exit code.

Первый контракт допускает одну сессию на экземпляр BaseEngine. Повторный запуск на том же экземпляре явно отклоняется, если не реализован и не проверен; повторный Stop безопасен. Не смешивать остановку игровой сессии с готовностью ядра.

## Проект и интерфейс модулей

Минимальный Project.json задаёт имя проекта, путь к Game.dll и каталог игрового контента. Пути проекта разрешаются относительно Project.json. Путь к установленной Editor.dll задаётся размещением host относительно EngineRuntime.exe, а не самой игрой. EngineContent также принадлежит установке host. Не полагаться на текущую рабочую директорию.

Для каркаса editor получает имя/путь того же проекта, но не загружает Game.dll. Возможность объявлять игровые типы без старта симуляции — будущая работа, не условие этой задачи.

Контракт DLL: небольшой общий заголовок, экспортируемые C-функции, явная версия и тип модуля, непрозрачная сессия. Не передавать STL-контейнеры и исключения через границу DLL. Зафиксировать соглашение вызова, срок жизни строк и указателей; создавать и уничтожать объект на одной стороне DLL. Ловить внутренние исключения до выхода через ABI и возвращать понятную ошибку. Контекст содержит только необходимые возможности, например журнал и запрос выхода, без указателя на весь Engine.
