# Отзыв по PainEngine — стратегический эпизод

## Что получилось

- Штатное создание C++ проекта, приватная сборка и активация Game.dll понятны; проектный Build.ps1 работает с явным Runtime SDK.
- Публичные Game, Character, AiCharacter, CubeComponent, UIComponent и Input APIs достаточны, чтобы вручную собрать небольшой тактический эпизод.
- FSM на `Ai::MachineBuilder` быстро дал цикл патруля, ожидания и погони. HUD с активным состоянием сделал переход понятным без отдельного debugger окна.
- Командлет `project.input` с настоящим Play/focus/key/frame и снимком D3D удобен для короткой воспроизводимой проверки; снимок `PAINENGINE_D3D_SCREENSHOT` в этом сценарии показывает сам D3D viewport. Размеры viewport можно менять и проверять.

## Главные затруднения

1. **Высокий приоритет — неявная регистрация выбранного Game класса.** Если C++ проект теряет `ENGINE_GAME`, `SelectProjectGame` молча создаёт базовый `Game`; проект всё равно стартует и обновляется, exit 0, но игровой код не выполняется. `Content/ProjectGame.txt` заставляет ошибку выбора проявиться, но проекту стоит сделать отсутствие GameTypeCatalog явной ошибкой при намеренном C++ режиме.
2. **Высокий приоритет — физическая плотность и масса.** Код передаёт `density=12` в динамический ящик. При импульсе 150 ожидается заметное перемещение, достаточное для ворот; фактически после 60 кадров смещение всего 0.021 м. Координатор локализует дефект передачи плотности в Jolt; до исправления победный путь физикой заблокирован. Игровая сила не была искусственно увеличена.
3. **Средний приоритет — отдельные пути запуска не идентичны.** Game DLL создаёт эту сцену процедурно в `ProjectGame`; стартовая JSON сцена нужна для Editor. При первом запуске `project.input` зафиксировал шаблонную сцену, пока не восстановили выбор Game класса и не сделали общую инициализацию. Для первой игры пришлось вручную изучать `SceneModule`/`GameEditModule` lifecycle.
4. **Низкий приоритет — разные точки захвата кадров.** Переменная `PAINENGINE_D3D_SCREENSHOT` отсутствует в обычном standalone loop и существует на `RenderViewportFrame`; это ограничение диагностического hook, не отказ рендера. Для этой работы я вызвал `project.input`, который способен дать D3D снимок и размеры настоящего viewport.
5. **Средний приоритет — физический импульс в первом кадре.** Game components создают Jolt body после первого шага симуляции. Я буферизовал E до `HasPhysicsBody()`, чтобы первый короткий тап не терялся; это игровая сторона инициализации. После применения плотности проверить, что у тела ожидаемая масса и импульс.

## Предложения с игровой причиной

- При выборе C++ Game явно проверять каталог и сообщать, когда проект будет запущен базовой игрой: иначе дизайнер получает пустой игровой цикл и считает свой модуль подключённым.
- В публичной диагностике или HUD проекта показывать наличие rigid body, массу/плотность и скорость динамического тела; автор стратегии сможет сразу отличить слабый импульс от тела, которое ещё не создано.
- В документации кратко сопоставить `project.input` с реальным Game DLL Play: какая сцена копируется, когда вызываются `AfterInitialize`, `PreUpdate`, `InitializeGameplay`, и какой именно Game factory создаёт играемый экземпляр.

Впечатление от масштаба: для одного коридора API понятен и даёт настоящую логику. Заметное препятствие не объём кода, а тихое падение на базовый класс и отсутствие диагностируемого физического эффекта. Проверка победы ожидает обновления SDK и ещё не завершена.

## Обновление по итоговому игровому проходу

- Фикс SDK `STRATEGY-003` подтвердил причинность: на исходных настройках и том же E-вводе ящик изменился с x=0 до -2.22254 м вместо -0.0209861 м; порог прохода открыт.
- Первый длинный проход обнаружил отскок ящика обратно через ворота. Это был игровой баланс/геометрия. Добавлен физический стопор с restitution 0 вместе с restitution 0 у контейнера; ящик теперь естественно останавливается на x=-1.80638, и игрок успевает пройти.
- Полный clear→win в настоящем Play: боец z=9.312, `won=1`, `lost=0`, охранник в FSM Chase; D3D кадр после победы показывает сцену и HUD.
- Исходный ZIP распакован в чистую папку, собран на текущем Runtime и повторил победу. Архив не содержит скомпилированного SDK/модуля.
- Ранние ошибки в прототипе: отсутствовавшая `ENGINE_GAME` регистрация, один ошибочный C++ заголовок, lifecycle bootstrap только в игровом цикле и первые тёмные кадры. Всё исправлено на уровне проекта; ранние логи оставлены с явными пояснениями, они не используются как финальные pass.

## UX-наблюдения

- При пустом `GameTypeCatalog` проект мог тихо запуститься как базовый `Game`; явный `Content/ProjectGame.txt` помогает получить ранний отказ при потерянной регистрации.
- `AfterInitialize`/процедурная генерация, вызываемая там, не гарантировала карту при Editor Play. Общий bootstrap в `PreUpdate` работает в проверенном сценарии; для редакторского проектирования сцены нужен обычный сохранённый scene workflow.
- Действия клавиш и кадров через `project.input` дали надёжный способ повторить пользовательский Play и получить D3D доказательства. Обычный standalone Run не активировал этот viewport screenshot hook.
- Для физического результата полезно сверять размер/массу и плотность Jolt: первоначальный малый сдвиг оказался дефектом handoff density, который координатор подтвердил и исправил в Engine, а не поводом завышать импульс в игре.
