# Отзыв — уставший автор 2D бомбардировки

Устал, но шаблонный путь не развалился: CLI создал проект, включение SDK дало понятную Source-структуру, повторная сборка активировала новую DLL и smoke три кадра проходил как в game, так и в editor mode. Ошибка C++ оказалась моей опечаткой, лог её показал; линковочная ошибка с MSPDB140.DLL ушла вне sandbox. Хорошо, что это не выглядело как «проект сломан» после первой сборки.

Самый полезный рабочий цикл был короткий: простая сцена → Play → реальные `HIT unit id=... trace=Hit` → Stop → исправление прицеливания. Ошибку z-координаты я сначала сам и создал; лог промахов показал где именно. Ортографическая XZ камера, `Scene::Raycast`, фильтр `channels`, ignore списка бомбы и trace statistics доступны в публичном API. Физики и автоматических столкновений нет: для этой маленькой игры это надо явно написать. Для уставшего гейм-дизайнера это уже много кода на самое простое попадание.

HUD через `UIComponent` добавляется без разметочного файла, панель держит фиксированную ширину и текст можно менять по имени. Пришлось увеличить её до 460 пикселей, иначе конец строки обрезался. Сохранённый frame dump стал полезнее текстового smoke: сразу видно камеру, свет, один пол и попадание с искрами. Изменение viewport/resize и реакцию HUD на изменение размера отдельно UI-персоны не проверил.

`InstancedMeshComponent` собрал три уровня и счетчик показал 11 из 13 нарисованных. С расстоянием выбранного ортографического кадра все видимые экземпляры оказались в LOD2 — понять переключения по одной игре сложно; нужен простой индикатор расстояния/LOD прямо в UI. Упрощение процедурного куба не уменьшило 12 треугольников и честно оставило это в логе. Default mesh validation ругнулась, что центрированный куб не стоит pivot-ом на земле; это разумно для vehicle asset, но для случайного игрового примитива нужно менять профиль. Валидация полезна только когда автору понятно, какой профиль он проверяет.

GPU sparks создались после попадания и видны на отдельном кадре, но глубинное столкновение/сортировку я настроил, а не проверил независимым сценарием отскока. Клавишу B и W/A/S/D подключил к Input API и controller, однако фактический ввод координатором в UI не подтверждён. Это надо оставить непроверенным, а не записывать как победу.

`GameSubsystem` позволил получить session данные, сцено-жизненный цикл и ticking; новый механизм хорошо подходит для счётчика раунда. GameSettings API дал прочитать значения после установки, но кадр-статистики в обычном `PreUpdate` были нулевыми: текущий игровой код не имеет удобного момента после рендера. Предлагаю документировать момент их обновления или дать безопасный post-frame callback.

Приоритетные пожелания:

1. Добавить короткий пример `Raycast` с движущейся целью, каналом, ignore и понятным статусом; реальная причина — написать простое попадание сейчас означало вручную синхронизировать движение и луч.
2. Показать Current LOD/Drawn/Culled рядом с кадром в игре; реальная причина — по сцене не видно, почему 2 из 13 instances исчезли и какой LOD выбрался.
3. Уточнить, в какой фазе доступны `GetFrameStats`; real-time счётчики хотелось бы читать без собственной render интеграции.
4. Показать скорость/клавиши CharacterController в проектном примере; код привязки B сработает только если контекст/фокус действительно получает event.

Ортографика, trace masks, component primitives, procedural scene data, builtin HUD, subsystem, settings, GPU particles, instances и diagnostics исследованы небольшими порциями. Не проверял SkeletalMesh/клипы из-за отсутствия подходящего ассета, направленное солнце и тени не нужны этой плоской сцене, Forward/Deferred не сравнивал, а UI вводом клавиатуры отдельно не управлял.

### Дополнительные проверки

В side copy проверил настоящий переход `GameSession` между двумя Scene: subsystem instance и данные пережили закрытие первой и готовность второй. Это полезная часть API, но пример потребовал отдельный CPU helper; явного готового метода «сменить сцену» в игровом Game не нашёл.

Forward, Deferred и Custom реально запускались. Deferred корректно собрал G-buffer и lighting shaders; Debug overlay визуально выводит 4 панели. Базовый Custom fallback выглядит/работает как Forward, а для своего рендерера нужно унаследовать Game и override Draw. VSync/AA/settings значения доступны в одной сессии; смена настроек не сохраняется между проектными запусками.

Host VFS подтверждён в проектном адаптере и через доступный Game bridge: /Game scene разрешён/прочитан. Напрямую вызвать getService из Game нельзя: host context остаётся внутри сгенерированного модуля, в игровом public API нет общего GetCapabilities. Skeletal loader реально получил путь к CesiumMan.glb, но конфигурация ответила `Assimp not enabled`; импорт и клип заблокированы без пересборки релиза с Assimp.

SDK-проверки копии оказались понятными: мастер сгенерировал родительские вызовы, плохая сборка не заменила исправную DLL, исправление восстановило новый кандидат. Это снизило нервозность после исходной линковочной ошибки — при ошибке кода можно не бояться потерять последний рабочий модуль.

Живое изменение настроек подтвердил одним runtime запуском: Forward → Deferred/G-buffer → Custom, вместе с переключением AA и VSync, кадры продолжили рисоваться без перезапуска. Это полезнее, чем статическое значение в constructor. Оставлю пожелание добавить короткий игровой пример такой смены рендера: в API видна возможность, но у начинающего нет очевидного места/сценария для проверки.

### Редакторский отзыв (диагностика, без своего repro)

В стеке аварии Ctrl+Alt+R видна цепочка от QAction/QMenu activation прямо в глобальный `QWidget::setEnabled(false)`, после чего рекурсивная смена enabled проходит через `QMenu::changeEvent` и падает в `QAction::setEnabled`. Похоже на reentrancy активного меню; частичный stack scan не доказывает причину. После переноса тяжёлого действия на следующий event turn нужно всё равно не блокировать целиком главное окно: безопаснее поставить busy flag, затем отключить только scene панели и действия через уже существующий refresh/guard. Повторный запуск сценария нужен для подтверждения.


## Финальные наблюдения координатора

Итог координатора: финальная DLL в standalone game показала повторные попадания и вспышки; на B в логе появился input B: request bomb drop. W/D короткими нажатиями не изменили позицию; удержание остаётся непроверенным. Кадр первого попадания визуально проверен.
