# Градосимулятор: потребности и план следующей итерации

Обновление после обсуждения: CLI-диагностика и документация реализованы, 16/16 сценариев проходят; [результаты](../../2026-11-04-launcher-cli/report.md). Property Inspector, Raycast и подтверждение спавна уже были в движке. Игровое строительство и согласованность экономики остаются задачами примера игры, не подтверждёнными недостатками Engine. [SaveGame](../../../../Engine/docs/SAVEGAME-DESIGN.md) спроектирован отдельно, пока не реализован. Ниже сохранён исходный анализ и его последовательность.

Актуальность: 2026-11-04, после исправлений и установки PainEngine 2026.11.04.1. Персона №2 — Curious City: дома, спавн и экономика. Персона №1 с машинками рассматривается отдельно. Это анализ и план, не отчёт о реализации перечисленных ниже возможностей.

## Основание и фактический результат

Первичные источники: [отзыв автора](feedback.md), [дневник](diary.md), [проверки](evidence.json), [архив исходников проекта](../reports/sideprobes/curious-city-final.zip). Уточнения: [координатор](../coordinator-evidence.json), [исправления BUG001–008](../fixes/report.md), [Assimp](../../2026-11-04-2026.11.04.0-assimp/report.md), [Blender](../../2026-11-04-2026.11.04.1-blend/report.md).

Автор уже собрал на существующих API три дома: начальные 500 уменьшаются до 200, доход составляет 30 в секунду; HUD показывает баланс/доход/полосу, кнопка приостанавливает и возобновляет доход. Клик выбирает дом через RaycastCursor, параметры компонента сериализуются, GameSubsystem сохраняется между сценами GameSession, VFS читает /Game, экспортированная игра запускается. Следовательно, новая универсальная «подсистема экономики движка» для его текущей задачи не нужна.

Сверка с финальными исходниками важна: сейчас дома создаются автоматически в OnSceneReady. Клик только выбирает существующий дом. Покупка нового дома игроком, предпросмотр размещения и рост города в ходе игры ещё не реализованы. Это следующий игровой этап, а не уже работающий интерфейс строительства.

## Что ему конкретно нужно

**Прямо сказано автором:** понятное объяснение требования новой папки; понятный пример передачи владения AddComponent. Автор отдельно отмечает полезность диагностического журнала. Пожелание видимого баланса закрыто уже работающим HUD.

**Вывод анализа по его цели:** короткий надёжный путь от новой игровой идеи до видимого результата: создать C++ проект → настроить дом/цену/доход → поставить дом → увидеть списание денег и новый доход → сохранить и повторить. Для гейм-дизайнера цена этого пути определяется количеством ручных действий и ошибок C++, а не количеством новых систем движка.

Пример владения уже существует: [ReferenceExamples.cpp, AddCube](../../../../Engine/docs/api-reference/examples/ReferenceExamples.cpp), описание Ok/Deferred и владения есть в [API Reference source](../../../../Engine/docs/api-reference/content.mjs) и [Scene.h](../../../../Engine/Include/Engine/Scene/Scene.h). Поэтому следует улучшить обнаружимость и добавить контекст дома, а не публиковать второй противоречащий справочник.

| Потребность | Минимальное изменение | Владелец | Приоритет / происхождение |
|---|---|---|---|
| Понятный старт проекта и объяснимые отказы | --help, UTF-8 stderr, примеры нового пути, Create → Enable; видимый лог сборки | Launcher / документация | P1, прямое затруднение |
| Спавн без ловушек владения | Один компилируемый пример дома: настройка Derived до передачи, базовый unique_ptr, Ok/Deferred/ошибка, разрешение ID после границы обновления | SDK-пример / документация | P1, прямое затруднение |
| Цена/доход меняются без редактирования C++ | Свойства игровых HouseDefinition/CityRules через существующие property macros и Inspector | Игровой пример | P1, вывод анализа |
| Реальное строительство вместо стартового спавна | Выбор дома, ghost preview, клетка/занятость, подтверждение/отмена, проверка денег, результат в HUD | Игровой пример на существующих Input/Trace/Scene API | P1 после основы, вывод анализа |
| Одна операция покупки меняет согласованное состояние | Списание только после принятого спавна; неуспех ничего не меняет; доход зависит от принятых домов | Игровая экономика | P1, вывод по коду |
| Понятный доступ к моделям | Информация Assimp/Blender и версии закреплённого runtime до импорта | Editor/Launcher | P2, вывод по старому отказу |
| Проверяемый HUD и ввод | Маленький пример Balance → Label, Income → Bar, Pause → Button; нет двойных подписок после Play/Stop/Reload | Игровой пример / тесты | P2, вывод; API уже есть |
| Возврат к построенному городу | Сначала определить сохранение игрового состояния отдельно от Save сцены и recovery редактора | Игровой пример; минимальная поддержка Engine только при найденном пробеле API | P2, предложение аналитика, автор прямо не требовал |

Дополнительный риск обнаружен чтением игрового кода, **не воспроизведён как Engine-баг**: CityEconomySubsystem заранее задаёт houses=3 и списывает всю сумму, а при неуспешном AddComponent лишь продолжает цикл. Значит, при отказе спавна счётчик/доход потенциально разойдутся со сценой. maxHouses в CityRules пока служит демонстрацией сериализации и журналирования, а не ограничением покупки. Исправлять это следует при реализации настоящей игровой операции покупки, с отрицательным тестом.

## План реализации

### 1. Закрыть неопределённости и улучшить диагностику старта

Сначала четыре небольшие задачи: (а) диагностировать существующий каталог и неизвестный CLI-флаг, (б) показать Create → Enable в --help, (в) повторить удержание ввода и потерю фокуса на Curious City, (г) актуальные Save/Reopen и recovery на закрываемой копии. Сведения о версиях host/VFS брать из штатных тестов, не добавлять обход в игру.

Готовность: успешное создание C++ проекта; понятный ненулевой отказ без изменения существующих файлов; удержание даёт движение, key-up/потеря фокуса его прекращают; сохранённая высота дома восстанавливается, recovery возвращает несохранённое изменение. Если сценарий не проходит — сначала отдельный воспроизводимый дефект и исправление.

### 2. Подготовить минимальный пример дома и экономики

В игровом проекте выделить параметры стоимости/дохода/лимита и одну операцию TryBuildHouse. Использовать текущий GameSubsystem, компоненты и property macros. Сначала документировать существующую передачу владения; дополнительный typed overload рассматривать только если пример не решает повторяющееся затруднение, сохраняя ownership при отказе.

Готовность: настраиваемые параметры видны в Inspector, Save/Open и Undo/Redo сохраняют их; пример компилируется с поставляемым SDK; Ok/Deferred списывают цену ровно один раз, отказ не меняет деньги/число домов. Доход считается по фактическому принятому состоянию города.

### 3. Дать замкнутый игровой цикл строительства

Использовать существующие ScreenPointToRay/Raycast, игровой ввод и примитивы: выбранный тип дома → предпросмотр клетки → зелёный/красный результат проверки → подтверждение или отмена. Простая таблица занятых клеток живёт в игре; дорожную сеть, поиск пути и общую систему строительства в Engine сейчас не вводить. Привязка editor gizmo и игровая строительная сетка — разные механики.

Готовность: исходный сценарий даёт 3 дома и баланс 200; покупка за 100 даёт 4 дома и баланс 100; через одну секунду дохода получается 140. Занятая клетка, недостаток денег, отказ спавна и отмена не списывают деньги. Клик по HUD не размещает дом в мире. Удаление/снос — отдельная следующая история, не скрытое требование первой версии.

### 4. Сделать итерации удобными для гейм-дизайнера

Показать имя выбранного дома, стоимость, ожидаемый доход и причину запрета. Сохранить существующий смысл Pause income: остановка дохода, а не обещание глобальной паузы всего мира. Вывести возможности выбранного runtime и понятную причину недоступного импортёра. Использовать проверенный импорт FBX/BLEND для замены примитива моделью дома.

Готовность: параметры меняются без переписывания C++; UI отражает новые значения; текст на русском сохраняется без Enter; после Play/Stop/Reload кнопка и клавиша вызывают действие ровно один раз; импортированная модель сохраняет материал после переноса проекта.

### 5. Сохранение партии — только после стабильного строительства

Определить небольшой версионированный игровой snapshot: баланс, параметры домов, их устойчивые игровые идентификаторы/позиции, оставшаяся доля интервала дохода. Не путать его с автоматическим восстановлением редактора, сценовым JSON и временем жизни GameSubsystem. Сначала реализовать в примере, добавлять общий API Engine только при доказанном недостатке существующих средств.

Готовность: сохранение → закрытие → загрузка даёт те же деньги, дома и доход без повторной оплаты; ошибочный snapshot не разрушает текущую партию; возвращение между сценами не дублирует дома. Это рекомендуемая следующая возможность, а не устранение подтверждённого бага.

## Объём следующего релиза

Рекомендую взять этапы 1–3 как первую законченную итерацию: **автор без правок ядра создаёт проект, меняет параметры и покупает дом кликом, получая проверяемый результат в HUD**. Этапы 4–5 делать после её проверки тем же агентом. Экономику оставить в Game; Engine улучшать в диагностике, доступности текущих API и обнаруженных дефектах.

Для проверок использовать существующие commandlets project.build, scene.property, session.lifecycle, trace.raycast, camera.screen-ray, ui.edit-text и asset.import. Игровые TryBuildHouse/occupancy/balance проверять в тестах проекта; если потребуется консольный вызов игрового сценария, он должен загрузить реальный игровой модуль, а не дублировать экономику внутри EngineCommandlets.

Не включать без отдельного запроса: ECS, визуальный скриптинг, полноценную физику, транспортную сеть, жителей/профессии, торговлю, массовый pathfinding. Отзыв этой персоны не обосновывает такой объём. Сроки не оцениваются до проверки этапа 1 и фиксации состава этапа 3.
