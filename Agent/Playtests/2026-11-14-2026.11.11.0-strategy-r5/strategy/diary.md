# Дневник r5 — диагностика AI и строй

## Замысел

Продолжить «Ремонтный коридор»: использовать AI Diagnostics на фактической группе во время Play/Pause, найти тактический ответ для шлюза и добавить один игровой шаг — переключение построения группы перед следующим приказом.

## Изменение игры

В `Source/ProjectGame.cpp` добавлена клавиша F: переключает `Ai::Group::SetFormation` следующего перемещения между линией (`columns=3`) и колонной (`columns=1`). Текущие слоты не изменяются до нового ПКМ; атака остаётся колонной для узкого прохода. HUD показывает счётчик группы и текущий строй следующего перемещения. В телеметрию добавлено `formationColumns`.

## Практический прогон AI Diagnostics

`r5-ai-diagnostics-game-retry-request.json` использует project.input настоящего r5: Play, выбор трёх бойцов рамкой, E сдвигает физический контейнер, группа получает приказ по коридору, F удерживается 30 кадров, затем Pause → diagnostics → Resume → новый ПКМ → Pause → diagnostics → Stop.

Paused snapshot нашёл `CorridorGuard` serial 1 и живую группу `Player order 131` serial 5. На ней:

- AUTO радиус `0.40000000596 м` (после STRATEGY-019), поле `ready`.
- A→B из (0, -6) в (0, 3.4) нашёл путь (`found`) при AUTO.
- Ячейка в проходе шлюза (12,52) имеет clearance `0.875 м`, цену 1 и walkable=true для AUTO.
- При ручном радиусе `1.0 м` та же ячейка walkable=false, а A→B вернул `partial`: поле не проводит агента полного радиуса через узкий центральный зазор.
- После нового приказа в колонну AUTO снова дал `path=found`, `field=ready`, radius 0.4.
- Отдельный запрос к guard serial1 вернул `Patrol / FollowRoute`, историю `Patrol → Pause → Patrol` и perception overlay (34 lines). Ячейка с guard-восприятием не смешивается со скриншотом выбранной группы.

Игровой вывод по диагностике: clearance центра шлюза равен 0.875 м. AUTO радиус живой группы равен радиусу бойца 0.4 м; ручной 1.0 м больше clearance и не даёт полного A→B. Это сравнение не предсказывает результат конкретного строя: его проверял отдельный длительный игровой приказ.

## Проверка переключения строя

`r5-ai-diagnostics-game-retry-telemetry.log`: приказ линии создал слоты примерно `(-0.9,-1.04)`, `(0,-1.04)`, `(0.9,-1.04)` при `formationColumns=3`. F удерживался 30 кадров: в следующей телеметрии режим стал `formationColumns=1`, но прежние слоты линии сохранились. После нового ПКМ принят второй приказ и слоты перестроились по колонне. Это не автоматический выбор движком: HUD прямо описывает состояние как строй следующего хода.

D3D `r5-ai-diagnostics-game-retry-line.bmp` показывает реальную группу в Play и HUD «ход линия». `r5-ai-diagnostics-game-retry-overlay.bmp` снят после paused diagnostics: видны сетка/стоимость/clearance, поток направления, колоночные slots и A→B probe поверх коридора; HUD показывает «ход колонна». Эти кадры действительно просмотрены.

## Исправление Engine

Координатор зарегистрировал STRATEGY-019: AUTO radius раньше брал радиус контроллера группы 1 м вместо крупнейшего живого участника. Его native regression был FAIL до fix и PASS после; r5 повторил AUTO/manual сравнение на настоящей игровой группе с новым Engine.lib SHA `4E7FB9ECDADC92F92B7AAB7BEF1FA5D31A25AB76752F8D899828D7860519530A`.

Поздний игровой повтор подтвердил STRATEGY-020: после line→column группа могла не достигнуть спроецированного slot. Root исправил это в движке; точный длинный Play-повтор подтверждён после STRATEGY-020b.

## Неудачные попытки и ограничения

- STRATEGY-018: открытие через Launcher использовало пользовательский default store. Прямой screenshot-only CUA `get_window_state` завис два раза (один вызов >500 с, второй >370 с); оба процесса редактора закрыты. До AI Diagnostics UI panel не дошёл. Это ограничение окружения/helper, не ошибка Engine. Точный запрос/ответы не скрывались.
- Первый discovery diagnostics запрос без `controller` ожидаемо дал fallback radius0.5 и `field=none`; использовался только для определения ID controllers, не как AUTO доказательство.
- Первый `r5-ai-diagnostics-game-request.json` имел неподдерживаемый шаг `{kind:"resume"}`, project.input вернул exit2 `unknown project.input step`. Исправлено в новом запросе через документированный `{kind:"control",action:"resume"}`; старый лог сохранён.
- Первые D3D frame-hook значения сняли игровой кадр до диагностического вызова, поэтому эти изображения не используются как доказательство диагностического overlay.

## Свежая проверка и ограничения

Исходный архив r5 на SDK4E7/STRATEGY-019 сохранён отдельно как pre020. После двух ранних застреваний root исправил STRATEGY-020 в движке; на финальной SDK020b проект пересобран. Удлинённый Play из той же свежей распаковки выполнил линию, смену на колонну и новый приказ: `orderStatus=на месте`, `Player order 131 movement: Arrived`, все три выбранных бойца остались connected, `barrierViolationFrames=0`. Для S2 конечная позиция (-0.791471,-0.971346) при slot (-0.875,-0.925), разрыв около 0.095 м. Охранник успел захватить отряд (`lost=1`), поэтому это подтверждает достижение группового приказа, но не победу кампании. После обновления README собран новый source-only ZIP; из него успешно выполнены clean-extract build/Play и Runtime60.

Проект остаётся процедурным: `Main.scene.json` пустой, диагностика выполнялась поддерживаемым project.input вызовом API, а не вручную открытой кнопкой AI (из-за STRATEGY-018). Полноценного ручного прохождения оператором, Edit authoring и NavMesh здесь нет; навигация — существующий NavGrid.

## Повтор STRATEGY-020 и итоговый архив

Два длительных прогона на SDK до финального исправления заканчивались `Moving` при неподвижном среднем бойце. Root воспроизвёл игровую причину отдельно и исправил проекцию слотов и возврат к проходимой ячейке поля; мои повторы не маскировали это кодом проекта. На SDK020b точный прежний запрос завершился `Arrived`: final diagnostics ответ указал `movement: Arrived`, AUTO `0.40000000596`, поле `ready`, A→B `found`, clearance `0.875`, `barrierViolationFrames=0`. Командлет exit0; последнее состояние игры — пленение, не победа.

После этого проекта README и source ZIP обновлены на SHA `4202492B1EFB832315DA1CD86281B9A540B5D3641011AB33BB76D6D1851B3FC2`. Предыдущий архив, прогоны до SDK020b и причины отказов сохранены как исторические результаты. Fresh extraction, сборка, Play и Runtime60 подтверждены именно на новом архиве, не на рабочей копии.
