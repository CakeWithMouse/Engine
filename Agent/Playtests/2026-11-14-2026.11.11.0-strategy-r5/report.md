# Repair Corridor r5 — строй и AI-диагностика

Тот же strategy_developer продолжил r4 на main a5468726, Engine 2026.11.11.0.
Работал один игровой агент. Общий прогон персон не запускался.

## Игровой результат

F выбирает линию или колонну для следующего приказа движения выделенной группе.
HUD показывает выбранный режим. Удержание F 30 кадров переключило его ровно один
раз; действующие места бойцов оставались прежними до следующего ПКМ. Новый
приказ задаёт реальные новые места в строю. Для атаки сохранена колонна,
подходящая для узкого шлюза. Выделение рамкой, групповые приказы и физический
сдвиг груза продолжают использовать прежние публичные API.

Агент опробовал новую диагностику на своей игре через настоящий
Engine.Scene.AiDiagnostics v1: paused Group5, поле ready, радиус AUTO=.4,
маршрут A(0,-6)→B(0,3.4) найден. В клетке шлюза clearance=.875 и cost 1;
для радиуса .4 walkable=true, для ручного 1.0 — false, путь partial.
Это полезное объяснение проходимости солдат через узкий проход.
Отдельный запрос охранника вернул Patrol/FollowRoute, историю FSM и 34 линии
восприятия. JSON: strategy/r5-ai-diagnostics-game-retry-{0,1,2,3}.json.

Настоящий D3D-кадр после включения diagnostics и кадра на паузе:
[overlay](strategy/r5-ai-diagnostics-game-retry-overlay.bmp).
Он показывает сетку, clearance/cost, поле, места группы и пробный маршрут.
Восприятие охранника проверялось отдельным API-запросом, не этим групповым кадром.

## Исправление и проверки

STRATEGY-019: диагностика использовала radius 1 виртуального центра Group,
хотя навигация использует максимальный радиус живых участников. Исправлен
только AUTO-выбор диагностического радиуса; игровая навигация и ABI не менялись.
Native UI-регрессия сначала упала на этом случае, после исправления прошла.
Тот же автор подтвердил исправление на своей настоящей группе (.400000006).
[Разбор и логи](fixes/STRATEGY-019.md).

STRATEGY-020 найден при продлении игрового прогона: после смены строя возле
барьера второй боец переставал двигаться, группа оставалась Moving.
CPU-регрессия без охранника воспроизвела две причины: места после проекции
оказывались слишком близко, а пограничная клетка допускала radius.4 бойца,
но отсутствовала в поле с округлённым radius.5. Исправлены резервирование мест
и возвращение в доступную соседнюю клетку поля. Промежуточный игровой повтор,
где первая правка была недостаточна, сохранён. Обе CPU-фазы теперь доходят
до Arrived без пересечения барьера, весь набор AI — 58/58.
[Подробности](fixes/STRATEGY-020.md).

На финальной SDK тот же исходный запрос автора завершил построение: первый
статус «на месте» в 13-м образце телеметрии, ещё при lost=0. Второй боец
достиг (-.791471,-.971346) при месте (-.875,-.925), ошибка около .095 м;
barrierViolationFrames=0. В продолженном без атаки сценарии охранник позже
вызывает поражение — это игровое правило, не незавершённый приказ.
Свидетельство: strategy/r5-fresh-long-column-post020b-telemetry.log.

Runtime/Editor/Commandlets/локальный SDK собраны; whole-archive link прошёл.
SDK Engine.lib SHA256:
`4202492B1EFB832315DA1CD86281B9A540B5D3641011AB33BB76D6D1851B3FC2`.
Native EditorUiTests проверил слои, поле, места группы, выбор контроллера,
ручной радиус и Play/Pause/Stop. Новый AiDiagnosticsCommandletTests проверил
preview/live/pause/clear/resume/stop и отказ на неверном запросе.

## Ограничение проверки UI

Инструмент get_window_state дважды завис до начала работы с панелью AI.
Открытие точного редактора подтверждено, ручной проход панели на игре не выполнен.
Поэтому практическая проверка использует настоящий диагностический API и D3D,
а поведение панели — отдельный native UI-тест. Эти виды доказательств не смешаны.
Неуспешные попытки сохранены и классифицированы в [issues.md](issues.md).
