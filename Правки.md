# Правки: анализ архитектуры, корректности и узких мест

Для владельца проекта. Анализ текущей рабочей копии от 12 сентября 2026 года. Изменения исходного кода в рамках этой задачи не вносились; приложение, сборка и тесты не запускались. Основание выводов — C++/HLSL, project/solution files и состояние Git, а не измерения FPS.

## 1. Главный вывод

В проекте уже есть существенная техническая основа: несколько проходов рендера, shader variants, отдельный depth SRV, кеширование FBX-ресурсов, аппаратный инстансинг, каскадные тени и compute-частицы. Основное ограничение развития — отсутствие единого контракта кадра и владения ресурсами. Компоненты одновременно содержат поведение, данные сцены и D3D draw-код, а подготовка камеры/света повторяется на уровне отдельных объектов и проходов.

Первым этапом стоит стабилизировать правильность кадра и воспроизводимость окружения. Оптимизация текущего FPS без этого может скрыть ошибки: скорость симуляции зависит от частоты кадров, Forward и Deferred не эквивалентны по материалам, а shader compiler всегда отключает оптимизацию.

Наиболее сильные **кандидаты** на runtime bottleneck:

| Кандидат | Когда проявляется | Основание |
|---|---|---|
| Подготовка объектов на CPU | Много компонентов/инстансов, включены тени | Матрицы камеры инвертируются и свет копируется для каждого объекта; обновления повторяются в draw и shadow |
| Сортировка частиц | Большие emitter или много emitter | Полная bitonic network с отдельным dispatch и CB update на каждый шаг |
| Отправка draw calls и лишняя геометрия | Много объектов/submesh, три каскада | Нет общего visibility pass и батчинга FBX draws; общий rasterizer без back-face culling |
| Полоса памяти G-buffer | Высокое разрешение | 20 байт цветовых MRT на пиксель плюс depth; world position хранится отдельно |
| Создание instance buffers | Массовое добавление экземпляров | GPU buffer/SRV пересоздаются при каждом добавлении |
| Неоптимизированные HLSL | Любая нагруженная GPU-сцена | `D3DCOMPILE_SKIP_OPTIMIZATION` в общем и particle compiler |

Назвать единственного победителя или процент ускорения без CPU/GPU timings нельзя. Ниже подтвержденные свойства кода отделены от предполагаемой стоимости.

## 2. Приоритеты

- **P0** — дефект, способный прервать нормальный lifecycle, привести к неопределенному поведению или продолжению работы с невалидными ресурсами. Исправлять до расширения соответствующего пути.
- **P1** — ошибки кадра, контракта API, переносимости или владения, которые стоит закрыть в ближайшей серии изменений.
- **P2** — производительность, качество изображения и архитектурные улучшения после восстановления корректности; порядок уточнять замерами.

Приоритет отражает очередность инженерной работы, а не измеренное влияние на FPS. Пути в документе относительны корню репозитория. ## 3. Жизненный цикл и воспроизводимость

### P0. WM_QUIT не останавливает внешний цикл

**Где:** `Game.cpp`, `Game::Run` (начало функции около строки 1527), `Exit`; `Display.cpp`, `WindowProc`.

`Run` содержит внешний `while (true)` и внутренний цикл `PeekMessage`. При `WM_QUIT` выполняется `break` только из внутреннего цикла. После сообщения о завершении приложение продолжает `Update`, draw и `Present`; после закрытия окна внешний цикл тоже не заканчивается. Отдельный `MessageHandler`, который вызывает `Exit`, не используется основным циклом, а `Exit` сам только вызывает пустой `DestroyResources` и отправляет `WM_QUIT`.

**Исправление:** единый running/quit contract: завершать `Run` до начала следующего кадра, иметь явный путь shutdown после выхода из цикла. Возвращаемый результат `Present` учитывать отдельно, а не продолжать бесконечно после ошибки устройства.

**Критерий приемки:** закрытие окна и Escape завершают процесс штатно; после принятого quit draw больше не отправляется. Это будущая проверка после разрешения на запуск.

### P0. Ошибки инициализации не останавливают дальнейшую работу

**Где:** `Game::Initialize`, `CreateDeviceAndSwapChain`, `CreateDepthBuffer`, `CreateBackBuffer`, `InitShaderBuffers`.

После неудачи `CreateDeviceAndSwapChain` печатается сообщение, но затем вызывается `InitRenderTarget`, использующий `SwapChain`. Ошибки depth texture/DSV не прекращают последовательность создания ресурсов. `Initialize` возвращает `void`, поэтому вызывающая сторона не получает признак готовности. `InitShaderBuffers` объявлена возвращающей `HRESULT`, но в конце успешного пути нет `return`; результат создания input layout также не проверяется. `CreateBackBuffer` скрывает неудачу от своего вызывающего кода.

**Исправление:** возвращать результат всей инициализации и не входить в `Run` при неудаче; передавать ошибки вверх, создавать ресурсы во временных RAII-объектах и публиковать их только после успеха. У `InitShaderBuffers` должны быть определенные return values на всех путях.

Также список feature levels доходит до 9.x, хотя используемые shaders требуют SM5 и GPU-частицы используют compute. Согласовать минимальные требования приложения с выбранным feature level; успешное создание низкого feature level не означает поддержку всего renderer.

**Критерий приемки:** отсутствие HLSL/ошибка shader/device creation дает понятный отказ и освобождение уже созданных ресурсов, без перехода к невалидным draw.

### P1. Окружение не воспроизводится из одного репозитория

**Где:** `1_Lab/1_Lab.sln`, `1_Lab/1_Lab.vcxproj`, `StartMain.cpp`, `.gitignore`.

Подтверждено неправильное сопоставление: solution `Debug|x64` собирает project `Release|Win32`. Это меняет и разрядность, и debugging/optimization assumptions. Кроме того, Assimp/stb_image не обеспечены явным manifest с версиями; проект импортирует пользовательские `.props`. Asset paths завязаны на два локальных диска, HLSL — на current working directory.

В Git уже отслеживаются некоторые результаты сборки (`.ilk`, `.pdb`, `.tlog` и др.), а рабочая директория содержит временные каталоги и посторонние файлы. Поэтому копирование всей папки и передача Git checkout дают различное содержимое.

**Исправление:** сначала починить mapping `.sln`, закрепить язык и конфигурации, затем задать версионируемые зависимости и способ поиска assets от project/content root. Описать runtime DLL для выбранной разрядности. Отдельным согласованным изменением убрать build outputs из индекса и дополнить ignore rules; не удалять пользовательские файлы без разбора. Исключение уже отслеживаемых файлов требует работы с индексом, одного `.gitignore` недостаточно.

**Критерий приемки:** новая рабочая копия имеет документированный путь подготовки и однозначную конфигурацию. Саму сборку на чистом окружении выполнять только по отдельному разрешению.

### P1. Resize объявлен, но не реализован

**Где:** `Display::WindowProc`, ветка `WM_SIZE`; `Game.h` с объявлениями resize-related методов; `Game::InitDeferredResources`; `Player::UpdateProjectionMatrix`.

`WM_SIZE` читает client rect и больше ничего не делает. Размеры `Display` остаются прежними; back buffer/depth не пересоздаются, `ResizeBuffers` в рендер-коде отсутствует. Проверка размеров deferred texture не помогает, потому что получает старые значения из `Display`.

**Исправление:** единый `OnResize`: отложить изменение до безопасной границы кадра, освободить bindings/views back buffer, пересоздать swap-chain-dependent ресурсы, обновить viewport и projection. Отдельно обработать minimize/нулевой размер. Сейчас окно также создается с outer dimensions, а не с гарантированным client area заданного размера — это стоит привести к тому же контракту.

**Критерий приемки:** после resize совпадают client area, back buffer, depth, G-buffer и aspect камеры.

## 4. Корректность кадра и GPU-состояния

### P1. Время симуляции определяется количеством кадров

**Где:** `Game::Run`, `Game::Update`; `SunGame::DrawForward/DrawDeffered`; `BaseGame::Draw`; `ParticleSystemComponent::Tick`.

Реальное `deltaTime` измеряется, но сцена и камера получают `0.13f` из draw. Например, 60 кадров дают 7.8 единицы переданного в `Tick` времени за секунду, 144 кадра — 18.72. Частицы ограничивают этот шаг до `0.05f`: при тех же частотах это 3 и 7.2 единицы simulation time. Это арифметика по коду, не результат измерения работающей сцены. `FIXED_FPS` лишь ограничивает большое измеренное delta до 0.1 и не реализует fixed-step loop.

**Исправление:** перенести `UpdateCamera`, `Tick` и подготовку сцены до выбора render path; передавать один настоящий delta либо ввести fixed-step accumulator с ограничением catch-up. Рендер не должен выбирать скорость симуляции. Константы существующих скоростей придется пересмотреть, поскольку они могли подбираться под прежний шаг.

**Критерий приемки:** одинаковое движение за одинаковое wall-clock время при разных частотах рендера; Forward/Deferred не меняют логику обновления.

### P1. RenderType и shader variants могут расходиться

**Где:** `Game::RegisterComponent`, `ShouldUseDeferredGeometryVariant`, `SetRenderingType`; fallback в `SunGame::DrawDeffered`.

Компоненту назначается одна пара VS/PS при регистрации. `SetRenderingType` меняет только enum. Поэтому переключение после регистрации оставляет старый вариант шейдера; fallback из deferred в forward тоже продолжает использовать G-buffer shaders на одном цветном target. Признак прозрачности участвует в выборе варианта и также фактически является частью этого контракта.

**Исправление:** хранить у материала варианты для проходов и выбирать нужный при submit/draw. Более дешевое промежуточное решение — запретить runtime-переключение после регистрации и явно проваливать неудачную инициализацию deferred, убрав ложный fallback. Для произвольного shader path проверять поддержку нужного варианта: define сам по себе не создает MRT output.

**Критерий приемки:** цветной target и shader output signature всегда соответствуют проходу; невозможный fallback выдает понятную ошибку.

### P1. Input layout зависит от предыдущего объекта

**Где:** `GameComponent::Render`, `FBXComponent::Render/RenderShadow`, `Game::RenderShadowMaps`, `SunGame::DrawForward`.

FBX draw устанавливает собственный input layout, а обычный `GameComponent::Render` свой layout не устанавливает и ожидает, что он уже назначен снаружи. После FBX или shadow draw примитив может получить mesh/shadow layout предыдущего объекта. В Forward после shadow pass восстанавливаются viewport/rasterizer/targets, но не базовый layout. Порядок компонентов в `std::map` превращается в скрытую зависимость результата кадра.

**Исправление:** каждый draw packet должен явно определять layout и обязательное pipeline state, либо renderer должен гарантированно назначать их при переключении типов пакетов. Добавить явные состояния для opaque, transparent, skybox и shadow, после чего уже оптимизировать лишние `Set*` вызовы кешем состояний.

**Критерий приемки:** перестановка независимых opaque objects и изменение их имен не ломают vertex interpretation.

### P1. Прозрачность не имеет полноценного прохода

**Где:** `SunGame::DrawForward/DrawDeffered`, `Game::CreateDepthBuffer/CreateBlendStates`, `ParticleSystemComponent::Render`.

Forward перемешивает opaque/transparent в порядке имен. Deferred отделяет прозрачные объекты, но не сортирует их. Для прозрачности меняется только blend state; depth writes не отключаются. Частицы сортируются только внутри своего emitter, поэтому это не решает смешивание между системами частиц и другими объектами. Даже пиксели с малой alpha могут записывать depth и мешать следующим прозрачным draws.

**Исправление:** opaque pass завершать до transparency; сортировать прозрачные draw packets от дальних к ближним, оставить depth test и выключить depth write. Для пересекающихся прозрачных мешей одной сортировки объектов недостаточно — это отдельное ограничение, которое нужно принять или решать специальной техникой. Skybox должен получить явный контракт глубины вместо обычного куба со стандартной записью depth.

**Критерий приемки:** прозрачные поверхности не скрывают последующие поверхности только из-за своей записи depth; порядок opaque объектов не влияет на depth collision частиц.

### P1. Данные directional light и shadows обновляются несогласованно

**Где:** `GameComponent::Update`, `Game::RenderShadowMaps/UpdateShadowCascades`, оба полных draw-пути.

В начале `Update` directional light заменяется значениями по умолчанию. Настройки из `Game` копируются обратно только внутри `IsShadowEnabled()`. Значит, отключение теней мешает обычным component buffers получать настроенный directional light, хотя сам свет должен работать независимо. `SetGame` не решает проблему: следующий `Update` перезапишет значения.

Еще одна зависимость: обычный `Update` компонентов выполняется до `UpdateShadowCascades`. `RenderShadow` повторно обновляет opaque компоненты уже после вычисления матриц, поэтому они могут получить актуальные данные; transparent-компоненты shadow draw пропускают и могут сохранить матрицы предыдущего кадра. Полагаться на побочный `Update` внутри shadow нельзя.

**Исправление:** `camera → world transforms → lights/cascades → frame constants → draw packets`; параметры directional light обновлять независимо от включения теней. Все проходы кадра должны читать один завершенный snapshot.

**Критерий приемки:** свет регулируется при выключенных тенях; все материалы кадра используют каскады того же кадра.

### P1. Deferred не сохраняет свойства forward-материала

**Где:** `Shaders/ReflectiveSphere.hlsl`, `ReflectiveFBX.hlsl`, `RotatedFigure.hlsl`; `Game::UpdateDeferredLightingBuffer`.

Reflective G-buffer branches пишут только albedo, normal и world position. Общий deferred lighting не получает cubemap/reflection strength/Fresnel parameters и не вычисляет соответствующие отражения. Ambient задан иначе, чем в component forward buffers. Поэтому переключение пути меняет модель освещения, а не только способ ее вычисления.

**Исправление:** определить общий lighting/material contract. Выбрать, какие свойства кодируются в G-buffer, а какие рисуются отдельным forward-проходом. Вынести общие lighting functions и параметры; если reflective остается forward-only, исключать его из G-buffer и правильно композить с depth. Не маскировать отличия одной увеличенной ambient-константой.

**Критерий приемки:** для заявленной общей модели материала оба пути дают сопоставимое изображение; исключения названы явно.

## 5. Компоненты, инстансинг и владение

### P0 для общего CreateInstance. Неинициализированный GamePtr

**Где:** `GameComponents.h`, поле `GamePtr`; `GameComponents.cpp`, конструкторы, `CreateInstance`, `Update`.

Поле `GamePtr` не имеет инициализатора. Обычная регистрация выставляет его, но общий `CreateInstance` создает объект и кладет в `InstanceArray`, не вызывая `SetGame`. Затем `Update` рекурсивно вызывает `Inst->Update`, где читается `GamePtr`. Это путь с неопределенным поведением. Специализированный `CreateSphereInstance` указатель выставляет, поэтому нельзя переносить этот вывод на любой sphere instance как уже наблюдавшееся падение.

**Исправление:** все raw observer pointers и shader pointers инициализировать `nullptr`; фабрика экземпляров должна устанавливать owner/context до помещения объекта в обновляемый список. Установить одинаковые постусловия для общего и специализированных API.

### P1. Ресурсы и объекты не имеют единого владельца

**Где:** `Game::~Game`, пустой `DestroyResources`, `GameComponent` с default destructor, `SphereComponent::CreateSphereInstance`, `RegisterComponent`.

`Game` не удаляет компоненты из `Components`; экземпляры также не освобождаются владельцем. Базовый компонент хранит VB/IB/CB/SRV/sampler как raw COM pointers без общей очистки. У `Game` часть D3D-ресурсов в `ComPtr`, часть raw; destructor освобождает shader cache и три сервисных объекта, но не весь набор. У `Game` есть виртуальные методы, а destructor не виртуальный: удаление наследника через `Game*` не имеет правильного полиморфного контракта.

В `CreateSphereInstance` вызов `GetDevice` увеличивает COM refcount, а соответствующий `Release` закомментирован. Это отдельная утечка на каждое создание экземпляра. Общий `CreateInstance` освобождает временную ссылку до использования указателя — устройство пока удерживается `Game`, но такой lifetime-pattern нужно заменить ясным RAII.

**Исправление:** `Game/Scene` владеет компонентами через `unique_ptr`, instance owner владеет экземплярами, `Parent` и light registry — observer references/handles. GPU-объекты — `ComPtr`; разделяемые model/texture assets — resource handles с явным владельцем. `Game` получает виртуальный destructor. Миграцию делать по подсистемам, чтобы не получить double release на уже разделяемых FBX-буферах.

**Критерий приемки:** создание/уничтожение сцены возвращает CPU/GPU resources к исходному набору; shutdown действительно вызывает этот путь. Проверка live resources потребует отдельного разрешения на запуск.

### P1. Регистрация с повторным именем сообщает ложный успех

**Где:** `Game::RegisterComponent`.

Метод сначала связывает компонент, регистрирует свет или создает GPU buffers, а затем вызывает `Components.emplace` без проверки результата. При повторном имени новый объект не входит в map, но метод возвращает `true`; для источника света указатель уже добавлен в `PointLights`. `nullptr` также не проверяется перед разыменованием.

**Исправление:** проверить pointer/name до побочных действий; вернуть различимые ошибки; определить политику replace/reject и unregister. Световой список должен изменяться атомарно с реестром компонентов.

**Критерий приемки:** успешная регистрация означает наличие именно переданного компонента в сцене; неудачная не оставляет ресурсов и вторичных записей.

### P1. Transform cache может вернуть старую позицию

**Где:** `GameComponents.h`, `SetPosition`, `SetParent`; `GetWorldMatrix`.

У корня кеш возвращается при `!bTransformDirty`. `SetPosition` не инвалидирует его. После изменения позиции статичный объект может продолжать рисоваться со старой матрицей. У дочерних объектов кеш фактически не экономит вычисления: каждый запрос снова поднимается по родителям. Цикл parent-ссылок приводит к неограниченной рекурсии. `GetCenter` возвращает local position, в частности light registry не учитывает parent transform.

**Исправление:** единый набор transform setters с инвалидацией; version-based world transform или вычисление иерархии один раз в топологическом порядке; запрет циклов; отдельные `GetLocalPosition`/`GetWorldPosition`. Не обновлять полное поддерево рекурсивно на каждый запрос draw.

### P1. Цветной инстансинг и тени описывают разную геометрию

**Где:** `GameComponent::Render`, `RenderShadow`, `GetBufferElementCount`, `CreateInstanceBuffer`.

При непустом массиве цветной проход рисует только элементы `InstanceArray`, без владельца. Shadow pass рисует один обычный `DrawIndexed` владельца, не используя instance buffer. Получается принципиально разный набор преобразований в цвете и тенях. Это не недостаток разрешения shadow map.

Проверка `GetBufferElementCount() != InstanceArray.size()` никогда не обнаруживает рассинхронизацию емкости: getter возвращает тот же `InstanceArray.size()`. Реальная выделенная capacity не хранится.

**Исправление:** формализовать, входит ли владелец в список видимых экземпляров; использовать один instance transform stream во всех геометрических проходах, добавить shadow VS/путь для инстансов. Хранить фактическую GPU capacity и valid count раздельно.

**Критерий приемки:** каждый видимый opaque instance отбрасывает тень из своей world matrix; рост массива не может вызвать загрузку за пределы выделенного буфера.

## 6. Производительность: что менять и почему

### P2. Общие данные кадра пересчитываются для каждого объекта

**Где:** `GameComponent::Update` около строки 131; `FBXComponent::Render/RenderShadow`; `Game::RenderDeferredDebugOverlay`.

Каждый компонент инвертирует одинаковые view/projection matrices, очищает/копирует light arrays и вызывает `GetPointLights`, возвращающий новый `vector`. Затем это повторяется для экземпляров. FBX дополнительно вызывает `Update` в цветном draw, а shadow вызывает его по каскадам. Debug overlay четырежды готовит большие buffers с inverse matrices и lights, хотя показываемым диагностическим режимам не нужен весь этот набор.

Для `N` объектов, `I` экземпляров и `C=3` каскадов общая подготовка может повторяться порядка `O((N+I) × (1+C))`; у FBX есть дополнительное обновление цветного прохода. Это оценка структуры работы, не точное число всех вызовов для любой сцены. Родительские цепочки добавляют собственную стоимость.

**Исправление:** разделить `FrameConstants` (view/projection/inverse/camera/light/shadow), `ObjectConstants` (world/normal matrix/color), `MaterialConstants` и instance stream. Frame data формировать один раз после камеры/каскадов; на instance хранить только необходимое для конкретного draw. Shadow должен получать готовую world matrix, а не запускать весь `Update`.

**Ожидаемый эффект:** меньше CPU-работы, временных allocations и загружаемых констант, особенно при большом количестве объектов и тенях. Проверять CPU time подготовки и число `UpdateSubresource`, а не только общий FPS.

### P2. Создание инстансов постоянно перераспределяет GPU buffer

**Где:** `SphereComponent::CreateSphereInstance`, `GameComponent::CreateInstanceBuffer/UpdateInstanceBuffer`.

Каждое добавление уничтожает buffer/SRV и создает их под точное новое количество. При последовательном росте до `N` это `N` операций создания и сумма запрашиваемых размеров, пропорциональная `1+2+...+N`. Это **не** означает одновременную квадратичную резидентную память или обязательное копирование всех старых данных GPU на каждом добавлении; проблема — churn allocations/driver calls и отсутствие capacity strategy.

Во время draw создается временный `vector<InstData>`, заполняется и целиком копируется через `Map(WRITE_DISCARD)`. Хотя отдельные instance constant buffers не отправляются, их CPU `Update` все равно выполняется.

**Исправление:** bulk creation/finalize для загрузки сцены, либо capacity с геометрическим ростом; постоянный staging vector с `reserve`; отдельная легкая instance record вместо полного GameComponent там, где индивидуальное поведение не требуется. Формат и допустимость resource flags для выбранной стратегии upload проверить отдельно при реализации.

**Метрики:** время создания `N` экземпляров, число `CreateBuffer`, CPU time upload, bytes/frame. Это в первую очередь bottleneck создания и CPU-подготовки, не доказательство плохой скорости самого `DrawIndexedInstanced`.

### P2. Полная bitonic-сортировка частиц дорогая по числу dispatch

**Где:** `ParticleSystemComponent::DispatchSort` около строки 535; `GPUParticleSystem.hlsl`, `CSBuildSortKeys`, `CSBitonicSort`.

Для массива `M=2^k` вложенные циклы выполняют `k(k+1)/2` сортировочных dispatch на каждый render emitter, плюс один для ключей и один для симуляции. Для условных 10000 частиц буфер округляется до 16384: `k=14`, получается 105 sort dispatch, 107 compute dispatch вместе с keys/simulation. Это точный счетчик по алгоритму при таком количестве, а не замер GPU duration. Работа сети порядка `O(M log² M)`.

**Исправление:** сначала сделать корректными общую transparency и depth policy. Затем измерить симуляцию, сортировку и particle fill отдельно. Для эффектов, где подходит additive blending, можно иметь явный материал без сортировки; обычная alpha transparency требует сохранения корректного порядка. Если сортировка доминирует — рассмотреть сортировку блоков в shared memory и более эффективное межблочное объединение/radix подход. Выбор привязать к фактическим размерам emitter и платформе.

Также перенести compute simulation в отдельную фазу кадра. Сейчас дополнительный вызов `Render` может симулировать emitter повторно, а невызванный `Render` останавливает его симуляцию. Sorting и rendering можно привязывать к видимости отдельно от времени жизни симуляции.

**Метрики:** GPU ms simulation/sort/draw, dispatch count, overdraw; число частиц само по себе не показывает стоимость пиксельного покрытия.

### P2. Нет общего отсечения видимости и группировки draw packets

**Где:** обходы `Components` в полном renderer, `Game::RenderShadowMaps`, `FBXComponent::Render`, `Game::Run` rasterizer.

Каждый проход снова обходит реестр. Все подходящие объекты отправляются в draw без frustum/occlusion culling; shadow повторяет это для трех каскадов. Кеш FBX экономит хранение геометрии, но повторные модели все равно рисуются отдельно по submesh. Основной rasterizer использует `D3D11_CULL_NONE`.

**Исправление:** ввести render packets с bounds и flags; построить отдельные видимые списки для камеры и каскадов; opaque сортировать по pipeline/material/mesh, применять instancing для совместимых повторяющихся мешей. Culling включать после проверки winding и double-sided materials, не менять глобальный флаг вслепую.

**Метрики:** CPU submit time, draw calls, rendered/culled objects, triangles и shadow draws. Сам `std::map` не стоит объявлять главным bottleneck без сравнения: смена контейнера не устранит лишние draws и полное обновление каждого объекта.

### P2. G-buffer тратит bandwidth на world position

**Где:** `Game::InitDeferredResources`, `RotatedFigure.hlsl`, G-buffer branches материалов.

Три MRT занимают 4+8+8 = 20 байт на пиксель, depth — еще 4 байта. При 1920×1080 это примерно 39.6 MiB цветовых буферов и 7.9 MiB depth; back buffer, shadow maps, driver overhead и другие ресурсы сюда не включены. Это расчет размера хранения, **не измеренная пропускная способность**: реальная стоимость чтения/записи зависит от покрытия, кешей и компрессии GPU.

Третий target называется `Material`, но хранит half-float world position. В координатах большой величины half precision ухудшает точность; при этом depth и inverse matrices уже есть. Шейдер использует их лишь для fallback около нулевой позиции.

**Исправление:** сначала переименовать ресурс по реальному назначению или явно определить новый G-buffer contract. Затем сравнить восстановление позиции из depth с текущим хранением на нужном диапазоне камеры; при подходящей точности освободить target либо использовать его для material properties. Уплотнение normals также оценивать по требуемому качеству, а не только размеру.

**Метрики:** GPU time geometry/lighting при нескольких разрешениях и визуальная ошибка восстановленной позиции. Удаление target — изменение CPU/HLSL/overlay contract целиком.

### P2. HLSL всегда компилируется без оптимизации

**Где:** `Game::CreateShader` около строки 1919; `ParticleSystemComponent::CompileShaders`.

Флаги `DEBUG | SKIP_OPTIMIZATION` не зависят от C++ configuration. Поэтому выбор Release сам по себе не дает оптимизированные runtime shaders. Shader cache есть только в памяти процесса; кроме того, FBX input layout компилирует вспомогательный VS на экземпляр при первом draw.

**Исправление:** явно разделить debug shader policy и optimized policy, включить policy в cache key; вынести input layouts в кеш по vertex declaration и shader signature. Далее, при необходимости, добавить offline shader artifacts или disk cache. До этого измерения GPU следует маркировать как относящиеся к неоптимизированному HLSL.

**Ожидаемый эффект:** возможное уменьшение GPU instruction cost и first-frame stalls; проценты заранее неизвестны. После смены флагов нужно проверить изображение: оптимизатор способен проявить ошибки, ранее скрытые в коде.

### P2. Лишние постоянные расходы и неполная телеметрия

**Где:** `Game::Initialize`, `RenderDeferredDebugOverlay`, `Run`, `EndFrame`, `Update`.

G-buffer и shadow maps создаются независимо от использования. Три shadow maps по 2048²×4 байта — 48 MiB хранения depth, без учета накладных расходов. Overlay всегда добавляет четыре draws. Есть повторные clear back buffer/depth между `Run` и draw. `Present(1,0)` может ограничивать видимый FPS частотой дисплея, а `Objects` не считает скрытые экземпляры и submesh.

**Исправление:** ленивое создание ресурсов по включенным возможностям, переключаемый overlay, один владелец clears, счетчики draw/triangles/instances/dispatches и отдельные CPU/GPU timings. Синхронизацию Present сделать управляемой для измерений, сохранив нормальный пользовательский режим.

Не стоит сначала удалять каждый `ClearState`: на текущей архитектуре это может увеличить количество скрытых state dependencies. Сначала явные pass contracts, затем оптимизация state changes.

## 7. Импорт, материалы и ввод

### P1. Импорт теряет transforms узлов и часть данных материалов

**Где:** `FBXComponent::ProcessNode/ProcessMesh/ProcessMaterial/Render`, `BaseFBX.hlsl`.

`ProcessNode` рекурсивно проходит узлы, но не накапливает и не применяет `node->mTransformation`. Для файлов с нетривиальной иерархией геометрия будет размещена неверно. Цвет материала извлекается и хранится в mesh records, но draw не загружает его отдельно перед каждым submesh. `BaseFBX.hlsl` безусловно семплирует текстуру, не используя `HasTexture` как fallback для модели без изображения.

**Исправление:** определить import contract: bake node transforms в вершины/нормали либо сохранить render nodes с transform. Материалы оформлять по submesh с валидными default textures/constants. Отдельно определить неподдерживаемые свойства вместо молчаливой потери.

### P1/P2. FBX cache имеет скрытые предусловия

**Где:** `FBXComponent::LoadModel/CreateMeshBuffers`, статические `modelCache/textureCache`.

Кеш модели сохраняет GPU buffers, counts и bounds, а путь до создания буферов зависит от уже назначенного `GamePtr`. Если загрузить модель без устройства, можно опубликовать запись с пустыми GPU pointers. Последующий cache hit создает render records без исходных CPU vertices, поэтому обычное позднее создание буферов уже не имеет достаточных данных. Ключ также не включает device; повторное использование кеша другим устройством не предусмотрено.

**Исправление:** разделить CPU imported asset и device-specific GPU resource либо запретить публикацию GPU cache до полного успеха. Нормализовать путь до канонического asset identity, а не только слеши/регистр. Наличие mutex не делает immediate-context операции потокобезопасным asset pipeline.

### P2. Нормали и цветовой пайплайн ограничивают качество

**Где:** `BaseFBX.hlsl` и другие material VS/PS, texture creation, G-buffer formats.

Нормаль FBX преобразуется через `(float3x3)worldMatrix`; при неравномерном scale это не эквивалентно inverse-transpose normal matrix. Для примитивов normal generation зависит от конкретного shader: например, `RotatedFigure` использует derivatives world position. Универсального normal contract нет.

Изображения и back buffer используют UNORM; финальный цвет часто ограничивается `saturate`, mip chain для текстур не строится. Это ограничивает корректную работу с яркостью, дальними текстурами и единообразием Forward/Deferred.

**Исправление:** общий normal matrix contract и политика normal orientation; явно отделить цветовые текстуры от линейных data textures, затем при необходимости вводить linear HDR intermediate/tone mapping. Mipmaps добавлять с определенным ownership и загрузочным этапом. Не называть текущую систему PBR до появления соответствующих material data и lighting model.

### P1/P2. Mouse offset теряет события, а input lifecycle зависит от draw

**Где:** `InputDevice::OnMouseMove`, `Display::WindowProc`, конец полных draw-путей.

`MouseOffset` перезаписывается каждым Raw Input событием. Если за кадр поступило несколько событий, опрос камерой видит только последнее. Сброс offset выполняется внутри конкретного draw; это связывает input с render implementation. `WM_INPUT` также выделяет/освобождает byte array на каждое событие. Явного сброса pressed keys при потере фокуса в оконной процедуре нет.

**Исправление:** frame input snapshot с накоплением относительных смещений и колесика, централизованными begin/end frame, обработкой focus loss. Для Raw Input использовать переиспользуемое хранилище. Производительность allocations вторична по отношению к потере событий.

## 8. Предлагаемая архитектура следующего этапа

Это направление рефакторинга, а не описание уже имеющихся модулей.

| Граница | Что в нее перенести |
|---|---|
| Application / platform | Win32 loop, lifecycle, окно, resize, input snapshot, frame clock |
| Scene | Владение компонентами, transform hierarchy, lights, один update до рендера |
| RendererD3D11 | Device/context/swap chain, resize-dependent resources, общий контракт кадра |
| Render passes | Shadow, opaque forward либо G-buffer+lighting, skybox, particle compute, transparency, debug |
| Render packets | Mesh/material/transform/bounds и нужный shader variant без вызова поведения компонента |
| Resource cache | Imported CPU assets, device GPU assets, shader variants и input layouts с ясным lifetime |

На первом шаге достаточно извлечь последовательность проходов из `SunGame` в один renderer и перевести camera/lights в frame data. Полный ECS, сложный render graph и многопоточность не нужны для решения уже подтвержденных проблем. Их имеет смысл вводить при конкретных требованиях после стабилизации границ.

## 9. Практическая очередность изменений

1. **Передача проекта:** исправить mapping конфигураций; описать/закрепить зависимости и content root; отдельно очистить индекс от build artifacts. Оба подготовленных документа передавать вместе с исходниками и `AGENTS.md`.
2. **Жизненный цикл:** quit loop, результаты инициализации, неопределенные поля, return values, определенный shutdown. Это небольшие исправления до большого переноса классов.
3. **Владение:** компоненты/инстансы и COM-ресурсы, уникальность регистрации, unregister. Сохранить существующее разделение FBX buffers при миграции.
4. **Единый кадр:** настоящее время, input snapshot, transform/world data, camera/light/shadow data один раз; убрать `Update` из draw/shadow и отделить particle simulation от `Render`.
5. **Корректность renderer:** variants по проходам, explicit input/depth/blend state, opaque/transparent ordering, instance shadows, resize и material parity.
6. **Измерения после отдельного разрешения:** оптимизированные shaders и корректная Release-конфигурация, выключаемая диагностика, CPU/GPU timings.
7. **Оптимизация по результатам:** frame constants, instance capacity, visibility/batching, particle sort, G-buffer bandwidth — в порядке измеренной стоимости для целевых сцен.

## 10. Как подтвердить bottleneck после разрешения на запуск

Это план будущей проверки, а не выполненные тесты или добавленная тестовая инфраструктура.

Зафиксировать конфигурацию проекта, режим compiler flags HLSL, разрешение, режим Present, число объектов/instances/submesh/lights/particles, включение теней и overlay. Измерять отдельные CPU times для update, подготовки данных и submit, GPU timestamps для shadow, geometry, lighting, particle simulation/sort/draw и transparency. Время ожидания Present отделять от полезной работы; GPU queries читать без принудительного ожидания в том же кадре.

Провести независимые изменения нагрузки: разрешение при постоянной геометрии; число объектов при постоянном разрешении; shadows on/off; число emitter/частиц; overlay on/off. Уменьшение GPU-времени с разрешением укажет на зависимость от пикселей/bandwidth; рост CPU submit с количеством объектов — на подготовку/dispatch/draw overhead. Это направления диагностики, не универсальные доказательства одной причины.

Использовать повторяемый участок работы и несколько замеров, отдельно рассматривать startup/первую компиляцию и steady state. Только после этого фиксировать «главный bottleneck» и целевой бюджет в миллисекундах. Текущий счетчик FPS с VSync для такого заключения недостаточен.
